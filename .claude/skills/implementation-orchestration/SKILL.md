# 実装オーケストレーション

サブエージェントのネスト委任を活用して、設計→実装→レビュー→修正のサイクルを自律的に回す実装パイプライン。

## Essence（なぜこの構造なのか）

このスキルは二つの why から必然的に導かれている。手順だけを踏んで why を見失うと、地の「自分で実装して完了報告する」挙動に回帰し、この構造は崩れる。

### why 1: 最上位オーケストレーターのコンテキストは保護資産である

最上位オーケストレーター（Undine）のコンテキストは、wave 全体を保つための希少な保護資産である。Undine は全体像・依存関係・ユーザー判断・wave gate を保持しており、それこそがユーザーの判断基準の代理物である。実装・テスト・大規模な差分棚卸しといった雑事でこのコンテキストを汚染させることは、進行の中枢を削る行為であり、原則として禁止する。

### why 2: 各タスクをコンテキストウィンドウ制約の内側に設計する

これは暗黙だが決定的な設計原理である。観測事実として、**同一ドメインでは実装がレビューの約 4 倍のトークンを消費する。** そして実装誤りの大半は、コンテキストウィンドウ超過によるタスクの不完全さから生じる。大規模実装では、この不完全さを検知する枠組みが要る。

- 実装（重い）は使い捨ての Gnome コンテキストへ逃がす。
- レビュー（軽い）は別の Review-Sylph コンテキストで行う。レビューは負荷が低いぶん、実装の不完全さを正確に検知できる。
- ただしこの実装→レビュー→修正ループを Undine が直接回すと、Undine のコンテキストが大きく棄損される。だから**中間層として Orch-Sylph が入る。** Orch-Sylph が 1 ドメインのループを自分のコンテキストで抱え、Undine には結論（完了報告・レビュー判定）だけを返す。

つまり階層は「おしゃれ」ではなく、**トークン非対称性とコンテキストウィンドウ制約から出た必然の構造**である。

## パターン概要

```
Undine (設計エージェント・最上位オーケストレーター)
├── Sylph-Orch-A (ドメインA オーケストレーション) ─┐
│   ├── Gnome (実装)                               │
│   ├── Sylph (レビュー) ← ネスト委任              │ 並列
│   ├── Gnome (差分修正) ← 必要なら                 │
│   └── ... ループ → 完了報告                       │
├── Sylph-Orch-B (ドメインB) ──────────────────────│
│   └── 同上                                       │
├── Sylph-Orch-C (ドメインC) ──────────────────────┘
│   └── 同上
└── 全Orch完了 → Undine 受領・ユーザー報告
```

### 役割分担

| 階層 | エージェント | 役割 |
|------|------------|------|
| L0 | **Undine** | 波分割・Orch-Sylph 起動・最終報告 |
| L1 | **Orch-Sylph** | ドメイン内の実装サイクル管理（コンテキスト収集→Gnome指示→レビュー→判定） |
| L2 | **Gnome** | 実装（コード・テスト） |
| L2 | **Review-Sylph** | レビュー（設計 vs 実装の差分レポート + テスト結果確認） |

Orch-Sylph / Review-Sylph は別々の agent 定義ではなく、`.claude/agents/Sylph.md` の Sylph を**委任プロンプトで役割付けして呼ぶ**。Gnome は `.claude/agents/Gnome.md`。ネスト委任（Orch-Sylph が Gnome / Review-Sylph を産む）は、Sylph の frontmatter で `tools` を絞っていないため自動的に有効。

## 最優先ルール: Undine コンテキスト保護

Undine のコンテキストは wave 全体を保つための保護資産であり、作業量削減より優先される（→ Essence why 1）。

- Undine は implementation domain の source code、tests、e2e、domain docs、traceability、large diff inventory を直接作成・修正・精査しない。
- Undine は「担当 subagent が遅い / 応答しない / 途中で止まった」ことを理由に、自分で実装を埋めない。
- Undine は大きな調査や棚卸しが必要な場合、調査観点と受け入れ基準を設計し、実調査は Orch-Sylph または research subagent（Sylph）へ委譲する。
- Undine が直接読む basis は、wave plan、accepted decisions、domain completion reports、review verdicts、ユーザー判断に必要な要約に絞る。
- Undine が誤って直接作業した成果物は、正規の pass evidence に数えない。未信頼ドラフトとして扱い、Orch-Sylph に独立評価させる。

## 必須ネスト分離

実装 wave の実行単位は domain ごとの **Orch-Sylph** である。

- Undine は domain を直接実装しない。
- Orch-Sylph 自身も source implementation をしない。
- source implementation は必ず別コンテキストの **Gnome** に委譲する。
- review は必ず別コンテキストの **Review-Sylph** に委譲する。
- Review-Sylph は Gnome の説明だけに依存せず、basis docs、target files、diff、tests、verification evidence を根拠にする。
- この分離を維持できない場合、Orch-Sylph は実装せず `escalate` または `blocked` として報告する。

各 assignment には必ず次の趣旨を含める:

```text
Orch-Sylph自身は実装担当ではない。source implementation は必ず別コンテキストの Gnome に委譲し、
レビューは必ず別コンテキストの Review-Sylph に委譲すること。
これを分離できない場合は実装せず escalate / blocked として報告すること。
```

## サブエージェント・ハンドリング規則（Wave103 初回運用で確立、2026-07-02）

前提となる**通知配線の非対称**を理解すること: 子エージェントの完了通知が確実に届くのは**メインループ（L0 / Undine）だけ**である。サブエージェント（L1 以下）は、ターンを終えると「待機」ではなく**停止**し、背景起動した子の完了で起こされる保証がない（通知は停止した親を素通りしてメインループへ浮上する）。以下の規則はすべてこの事実から導かれる。

### 規則 1: L1 の子起動は「起動 → 明示的な待機報告でターン終了 → L0 中継で再開」が実効プロトコルである

**実測事実（Wave104 全ドメインで確認）**: この環境では L1 以下のエージェントの子起動は、フォアグラウンド指定の有無にかかわらず **async 化される**。子の完了通知は停止した親には届かず、L0（メインループ）に浮上する。したがって L1 の「待機」は次のプロトコルで実現する:

1. 子を起動する（`run_in_background` は付けない — 環境が async 化しても指定はフォアグラウンドのままにする）。
2. **起動した子の agentId と担当内容を明記した「待機報告」でターンを終える**（何を待っているか、次に何をするかを書く。これは規則 6 の「手ぶらのターン終了禁止」の例外ではなく、明示的な質問付き報告の一形態である）。
3. 子の完了は L0 に浮上し、L0 が SendMessage で親に中継・再開させる（コンテキストは保存されており、再開はやり直しではない）。
4. 親は中継を受けてフローの次段へ進む。

**子から親への SendMessage は届かない**（「No agent named ... is addressable」で失敗する実測あり）。子は最終報告を自分のセッションに残せば L0 経由で親に中継される。

### 規則 2: 並列は「1 メッセージ内の複数呼び出し」で実現する

独立な子（レビュー 3 レーン等）は、同一メッセージに複数の `Agent` 呼び出しを束ねて発行する。全員が並列に走る。**並列性のために意図的な背景起動は必要ない。**

### 規則 3: 意図的な背景起動 + 自前 Monitor は禁止。中継は L0 の責務である

L1 以下が「背景起動 + 静止検知 Monitor」等の自前待機装置で凌ぐ形は、動くが L0 の中継・再開を余計に要求することが実証されており、禁止する。待機は規則 1 のプロトコルに一本化する。L0 は孫の完了浮上を監視し、束ねて親に中継する役を負う（wave 実行中の L0 の主業務のひとつである）。

### 規則 4: 沈黙を根拠に再起動しない。生存判定はアーティファクトで行う

再起動が許されるのは「起動呼び出し自体がエラーを返した」場合のみ。通知が来ない・応答がないことは死の証拠ではない。疑わしいときは**子の書き込みスコープのファイル mtime を見る**（直近数分の書き込み継続 = 稼働中）。万一重複起動が生じた場合: 正を一体（最新のフォアグラウンド分）に定め、他を停止し、先行の書き込みは未信頼ドラフトとして最終状態に照合・吸収し、衝突の経緯をドメイン報告書に記録し、レビューは最終状態に対してのみ実施する。

### 規則 5: 孤児を残さない。子の生涯は親の責任で閉じる

調査用の子（Explore 等）を含め、起動した子は全員「完了を回収した」か「明示的に停止した」状態にしてから最終報告を返すこと。孫エージェントは L0 からは観測も停止もできず、放置児の掃除はユーザーの手動 UI 操作にしか頼れなくなる。

### 規則 6: ターンの終わり方は二種類だけ

①ドメイン判定（`pass` / `needs_fix` / `blocked` / `escalate`）を持った最終報告、または②呼び出し元からの追加指示が必要な明示的な質問付き報告。「〜を待ちます」だけの手ぶらのターン終了は禁止（規則 1 により、待つべきものがあるならまだターンは終わらない）。

### 規則 7: モデルは常に明示指定する

`Agent` 呼び出しの `model` は必ず明示する。無指定は親モデルを継承する（L0 から無指定で呼ぶと、セッションモデルの予算を子が消費する罠がある）。配分は wave 計画のモデル配分表に従う。

### 規則 8: 環境操作は L0 / ユーザーの統制点で行う

`pnpm install` 等の依存・環境変更は L1 以下では実施しない。これはサンドボックス制約（Codex 時代の遺物）ではなく、依存ポリシーの統制点をエージェント階層の下に渡さないための規律である。必要が生じたら escalate し、L0 がユーザーと調整する。

**回避工作も禁止**（Wave104 の実例から）: install が必要な状況を、代替配線（手動 symlink、独自 resolver、tsconfig paths だけで凌ぐ等）で黙って回避しない。回避は自分の環境では動いても、他エージェント・他の実行方法（root からの実行等）で環境差として露呈し、レビューで偽の blocking を生む。**「動く回避を発明できる」ことは「escalate しなくてよい」ことを意味しない。** Gnome への委任文にはこの趣旨を含めること。

### 非妨害の原則（従来規約の継承）

- 子が final status を返すまで、親は同一責務を自分で代替実装・代替レビューしない。
- 親が子の作業を打ち切ってよいのは、ユーザーが明示的に中止を指示した場合、または子が明確に `blocked` / `escalate` / `completed` を返し、親がその状態を記録した場合に限る。
- 子を誤って放棄・重複起動した場合、そのドメインは pass として扱わない。事実を記録し、規則 4 の照合手順で立て直す。

### L0（Undine）の心得

- 停止した L1 の子（孫）の完了通知はメインループへ浮上する。L0 はその内容を `SendMessage` で当該 L1 に中継し、再開させる（コンテキストは保存されているため、再開はやり直しではない）。
- L0 は孫を直接観測・停止できない。緊急停止の最終レバーはユーザーの UI 操作であり、それを要求する状況（重複起動等）を作らないことが規則 1-5 の目的である。

この規約は、実装速度よりもコンテキスト保護と正規レビュー証跡を優先するためのものである。

## サブエージェント委任時の文脈明示

Copilot 時代は `[subagent-call] 呼び出し元: X` という記号で「これはサブエージェント委任である／呼び出し元は誰か」を暗黙に伝えていた。Claude Code では `Agent` ツールが「子の最終メッセージはツール結果として呼び出し元に返り、ユーザーには表示されない」ことを構造的に保証するため、この記号は不要である。

代わりに、**委任プロンプトの冒頭で役割と呼び出し元を散文で明示する。** 記号に暗黙に込めていた意図を、地の文として明示に引き上げる（情報量が増え、子が普通に読める）。冒頭に次を含めること:

- あなたは誰か（Gnome / Orch-Sylph / Review-Sylph）
- 呼び出し元は誰か（Undine / Orch-Sylph）
- これはサブエージェント委任であり、最終報告は呼び出し元に返る（ユーザーには表示されない）
- ユーザーへ直接確認はできない。判断に迷う点・不足情報は最終報告に「質問」として明記して返す

## 波分割ガイドライン

### 手順

1. サブシステム間の依存グラフを描く
2. **基盤層**（依存なし）と**依存層**（基盤に依存）を特定する
3. 基盤層を Wave 1、依存層を Wave 2 に分割する
4. 各波内では全項目を並列で Orch-Sylph を起動する
5. Wave 1 の完了を確認してから Wave 2 を起動する

### 分割の判断基準

| 基準 | ガイドライン |
|------|-------------|
| **依存関係** | 依存元が確実に存在するまで依存先は起動しない |
| **波の数** | 通常2波で十分。3波以上は依存チェーンが深い場合のみ |
| **波内の独立性** | 同一波内の項目は相互に依存してはならない |
| **依存がグループ内で閉じる場合** | 同一 Orch-Sylph 内で順次実装（例: ワールドマップ→酒場） |

## Orch-Sylph のフロー

### ステップ

```
1. コンテキスト収集
   - 設計文書を読む
   - テスト設計を読む
   - AC・シナリオを読む
   - 既存コード（型定義・関連モジュール）を読む

2. Gnome を呼び出して実装
   - 設計文書・テスト設計・既存コードの場所をプロンプトに含める
   - テスト実装を含めることを明示する

3. Review-Sylph を呼び出してレビュー
   - 設計文書・テスト設計のパスを渡す
   - Gnome が作成/変更したファイルのパスを渡す
   - テスト実行結果を渡す

4. レビュー結果で判定
   - 合格 → 完了報告
   - 差分あり → コンテキストを整理して Gnome を再呼び出し（ステップ2へ）
   - ループ上限到達 → 残差分を報告して終了
```

### Gnome への指示テンプレート

```markdown
# 実装タスク: {サブシステム名} (#{設計ID})

あなたは Gnome（実装担当）。これは Orch-Sylph からのサブエージェント委任である。
最終報告は呼び出し元（Orch-Sylph）に返り、ユーザーには直接表示されない。
作業中にユーザーへ確認はできないため、判断に迷う点・不足情報は
最終報告に「質問」として明記して返すこと。

## 参照ドキュメント
- 設計文書: `discussion/design/{category}/{file}.md`
- テスト設計: `discussion/test/{category}/{file}.md`
- AC: `discussion/acceptance-criteria/{category}/{file}.md`
- シナリオ: `discussion/scenarios/{category}/{file}.md`

## 既存コード（必要に応じて参照）
- 型定義: `packages/engine/src/types/...`
- 関連モジュール: `packages/engine/src/...`

## 実装要件
1. 設計文書に従ってエンジンコードを実装する
2. テスト設計に従ってテストを実装する
3. テストを実行し、全件パスすることを確認する

## 重要な規約
- エンジンパターン: execute → EngineEvent[] → applyEvents
- Position型は { x, y, level } — z ではなく level
- 純関数・副作用なし
```

### Review-Sylph への指示テンプレート

```markdown
# 実装レビュー: {サブシステム名} (#{設計ID})

あなたは Review-Sylph（レビュー担当）。これは Orch-Sylph からのサブエージェント委任である。
最終報告は呼び出し元（Orch-Sylph）に返り、ユーザーには直接表示されない。
Gnome の説明だけに依存せず、対象ファイル・差分・テスト結果を自分で確認すること。
判断に迷う点・不足情報は最終報告に「質問」として明記して返すこと。

## レビュー対象
- 実装ファイル: {Gnome が作成/変更したファイル一覧}
- テストファイル: {テストファイル一覧}

## 判定基準ドキュメント
- 設計文書: `discussion/design/{category}/{file}.md`
- テスト設計: `discussion/test/{category}/{file}.md`

## テスト実行結果
{直前のテスト実行結果}

## レビュー観点
1. **設計適合**: 設計文書の各セクションが実装に正しく反映されているか
2. **テスト適合**: テスト設計の各テストケースが正しく実装されているか
3. **テスト結果**: 全テストがパスしているか

## 報告形式
- 適合: 件数と主要な確認ポイント
- 差分: 具体的な箇所と修正指針
- 裁量判断: 設計未定義だが合理的に実装された箇所
- 判定: 合格 / 要修正（差分一覧付き）

## レポートファイル出力
レビュー完了後、レポート内容を以下のパスにファイルとして書き出すこと:
`discussion/implementation/reviews/{category}/{file}.md`
- {category} と {file} は設計文書のパスに合わせる（例: 設計が `design/unit/zodiac.md` なら `reviews/unit/zodiac.md`）
```

## レビュー判定基準

### 合格条件

以下の **両方** を満たすこと:

1. **設計適合**: 設計文書の各セクションの意図が実装に反映されている
2. **テスト合格**: テスト設計のテストケースが正しく実装され、全件パスしている

### 判定の注意点

- 裁量判断（設計未定義を合理的に実装）は **許容** — 差分ではなく注記として報告
- テスト設計にない追加テストは **許容** — ただし報告対象
- テスト設計のテストケースを実装していないのは **要修正**

## ループ制御

- **上限: 5ループ**
- 通常は 3-4 ループで収束する
- 5ループ到達時は残差分を報告して終了（Undine が判断する）
- 各ループで差分が減少しない場合は、設計文書の曖昧性を疑う → Undine にエスカレーション

### 早期脱出条件

**ユーザー判断が必要な設計の漏れ**を検出した場合、ループ回数に関わらず即座にループを中断し、その旨を Undine に報告してターンを返すこと。

- 例: 設計文書に記載のない判断分岐、複数解釈が可能な仕様、他サブシステムとの責務境界が不明確
- ユーザー判断が必要な状況で実装を続けても混乱が深まるだけ
- 報告には「何が不明で」「どの設計文書のどの箇所が曖昧か」「実装を進めるために必要な判断は何か」を含める

## レビューレポート出力規約

Review-Sylph のレビューレポートは、口頭報告とは別にファイルとして永続化する。

### 出力先

```
discussion/implementation/reviews/{category}/{file}.md
```

- `{category}` と `{file}` は設計文書のパスに合わせる
  - 例: 設計 `discussion/design/unit/zodiac.md` → レポート `discussion/implementation/reviews/unit/zodiac.md`
- ディレクトリが存在しない場合は作成する

### レポートの内容

```markdown
# レビューレポート: {サブシステム名} (#{設計ID})

- 日時: {タイムスタンプ不要 — Git履歴で追跡}
- ループ: {最終レビュー時のループ番号} / {総ループ数}
- 判定: 合格 / 要修正

## 設計適合
{セクションごとの適合状況}

## テスト適合
{テストケースごとの実装状況}

## テスト結果
{パス/全体件数、失敗があれば詳細}

## 裁量判断
{設計未定義だが合理的に実装された箇所}

## 差分・残課題
{あれば — なければ「なし」}
```

### 書き出しタイミング

- **最終レビュー完了時**に書き出す（途中ループのレビューは上書きでよい）
- Orch-Sylph が Review-Sylph の結果を受け取った後、ファイル書き出しを行う

## 完了報告

Orch-Sylph → Undine への最終報告に含める内容:

```markdown
## 完了報告: {サブシステム名}

- ループ回数: N
- 作成/変更ファイル: {一覧}
- テスト結果: {パス/全体件数}
- レビュー結果: 合格 / 残差分あり
- レビューレポート: `discussion/implementation/reviews/{category}/{file}.md`
- 裁量判断: {あれば}
- 注意事項: {あれば}
```
