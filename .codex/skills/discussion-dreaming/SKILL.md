# discussion-dreaming

よい夢の基準は、自然に尋ねれば伝わる問いに対して、地図の古さや途切れのせいで古い答えや途中までの答えを返してしまうことを減らせたか。

## 今回の夢を組み立てる

ユーザーがウンディーネに「そろそろ夢を見ようか」と声をかけたら、今回見渡す範囲と構成を相談する。トピックの指定は要らない。相談の材料が足りなければシルフに浅い下見を委ねてよい。実行範囲に合意済みなら、その合意から続ける。

夢の開始時は git status で未追跡も含めて clean と確認する。dirty なら変更を所有者に伝え、夢のために既存の仕事を stash・コミットしない。実際の下見・精査・編集・読み直しは、いずれも GPT-6.1 Sol（gpt-6.1-sol）のシルフに委譲する。モデルを明示し、依頼と入口だけを渡す。大量の記録や差分をウンディーネのコンテキストに戻さない。

## シルフの判断

- まず discussion/_conventions.md と階層ごとの地図を入口にする。変更履歴、地図から漏れた記録群、ユーザーが感じた違和感、過去の夢を手がかりに今回の候補を選ぶ。前の夢は当時の観測。古さや件数だけで対象を決めない。
- 初回のように全体像がない回は広く浅く見渡す。選んだ領域は根拠まで辿り、それ以外は次に選べる見当を残す。通常回は関心や気づきに応じて広さを変える。
- 担当する話題と導線を試す具体的な問いを分ける。ひとまとめにすると違いが隠れ、分ければ次の人が行き先を選べるところで分担する。広すぎる場合は観測と未確認範囲を分担元に返し、同じ階層の次の巡か後日の夢に回す。共有mapは編集者を一人に決める。
- 自然な問いを今の地図で辿り、どこでどんな答えになるかを、決定・実装・確認記録と照合する。入口の更新、まとまって育った話題への専用map、変更なし、から選ぶ。実装と合意の食い違いは根拠と未確認の区別を保つ。原因究明や仕様・コードの修正は別の仕事。
- 変更した代表的な道を、答えを知らないシルフが入口と問いだけで辿れるか確かめる。ウンディーネには問い・辿れた根拠・見た範囲と残りを短く返す。

## 一回を閉じる

discussion/development_convention/dreams/ にその回の短い記録を置き、地図から引けるようにする。何に着目したか、入口と問い、観測・根拠、直した理由（またはそのままでよかった理由）、見た範囲を残す。後日、日付以外に話題や現象からも気づきを引けるようにする。

mapと夢の記録を明示的に選び、一回一コミットで閉じる。map変更ゼロでも記録を残す。途中で現れた他者の変更を混ぜない。終了時に状態を確認する。
