# C4設計: 操縦チャネルv0(契約外殻・参照ドライバ・粗いオーバーレイ)

> Status: 設計方向=Accepted(ユーザー合意 2026-07-11)。閉問題C4「外から動かせる」のwave化前設計討議のまとめ。
> UX定義: [../implementation/screens/c4-channel-diagnostics.md](../implementation/screens/c4-channel-diagnostics.md)。
> 親設計: [runtime-player-control-channel.md](runtime-player-control-channel.md)(方向・挿入点・三階建て・不変条件)。本文書はその契約詳細のC4分の具体化。
> 関連改定: C4二相化とC5実駆動判定([../implementation/closed-problem-decomposition.md](../implementation/closed-problem-decomposition.md) §3/§4)、特区憲章([../concept/mvp-boundary-amendment.md](../concept/mvp-boundary-amendment.md) §6)。

## 1. C4の性格(改定後)

- ゲートは機械のみ: fixture一発の疎通に加え、**参照ドライバ(疑似魂)による持続駆動の機械テスト**(数分駆動でフレーム停滞なし・切断/再接続成立・応答遅延計測)。
- 「インテント1個」は機能の広さではなく**縦の貫通**: 外部プロセス→WS→token認証→契約検証→解決→画面でモデルが動く、を最初から最後まで通す。
- 人間の観測(「外部駆動が美しいか」)はC5のゲートで、**この参照ドライバの実駆動プロファイル**を証人として実施する。実物の魂の接続はC5完全閉鎖以後。
- 経緯: fixture一発を「外から動かせる」の証明とみなす欺瞞をユーザーが指摘(2026-07-11)。参照ドライバの製作自体が「駆動する側から見て契約が書きやすいか」の検証を兼ねる。

## 2. 契約の二層化(依存の分析から)

**インテントのpayload語彙は後続の閉問題に依存する**(エンベロープ付き=C5の合成意味論、音素タイムライン=C6、変調=情動の状態語彙(未決))。先に全部を設計するのは閉問題の直列に矛盾する。よって契約を二層に割る:

- **外殻(封筒)**: 依存なし。C4で確定する(§3)。
- **payload(インテント種別ごと)**: その意味論を所有する閉問題が閉じたときに**追加**する。v0の `intent.set` だけはC4自身が意味論の所有者(粗いオーバーレイ)なので今決める(§5)。

これを成立させる設計要件は一つ: **外殻は「種別の追加が既存を壊さない」形(additive extension)であること**(ユーザー強合意 2026-07-11)。「三階建てを見越して切る」の正体は、三階建てを設計することではなく、**三階建てを後から載せられる基礎だけ打つ**こと。

## 3. 外殻の仕様(5点)

### 3.1 接続と認証

`ws://127.0.0.1:<スロット採番ポート>/channel?token=<スロットtoken>`。Browser Sourceと同じ作法(tokenはURL)。どの言語の魂でも一行で繋がる。チャネルは**手動開放**(起動時は閉。Accepted済み)。port/tokenはC1のスロット機構で採番・生成(Browser Sourceとは別ポート・別token)。

### 3.2 要求(クライアント→器)

```json
{ "v": 1, "id": "req-42", "kind": "intent.set", "payload": { } }
```

`v`=プロトコル版 / `id`=クライアント採番の相関ID / `kind`=**additive extensionの物理的な場所** / `payload`=kind固有。

### 3.3 応答(器→クライアント)

```json
{ "v": 1, "replyTo": "req-42", "result": "accepted" }
{ "v": 1, "replyTo": "req-42", "result": "rejected", "error": { "code": "slotValueOutOfRange", "message": "..." } }
```

拒否コードは列挙体系: `unknownKind` / `invalidPayload` / `unknownSlot` / `slotValueOutOfRange` / `slotNotWritable` / `channelClosed` 等(実装時に確定列挙)。ゲート要件「契約違反が拒否される」はこの列挙が担う。**拒否はクランプしない**(黙って丸めない)。

### 3.4 capabilities告知(器→クライアント、接続直後)

```json
{ "v": 1, "kind": "server.hello", "payload": { "protocol": 1, "supportedKinds": ["intent.set"] } }
```

魂は器に何ができるかを聞ける。C5/C6で種別が増えたとき、古い魂は知らない種別を使わないだけで共存する。

### 3.5 寛容の規則(双方向)

器は未知のkindを `unknownKind` で拒否するが**接続は切らない**。クライアントは未知のイベントkindを黙って無視する義務を負う。

## 4. TTL統一機構(有効性の意味論)

インテントは**受信時刻+TTLで失効する。TTLは省略可で、省略時は器の既定窓が適用される**。これにより:

- (b)明示TTLスタイル(「この頷きは800ms有効」)と (c)ストリーミングスタイル(魂が自分のリズムで送り続け、途絶=既定窓で失効)が**同一契約上の使い方の違い**になる。どちらを主とするかの裁定は魂を入れる頃まで繰延可能で、その日が来ても契約は変わらない(ユーザー合意 2026-07-11)。
- **切断→基底復帰がプロトコルの構造からタダで手に入る**(送りが止まれば落ちる)。「clearの送り忘れ」という事故クラスが消える。

## 5. v0 payload: `intent.set`

```json
{ "slotId": "face.angle.x", "value": 0.4, "ttlMs": 800 }
```

- `slotId` は**既存セマンティックスロット語彙**(C2/C3で確立した「器に入る駆動はすべて意味スロット層を通る」文法に乗る。新語彙の発明ゼロ)。
- `value` はスロット契約の正規化値。検証は既存防壁に相乗り(範囲外・不正ID・書込不可は**拒否**)。
- `ttlMs` 省略可(§4)。

## 6. 粗いオーバーレイ(C4の合成規則)

**インテントが有効な間、そのスロットIDについてはチャネル値が生成器値を単純に上書きする。失効・切断で生成器(基底)へ戻る。**

- 滑らかな立ち上がり・減衰・優先規則の精緻化はすべてC5(これはC5が精緻化する対象の粗い初期値であり、C5の先取りではない)。ユーザー注記: 見てみないと分からないが、最終的にC5でもこの規則のままになる可能性はある。
- スナップの不格好さはC4では判定対象外(C5の被告)。

## 7. 参照ドライバ(疑似魂)

- **特区 `apps/<魂>` の最初の住人**。LLM・知覚なしのシナリオ駆動(見る、傾げる、黙る、再開する、わざと切断する、再接続する)を数分間、現実的なプロファイルで流す常駐プロセス。
- 役割: ①C4の持続駆動機械テストの駆動源 ②契約エルゴノミクスの検証(書く行為そのもの) ③C5人間ゲートの証人 ④魂側開発への実行可能な手本。

## 8. fixture引き渡しの形(魂の形態非依存)

魂の形態はPython常駐 / Node常駐 / Agent SDKエージェント / ハイブリッドのいずれもあり得る(**今決めない**。契約の言語中立性が「決めないこと」を可能にする):

1. **契約は言語中立**: JSON over WS。TS固有の表現を契約に漏らさない。
2. **fixtureは純JSON**: スキーマ(封筒と各payload)+実際のやり取り例(接続→hello→インテント→受理/拒否のメッセージ列)。
3. **参照クライアント(=ゲートのテストスクリプト)はTS**で書くが、それはこのリポジトリの検証道具であり、契約の正はJSON側。
4. **接続の作法は単純に保つ**: token一枚で入り、メッセージ単位で完結。複雑なセッション儀式を要求しない。
