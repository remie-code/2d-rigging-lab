# 設計: Runtime Player = モデルホスト、役割つき起動

> Status: Accepted(ユーザー合意 2026-07-10、案(c)採用+起動UX確定)
> 関連: 境界改定は [../concept/mvp-boundary-amendment.md](../concept/mvp-boundary-amendment.md)、生理層は [physiological-layer-and-envelope.md](physiological-layer-and-envelope.md)。

## 1. 責務の再定義

> **Runtime Playerは「モデルホスト」である。Runtime Exportされたキャラクターに身体(評価・描画・配信)と生理(決定論的な生命感)を提供し、複数の駆動源 — 人間のトラッキング、または生理生成器+外部操縦チャネル — を受け付けて合成する器であり、知性・知覚・人格・音声はすべて器の外に住む。**

- 持つもの: 身体 / 生理 / 駆動源の受付と合成規則 / 役割別チューニング面 / sanitization・配信境界。
- 持たないもの: LLM、画面知覚、ペルソナの中身、TTS・音声処理(音はOBS側の世界、Playerにはパラメータだけが届く)。

背景: Runtime Playerは「人間が憑依するための器」(既存)に加え「自律キャラクターを住まわせるための器」の二面を持つ(ユーザー言語化 2026-07-10)。共有される芯=Runtime Export読込・評価・描画・フレームパイプライン・OBS配信・sanitization境界。役割で違うのは駆動源の生態系とチューニング面のみ。

## 2. アプリの形: 案(c) 同一アプリの役割つき起動(Accepted)

役割は二つ。**起動の瞬間にインスタンスの人格が決まり、実行中は変わらない**:

| 役割 | 駆動源 | チューニング面 |
|---|---|---|
| トラッキングホスト(ユーザー用) | iFacialMocap等のトラッキング入力 | 既存のInput/Mapping/Calibration/Dynamics Tune等そのまま |
| 自律ホスト(AI共演者用) | 生理生成器(基底)+操縦チャネル(オーバーレイ) | 生理プロファイル調整、チャネル診断(接続状態・最後のインテント・変調の現在値) |

不採用案の記録: (a)役割なし同居=配信操作UIがキャラ用ツマミで散らかり誤操作を招く / (b)別アプリ=芯(Electron殻・Browser Sourceサーバ・profile永続化)が未packages化の現状では大規模重複か大規模抽出を今日強制する(先回りの器づくり)。(c)は可逆な中間であり、将来(b)へ行く時は役割ラベルがそのまま分割線になる。

**エスカレーション**: 実機ゲートで機能の乖離が本当に大きくなったら「芯のpackages抽出+別アプリ化」へ(梯子方式)。

## 3. 成立の前提条件

1. **状態の分離**: profile類・window-stateのuserData空間を役割ごと(またはインスタンスごと)に分ける(同一userData共有では衝突する)。
2. **ポートの分離**: Browser Sourceサーバと操縦チャネルはインスタンスごとに別ポート。
3. **身元表示**: ウィンドウタイトル・トレイに役割バッジを明示(配信中のControl Window取り違え=放送事故対策)。

## 4. 防波堤: 役割は構成で表現する

**役割は起動時の構成(どのモジュール群を組み立てるか)を一度だけ決め、実行中のコードは自分の役割を問い合わせない。** トラッキングホストには生成器のインスタンスがそもそも存在しない、という作り方。`if (role === ...)` の散在は(c)を(a)より汚いものに堕とす — 実装時にはReview-Sylphのblocking観点へ翻訳する。

## 5. 起動UX(Accepted)

**扉は三つ**:

1. **役割つきショートカット(日常)**: 起動引数が役割を持つ。配信日は「アイコン二つをクリックするだけ」。
2. **素の起動口=ピッカー(恒久の原点)**: **役割引数なしの起動=常にピッカー**。大きなカード二枚(トラッキングホスト/自律ホスト)+「この役割のショートカットを作る」ボタン。初回限りではなく恒久の規則 — 素の起動口は永遠に「役割を選ぶ扉」であり続ける。
3. **トレイの「別役割のインスタンスを起動」(配信中の近道)**: 起動中のインスタンスから相方を起こす。既存トレイメニュー(click-through復旧の住処)に一行増えるだけ。

**禁止事項(明記)**: ピッカーに「次回からこの役割で自動起動」のような素の起動口を特定役割に縛る記憶を持たせない。素の起動口は中立、役割は近道(ショートカット)とトレイだけが持つ。

## 6. 起動直後に見えるもの

- **トラッキングホスト**: 今日と同一(Control+Stage、Runtime Export復元、Input接続は手動)+役割バッジ。
- **自律ホスト**: Control(自律ホスト版Overview: export状態・生成器状態・チャネル状態)+Stage。Runtime Export復元と同時に**モデルは呼吸している**。

**規則(Accepted)**: **生理層は自動起動 / 操縦チャネルは手動開放**。

- 生理=自動: 生成器はネットワークも外部リスクも持たない身体内在の心拍。「読み込まれた身体は生きて生まれる」。魂劣化時に基底が残る設計思想と一貫。
- チャネル=手動: 外部への口(loopbackソケット)を開けるのは明示操作。既存の流儀(startup restoreはInput Sourceをauto-connectしない / Browser Sourceは明示的に立てる)の正確な延長。OverviewにChannel: Closed/Open(token表示)が座る。

## 7. 配信当日の運用像

```
アイコン2クリック
  → A(トラッキングホスト): ユーザーのモデル復元 → Input接続 → 顔が乗る
  → B(自律ホスト): キャラ復元、既に呼吸 → Channelを開く → 魂(外部プロセス)が繋がる
  → OBS: Browser Source ×2(A/Bそれぞれ)
```

障害の隔壁がインスタンス境界と一致する: 魂が死んでもBは生理層で生き続け、Aは無関係。片方の再起動は他方に影響しない。
