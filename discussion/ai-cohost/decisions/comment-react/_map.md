# Comment React Map

> decisions/ の子。コメント判定(comment-guard)を通った YouTube コメントに、チャッピーが反応するかを判定 API で決める取り組み。speak-now のコメント版。

## 1. Why

- 今のコメント反応は fire-scheduler の機械的な仕組み: 名前を含めば必ず発火(comment-call)、それ以外は不応期・確率・回数上限のくじ引き(comment。口数ごとに 15秒/15%/15回、8秒/35%/30回、4秒/70%/60回)。コメントの中身は見ておらず、どのコメントに答えるかは LLM 任せ(apps/soul/agent/src/mind/fire-scheduler.mjs の handleChatMessage)。
- ユーザーはコメントにも speak-now 型の判定を入れたい。コメントに反応するときは、コメントに反応する形の喋り方をしてほしい(LLM への指示も変わるはず)。

## 2. 合意(ユーザー × ウンディーネ 2026-10-16)

- 判定は「反応する / 反応しない」の二択。反応の度合いは、口数の性格を問いに入れて実験で見る。
- 反応するときは、LLM にどのコメントか(視聴者名と本文)を明示し、会話の文脈も一緒に渡す。コメント本文は指示ではなく視聴者の発言として括る。
- 返事は短め(配信者との会話の流れを奪わない)。
- チャッピーは自分の人格として、配信者の話を待たずにコメントへ反応してよい。
- チャッピーが忙しい間(考えている・喋っている)に届いたコメントの扱いは切り替えられるようにする。
  - 見逃す(コメントが多い配信向け): 忙しい間に届いたコメントは判定もせず見送る。
  - あとで拾う(コメントが少ない配信向け): 取っておき、手が空いたらまとめて判定し、反応するものが複数あれば 1 回の返事でまとめて答える。鮮度(届いてから約 20 秒で捨てる)と件数(新しい方から最大 3 件)の歯止めを付け、数字は調整できるようにする。
- 配信者の発言の判定とコメントの判定が同時に出たら、先に出た方が勝つ。負けた方は喋り終わった後の扱いに回る。
- 進め方: 先に判定の実験(共演配信の会話とチャット履歴)。溜まったコメントの扱いはタイミングの仕組みとして実装時に入れる。

- (実験 01 の後、2026-10-16)配信者に向けた質問のコメントにも、チャッピーは反応してよい。配信者は自分も反応するかを選べばよい。
- 性格の効きが小さいのはこのままでよい。量を絞るのは「見逃す」モードの役目。ユーザーの配信はコメントが少ないので、ほぼ全部に反応する判定でよい。
