# speak-now を操縦席に組み込む — 合意

> Status: 合意 Accepted、context-check 済み(2026-10-16)。Gnome が実装済み・未コミット(`node --test` 1182/1182、check:soul-zone 通過)。ユーザー確認おおむね合格(§9)。
> 目的: 判定 → チャッピーが喋る → 次の判定、の流れを、ユーザーが操縦席から実際に喋って確かめられるようにする(アーカイブ実験では確かめられない)。
> 前提の実験: [_map.md](_map.md)、[experiments/](experiments/)。棚卸しの根拠: fire-scheduler / fire-orchestrator / cockpit-server の読解(2026-10-16、Sylph)。

## 1. 判定

- 呼ぶとき: 配信者(you)の転写が転写バッファに 1 件積まれるたび。
- エンジン: 当面 OpenAI Decisions API(`POST /v1/decisions`、`gpt-6-luna`、choice 1 問)。`judge(input) → { choice, probs, latencyMs }` の形で差し替えられるようにする。
- 問い C: 「{性格の 1 文} ゲーム配信で配信者の隣にいるサポート役の AI Tuber「{名前}」として、配信者の発言をここまで聞いた今、どう反応するのが自然か？ 配信者の話がまだ途中なら待ち、話し終えていればどう反応するかを選ぶ。」
  - {名前} と会話のラベルは、今の頭の identity に合わせる(チャッピー / コーディ)。
  - {性格の 1 文} は口数モード(控えめ / ふつう / おしゃべり)に対応([../../../../apps/soul/agent/scripts/probe-decisions-speak-now.mjs](../../../../apps/soul/agent/scripts/probe-decisions-speak-now.mjs) の `PERSONAS`)。
- 選択肢 v2: 待つ / 相槌を打つ / 応答する / 自発的に話す(同スクリプトの `CHOICES_V2`)。
- 入力: 直近 3 分の会話(「配信者: …」「{名前}: …」)。チャッピーが喋る前の内容も含む。行数の上限なし。視聴者コメントは入れない。
- 結果は最大確率の選択をそのまま使う(しきい値なし)。

## 2. 動き

- 応答・自発 → 通常の自発発火と同じ発火(LLM に応答と自発の区別は伝えない)。
- 相槌 → 何もしない(フィードに出すだけ)。
- 待つ → 何もしない。
- 口数ごとの不応期・確率は speak-now の判定には掛けない。口数は問いの性格の 1 文だけで効かせる。

## 3. タイミング

- チャッピーが考えて喋り終わるまで(忙しい間)は判定を呼ばない。
- 判定中に次の発言が確定したら、前の判定を待たずに並行して呼ぶ。結果が返ったときにチャッピーが空いていて、選択が応答・自発なら発火する。発火後に返った結果は忙しいので捨てられる。
- 判定を待つ間に配信者が喋り始めても判定は捨てない(人間と同じ。喋り始めが配信者と重なるのは自然な確率で起きてよい)。
- 喋り終わって手が空いた時点で、忙しい間に配信者の発言が 1 件以上あったときだけ、1 回判定する。
- 自発 pill が OFF のときと KILL 中は判定を呼ばない。

## 4. 既存の発火との関係

- speak-now を使っている間は、区切り応答(turn-end)・呼びかけ(call)・合いの手(interjection)を止める。呼びかけを止めるのは、判定が名前の呼びかけに応答するかを確かめるため。
- 沈黙が続いたときの発火と、視聴者コメントへの反応は残す。
- 置き場所: speak-now は fire-scheduler の外の別部品にする。fire-scheduler には「speak-now の間は turn-end / call / interjection を止める」スイッチだけを足す。
- fire-scheduler の原則「いつ喋るかは機械信号のみ・判断のための ask は打たない」(fire-scheduler.mjs 冒頭)は、リアルタイムの判定 API が無かった時代の判断で前提が崩れている(ユーザー)。原則の文そのものを「いつ喋るかは、リアルタイムの判定 API を使うモードではそれに任せ、そうでない(従来の)モードでは機械信号で決める」の趣旨に書き換える。

## 5. 見せ方・運用

- 運転バーの自発 pill と口数の隣に「話し始め: 従来 / speak-now」の切り替えを置く。選択は保存する。初回の既定は speak-now。
- 観測フィードに、応答・自発・相槌の判定を小さな行で出す(例: 判定: 自発 0.45)。待つは出さない。
- 判定ごとに、遅延・選択・確率をターミナルに 1 行(会話の本文は書かない)。
- キー: `apps/soul/agent/.env.decisions.local` の `OPENAI_DECISIONS_API_KEY` を、ElevenLabs と同じやり方で読む(process.env に入れない)。タイムアウト 3 秒。キーが無い・失敗したら発火せず、フィードにエラーを出す。従来方式へ自動では戻さない。

## 6. ユーザーの確認項目

- STT を ElevenLabs にし、口数を変えると喋る頻度が変わるか。
- 「チャッピー、〜どう思う？」と名前を呼んで質問すると応答するか(呼びかけの仕組みを止めた状態で)。
- チャッピーが喋っている間に話したことを、喋り終わった後に拾うか。
- フィードに判定の行が、ターミナルにログが出るか。
- (喋っている途中の息継ぎでの割り込みは気にしない、とユーザー)

## 7. 後で別途考える

- 判定まわりの見え方の体験。
- 視聴者コメントの扱い。

## 8. 実装報告(Gnome、2026-10-16)

- 追加: `src/mind/speak-now.mjs`(判定入力の組み立て・問い C・タイミングの制御 `createSpeakNowController`)、`src/mind/speak-now-decisions.mjs`(差し替え可能な `judge()` の Decisions API 実装、タイムアウト 3 秒、`loadDecisionsApiKey`)、各テスト。
- 変更: fire-scheduler に `speakNowMode`(ON の間 turn-end / call / interjection を止める。既定 OFF)と原則文の書き換え。cockpit-server に `POST /api/speak-start`、snapshot の `speakStart`、you 転写の受け渡し、idle 通知。運転バーに「話し始め」select(初回既定 speak-now は cockpit.mjs 側で設定)。フィードの判定行は selfFire SSE に相乗り(SSE 本数は不変)。ターミナルに `[cockpit] speak-now: ms=… choice=… p=… action=… trigger=… probs=…`。
- Gnome が決めた点: 「忙しい」には orchestrator が idle でない間に加え、fire() の Promise が片付くまで(受理から thinking までの窓)も含む。結果到着時に忙しかった判定も、フィードには判定行を出す(捨てたことはターミナルの action=drop-busy でだけ分かる)。判定のたびにキーを読む。直近 3 分に会話が無ければ判定しない。
- 実 API 確認(架空の短い会話 2 回): 「…チャッピー、次どうしたらいいと思う？」→ 応答 .93(2072ms)、「えーと、その、なんだっけ」→ 待つ 1.00(314ms)。2 秒台はタイムアウト 3 秒に近く、判定エラーになりうる。

## 9. ユーザー確認(2026-10-16)

- 「すごく自然に会話ができた気がする」。判定行はフィードに出る。応答・自発でチャッピーが喋る。
- 名前を呼んで質問すると「ほぼ確実に応答する。しかもこれまでよりもノーストレス」。
- Gnome の決定(忙しいの範囲を広めに取る、ターミナルの trigger 区別と全確率)はユーザー了承。捨てた判定の見え方は見せ方の議論で再検討。
- 未確認: ターミナルの `[cockpit] speak-now:` 行(見ていなかった)、喋っている間の発言を喋り終わった後に拾うか(後で試す)。タイムアウト 3 秒は、判定エラーが頻発したらユーザーが知らせる。
