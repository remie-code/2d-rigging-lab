# Discord VC への参加: 目標像と前提(ユーザー 2026-10-30)

> 状態: 体験の整理は一区切り(§14、2026-10-30)。次は開発の的を決める。設計(コードの切り方)はまだ。

## 1. 目標像

- チャッピーが Discord のボイスチャット(VC)に入って、そこにいる人たちの声を聞き、自分の声でしゃべり返す(ユーザー「完全にイメージ通り」)。

## 2. 場面

- 配信とはまったく関係ない、仲間内の VC。
- まずは、今のチャッピーをそのまま Discord に参加させられればよい。
- 将来の願い: TRPG の NPC のような役もできると嬉しい(当面は扱わない)。
- 当面の問い: チャッピーを Discord の会話に参加させることができるか。

## 3. 決めたこと・前提

- **誰がしゃべったかを分かる必要がある。** 文字起こしは参加しているメンバーそれぞれに行い、チャッピーには話者付きで渡す。今の YouTube コメントの拾い方に近いイメージ。
- **チャッピー専用の Bot として入るのが望ましい(可能なら)。** 価値観: チャッピーは「私たちと同列な参加者」である。
  - あなたの Discord の音を仮想ケーブルで横流しする手は、全員の声が 1 本に混ざり、チャッピーがあなたの声として聞こえるので、次善。
  - 自分のアカウントを自動で動かす手(セルフ Bot)は、Discord の規約違反なので外す【推測。調べて確かめる】。
- **いつしゃべるか**: ユーザーにも分からない。ひとまず判定 API(今の speak-now / comment-react の流れ)に頼り、よい判定の設定を考えられればよい。
- **同意**: 仲間内でやるので、声が文字にされて頭(Codex など)に渡ることは、事前に許可を取る。

## 5. 絵のすり合わせ(ユーザー 2026-10-30、調査の後)

> Undine は最初「配信のチャッピーを Discord に広げる」と読み、配信向けの言い回しを「壁」と呼んだ。これはずれていた。以下がユーザーの絵。まだイメージで、できるかは確かめていない。

- **これは、今の配信向けの作りを切り直す話を含む。** 今のチャッピーには配信に特化した機能がいくつもあり、Discord ですべて使うとは考えにくい。一方で、考える仕組みや記憶の仕組みなど、使い回せそうな部分は多い。しゃべらせたい場は今後も増えうる。
- **芯は、もともと何人もいる会話の場として作る。** 配信は、話し手がたまたま 1 人のケース(ユーザーの思いつき。設計として筋が通るかは要確認)。
  - 配信のコメントは声の参加者と種類が違う(文字・大人数・名前を残さない)。これが「モードが複数ある」と感じる最大の理由。
- **ユーザーが目にするモードの粒度は「どんな体験でチャッピーと出会うか」。** 例: 配信モード、Discord 参加モード。内部の線引き(耳の入口・声の出口・言い回し・モード固有の機能)をモードに持たせる粒度で機能するかは、まだ掴めていない。
- **しゃべる者は「ロール」を持つ。** 配信では「私のアシスタント」。TRPG の NPC として決まった場面でしゃべるなら、チャッピーというガワをかぶる意義は薄い。
- **記憶はモードで分ける。ロールごとにあるのかもしれない。** ロールの中でも引き継ぐかは分かれる(TRPG の NPC が、別のプレイヤー向けのセッションで過去を覚えているのはおかしい。ただし過去があると上手に演じられる可能性はある)。
- **画面は体験に合わせる。** Discord で使う人が YouTube の URL を指定する画面を見るのは気持ちよくない。設定の半分くらいは共通で使いそうだが、「同じ画面を使う」ことにこだわって不快な体験を与えるのは望ましくない。だからアーキテクチャを定めることが非常に重要。
- **体(Live2D)なしでもしゃべれるべき。** 今の「器がないと声も出ない」はバグっぽい。ただ、規模は大きくないと見られ、アーキテクチャの見直しにも関わるので保留。ユーザーの用途では、ほぼ確実に Live2D を使う。

## 6. 体験・ロール・記憶・しゃべり方(ユーザー 2026-10-30、§5 の続き)

- **層の言い方(Undine の整理・ユーザーの回答の前提)**: 体験(モード。どんな場でチャッピーに出会うか)/ ロール(その場でしゃべる者)/ 芯(考える・思い出す・声にして出す仕組み)。体験ごとに入口(耳)と出口(声・体)がぶら下がる。
- **ロールと体験は自由に掛け合わせない。**
  - Discord モードでは、ロールを複数登録でき、選んで会話に参加させる。
  - 複数のロールが同時に VC に入る可能性もある(すぐにはやらない。それぞれの調整が要る、という理解で十分)。
- **記憶はロールごと。** 卓ごとには分けない。「前の卓ではこういう言い回しは好ましくなかった」を次のセッションで使う可能性がある。
- **起動時にロールを選ぶ。** ロールの登録も要る(例: TRPG のキャラ設定を登録し、そのキャラクターとしてしゃべる)。
- **ロールに付くもの**: 性格の指示・声・いつしゃべるかの方針は必須。体(Live2D)はオプション。
  - 体のつなぎ方は今と同じ: runtime-player 側が channel を開き、魂がそこにつなぐ。
  - 体を設定しているのに channel が開いていなければ、失敗してよい。
  - 救いたいのは「体を設定していないのにしゃべれない」こと。
- **しゃべるかどうかには 2 つの層がある。**
  1. 場の制約: その場の進行が、しゃべってよいと許しているか(例: TRPG の進行上、NPC が今しゃべってよいか)。
  2. ロールの方針: 場が許していても、文脈上しゃべるべきか。これが「いつしゃべるかの方針」で、やはり必要。

## 7. 最初の一歩の意味と、2 段の判定(ユーザー 2026-10-30、§6 の続き)

- **「今のチャッピーをそのまま Discord に」**: Discord モードに「チャッピー」というロールを 1 つ登録する。性格と声は配信のチャッピーと同じものを使うが、ロールとしては別なので、記憶も別(おおむねその通り、ユーザー)。
  - 今のチャッピーは「配信のアシスタント」というロールを持つが、指示文はあるものの、キャラクターを演じてはおらず、ほぼ素の GPT-6.1 Sol でしゃべっている。
  - 狙いは、特にキャラクターを演じていないチャッピーを連れて行き、**技術的にできるかを見る**こと。
- **2 段の判定(場が許す → ロールが判断する)は芯の側に置く候補。** 配信モードの 1 段目は、配信者が手で止める仕組み(安全弁・黙らせる操作)にあたる(Undine の見立て、ユーザー同意)。

## 8. 場・操作する人・頭とロール・呼び名(ユーザー 2026-10-30、仕分けの後)

- **「場」(1 回の集まり。配信 1 本、VC のセッション 1 回)は、語彙として持つ。ただしユーザーが意識するものではない。** 人は場を開こうと思って配信ツールを開くのではなく、配信をしようと思って配信用のツールを開く。ユーザーに見えるのは体験。
- **「操作する人」という概念は必ずある。**
  - 操作する人は話し手でもあるが、ほかの話し手と同列かは別。
  - 違いは物理的な権限: Discord では、仲間はチャッピーと声でしか話さない。操作する人は手元で cockpit に相当するものが見え、そこから操作できる。
  - この違いをチャッピーが認知すべきかは、別の議論(未決)。
- **選びたいのは頭ではなくロール。** 今の気持ちは「GPT 系列ならチャッピー、Claude 系列ならコーディーというロールで話してほしい」に近い。5.6 Sol と 6.1 Sol の指示文はほぼ同じはずで、ほかが違うのは設定していないだけ。
- **呼び名**: 新しい単位はカタカナで「ロール」と書く。今ある「役」(記憶の書き出し役・思い出し役)と runtime-player の「役割つき起動」は、そのまま(Undine の勧め、ユーザー了承)。

## 9. 中心はチャッピーの存在、そして場(ユーザー 2026-10-30、§8 の訂正)

- **§8 の「場はユーザーが意識しない」を訂正。** 人は「配信をしよう」ではなく「チャッピーと何かしよう」と思ってこれを開き、体験(例: 配信)を選ぶ。中心に据えるべきはチャッピーの存在。
- **ユーザーは「中心は場かもしれない」と見ており、場をもう少し掘り下げて話したい。** → 議論中。
- **頭とロール(§8 を補う)**: ロールを選び、それを動かすモデルを決める。GPT 系列ならチャッピー、Claude 系列ならコーディー、という組み合わせは「運用として」そうしているだけ。
- 操作する人・呼び名は §8 のとおりで了承。

## 10. 場の形(ユーザー 2026-10-30、§9 の掘り下げ)

- **中心は「AI と」何かをすること。** チャッピーとしてふるまってほしいかどうかは、体験とセットで決まる。
- **開く順番は「体験を選ぶ → ロールを入れる → 場が開く」がいちばん近い。** Discord に何人かのロールを入れられることとも合う。
- **場の長さは体験 1 回分。** 配信のあとにそのまま雑談を続けることはよくあるが、それも「配信」という体験の内と考えてよく、厳密に考えなくてよい。
- **場の記録を、ロールの記憶とは別に残すことはしない。** 記憶はあくまでチャッピー(ロール)のもので、外から干渉する意図はない。今のように、チャッピーが感じたままを残せばよい。そこに場としての情報が含まれるのは問題ないが、記憶の方向性を外から歪めようとは思わない。

## 15. 開発の的と進め方(ユーザー 2026-10-30)

- **進め方は「受信の小さな試し → 配信の組み直し → Discord を足す」**(Undine の案 3。ユーザーも一番よいと思っていた)。
  - 0. 受信の試し: 魂と切り離した使い捨ての仕掛けで、Bot が入れるか・1 人ずつの声が届くか・不具合の場面で何が起きるかを見る。声も文字起こしも残さない。手順の準備は [probe-setup.md](probe-setup.md)。
  - 1. 組み直しの設計(ロールの持ち方・場・芯と入口出口の切り分け)→ 2. 配信の組み直し(wave ごとに配信が回る状態を保つ)→ 3. Discord の入口と出口。
- **設計から先は、あとで /context-check などを通してから始める**(ユーザー)。
- 的の外: TRPG の NPC、2 つ以上のロールの同時参加、アプリとしての起動口、受信の不具合への本格的な対策(試しの結果しだい)。
- Bot の作成と鍵のファイルを置くのはユーザー。鍵の中身はエージェントが読まない。

## 16. 受信の試しの決めごと(ユーザー 2026-10-30、context-check の後)

- 目的: この部品(@discordjs/voice + DAVE)で Discord 参加モードを作り始めてよいかを決める。
- **合格**: 黙ったあとの発言が毎回届く。出入りの後も届く。Bot の音が聞こえ、話者の名前が取れる。
- **入った直後の取りこぼし**は合否に入れない。起きたか・2 回目から戻るかを記録する。
- **不合格**: 黙ったあとでも届かない、または届かなくなって戻らない → 作り始める前に部品の選び直しを考える。
- 2 人目はいない。話者が分かれるかは今回は見ない(自分の名前が取れればよい)。
- 試しのコードは決まった場所に置き、コミットして残す(Discord 参加モードの下敷きにする)。置き場はリポジトリの決まりの調べ待ち。
- 作り方: Gnome 1 人に任せ、Undine が見直す。wave の段取りは使わない。本番の確かめは、ユーザーが VC でしゃべる人の手の確認。

## 18. 組み直しの設計の前提(ユーザー 2026-10-31、context-check の後)

- **ロールの定義は git に入らない手元のフォルダ `apps/soul/agent/roles/<ロール>/` に置く。** リポジトリにコミットする案は採らない(アプリが保存しているデータが GitHub に載るのはおかしい、ユーザー)。
- **記憶の git はロールごとに 1 つ。** 今の `memories/` を `.git` ごと `memories/<チャッピー>/` へ移す(自然、ユーザー)。
- **こーでぃーのロールも作る**(Undine の推奨、ユーザーはどちらでもよい)。新しいロールのときだけ、記憶の決まりのひな形の名前を差し替えて置く。チャッピーの `_conventions.md` は一字も変わらない。
- **ロールは場の途中で替えない。** 替えるなら場を作り直す(ユーザー)。
- **「何をする?」の最初の画面は今は作らない。**
- **しゃべるかどうかの判定は「体験」に属する**(ユーザー)。配信で「しゃべるか」と、Discord に招かれて「しゃべるか」はかなり違う。だから判定は体験ごとにあるべきで、配信の判定が「配信」に触れているのは問題ない。→ Undine の「判定の文言から配信の直書きを外す」案は取り下げ。芯が持つのは判定を呼ぶ仕組みまでで、問いの中身は体験が持つ、と読む【Undine の読み。設計で確かめてもらう】。

## 19. 組み直しの設計への返事(ユーザー 2026-10-31、stream-restructure.md を読んで)

- **YouTube につながらなくても場は開く。** 場を開いたあとで、コメントを拾う URL を入れることがほとんど(ユーザー)。→ YouTube の URL は場が開いている間に入れて Connect するのが普通の流れ。
- **体の器につながらなければ場は開かない。** そのとき「runtime-player が起動していない(か channel が開いていない)」と分かる表示が出るとなおよい(ユーザー)。
- **マイクと文字起こしは、場が閉じている間だけ変えられる。** 実際に変えたことはなく、変えないほうが安全(ユーザー)。
- 「移し替えの本番を誰が流すか」は言い方が分かりにくかった(ユーザー)。言い換えて聞き直す。

## 20. 引っ越しの仕方と、中身を見ることの決まり(ユーザー 2026-10-31)

- **今の設定と記憶をロールの形へ移す(引っ越し)は、新しい版を最初に起動したときに自動で行う**(案 B)。安心は 2 つで埋める: 引っ越しの前に元の設定と記憶を丸ごと写しておく。何が起きたか(どの指示を使ったか・件数)を引っ越しのあとに 1 回だけ出す。
  - 「この程度の作業を君がしくじるとは到底考えられない」「君を信頼している」(ユーザー)。
- **中身を見ることの決まりの見直し**(ユーザー): 「設定や記憶の中身を読まない」はエージェントが自分で課した決まりで、ユーザーは重要と見ていない。**重要なのはアクセスキーなど漏れると困るもの**。配信の内容などをエージェントが見るのは問題ない。
  - したがって、鍵(`.env*.local` など)を読まない・出さない・環境変数に入れない、は今まで通り守る。設定ファイル・記憶・配信の中身は、作業に要るなら見てよい。
  - 視聴者の名前を記憶に残さない決定(../memory/recall-flow.md §9)は、取り違えの理由による製品の決定で、この見直しとは別。そのまま。
