## 0. これは何を測ったか（限界の明示）

**一文入力 → Agent SDK(Opus) 応答 → ローカル TTS(audio_query + synthesis) → timeline 構築**まで。
**実器へのチャネル送出も音声再生もしていない**（チャネルなし計測）。したがって「入力 → **音声が
鳴り始めるまで**」の E2E 完全値はここには無い。それは人間ゲート（`preflight-e2e.mjs` / CLI）で
実器を起動して 1 回通すまで確定しない（C 系列の教訓「配線の存在 ≠ 疎通」）。

**SDK 実行は 4 ask のみ**（サブスク枠を使うため厳格に最小化: tools 動作確認 1 + 計測サンプル 3）。
4 ask すべてを **1 つの常駐セッション**で行った（residency の実証。初回のみ spawn コスト）。

## 4. 導出値

- **常駐初期化（spawn + init）≈ 1.9s**（セッション生成起点）/ 1.25s（ask 起点）。**恐れていた「12 秒
  スポーン」ではなかった**（この環境・この回）。ただし residency の価値は不変: `query()` を毎回作れば
  この初期化を都度払う（Issue #34）。常駐ストリーミング入力で初回のみに畳めている。
- **warm な ask（LLM 往復）≈ 3.2〜3.3s**（#2/#3）。TTFT warm ≈ 1.2〜1.9s。**#4 は 9.2s の外れ値**
  （モデル/経路の実行時変動。サンプル 3 では分散は語れない）。
- **TTS の支配項は synthesis ≈ 0.97〜1.24s**。audio_query は 18〜56ms と軽い。timeline 構築は
  < 0.4ms（実質ゼロ）。均等割り写像（Domain A）は計測上のコストにならない。
- **入力 → WAV 準備完了の目安 ≈ ask_ms(warm ~3.2s) + audio_query + synthesis(~1.1s) ≈ 4.3s**
  （#4 のような外れ値時はこの限りでない）。音声が鳴り始める実 E2E は accepted 受領時刻依存で、人間
  ゲートで測る。
- **input_tokens が 252 → 284 → 318 → 364 と単調増加**。residency（1 セッション）で会話履歴が
  context に累積するため。共演者としては文脈保持は望ましいが、長時間会話では枠消費が増える。

## 5. 所見

1. **`tools: []` で全ツール無効になる**ことを実証（`init.tools=[]`・応答にツール使用なし）。
   `disallowedTools` の併用は不要だった（wave 計画の分岐条件は非該当）。
2. **apiKeySource=`none`（サブスク OAuth）**。API キー混入ガード（env-guard）の前提が実機で成立。
   ガード対象未設定 → サブスク枠で走る、が裏取りされた。
3. **residency が `maxTurns: 1` で保たれた**。4 ask を同一プロセスで往復（generator は殺さず手動
   `next()` で汲む設計が効いた）。`maxTurns: 1` は「1 入力あたりの自律多段ループを抑える」意味で、
   ストリーミング入力セッションを終了させるものではない、と実測で確認。
4. ローカル TTS（synthesis ~1s）と LLM 往復（~3s）が主コスト。写像・timeline は無視できる。

## 6. 次の含意

- **E2E 完全計測（入力 → 音声が鳴り始めるまで）は人間ゲート**で取る（`preflight-e2e.mjs` / CLI の
  stderr 計測 JSON）。本記録はその手前（WAV 準備完了）までの内訳。
- **ask #4 の外れ値（9.2s）は要監視**。会話レイテンシは魂の常設監視項目（[../_map.md](../_map.md)
  §6 の未解決質問「会話レイテンシ」への初データ）。**専用の計測回は設けない**（Undine 裁定
  2026-07-12）——S3/S4 が自然に会話サンプルを量産するため、以後の experiments/ 記録では
  **「外れ値の頻度」（例: ask_ms が warm 中央値の 2 倍を超えた回数 / 総 ask 数）を常設項目**として
  この表形式に足す。
- **residency の token 累積**は長時間会話でコスト増。会話管理（転写バッファ・context 制御）は S6 の
  領分で、ここで観測した「1 セッションで input_tokens が伸びる」事実がその設計の入力になる。
- この記録が S 系列の計器の初回。以後の問題で同じ表形式（枠消費 + レイテンシ）を積み増す。
