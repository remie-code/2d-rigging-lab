# S2 耳の計測記録: ASR レイテンシチューニングと CPU 負荷

> Status: 記録（2026-07-12, Gnome / S2 Domain C）。
> 計測手段: `apps/soul/agent/scripts/bench-asr.mjs`（チューニング格子）/ `scripts/preflight-ears.mjs`（採用設定の縦貫通）/ PowerShell `Get-Counter` + `process.cpuUsage()`（CPU）。
> **音声素材の規律: 全計測は AivisSpeech の TTS 合成音声（メモリ上のみ）または合成正弦波。実マイクは一切使っていない。実マイク経由の数字は人間ゲート後にユーザーが追記する。**
> 環境: 論理 16 CPU 機・whisper.cpp v1.9.1 BLAS 版 + kotoba-whisper-v2.0 q5_0（CPU）・flash-attn 既定 ON。

## 1. 出発点（Domain B 実測の再確認)

/inference レイテンシは 30s 固定窓エンコーダ支配で**音声長非依存**。本 wave の再計測でも 4.3s 音声で warm 8.3〜8.4s@4T / 6.6〜6.7s@8T（Domain B の 9.5s@4T / 6.6s@8T と同帯域。4T は本計測の方がやや速いが同じ桁）。人間ゲート「数秒以内の追従」に対し未チューニングでは不合格域。

## 2. チューニング 3 系統の結果（Undine 裁定の有界探索）

固定 TTS 音声「こんにちは、耳のテストです。今日はいい天気ですね」（≈4.3s）・warm 中央値。

### 2.1 (a) audio_ctx（本命・採用）

whisper のエンコーダ出力は 30s = 1500 トークン（50 tok/s）。`/inference` は multipart フィールド `audio_ctx` を**リクエスト単位で受ける**ことを実機照合（サーバ再起動不要 = 発話長比例の動的設定が可能）。起動引数 `-ac N`（静的）も存在するが、静的値は maxSpeech(20s) を覆う必要があり短発話の利得を捨てるため不採用。

| audio_ctx | 音声 | warm | 転写品質 |
| --- | --- | --- | --- |
| なし（全窓 1500） | 4.3s | 6684〜6709ms @8T | 基準（正確） |
| 280（= 長さ×50+64） | 4.3s | 1504〜1535ms @8T | **全窓と一致**（句読点まで） |
| 220（margin ≈0） | 4.4s | 1206〜1225ms @8T | **壊れる**: 「今日は耳のテストです。」の反復混入 |
| 160（不足） | 4.4s | 1129ms @8T | **大破**: 幻聴の繰り返し |
| 192（= 式値） | 2.6s | 932〜951ms @8T | 一致 |
| 124（margin 39） | 1.7s | 1003〜1983ms @8T | **壊れる**: 「そうだね」→「そうだに?に」 |
| 192 | 1.7s | 939〜940ms @8T | 一致（全窓は「うんそうだね」＝同内容） |
| 256（採用下限） | 1.7s | 1459〜1495ms @6T | 一致 |
| 560（14.6s に不足） | 14.6s | 2814〜2823ms @8T | **末尾文が欠落**（窓が音声より短い） |
| 795（= 式値） | 14.5s | 3911〜3995ms @8T | 全文一致（「メッシュ先生」の聞き違いは**全窓でも同一** = モデル起因） |

**採用式**: `audio_ctx = clamp(ceil(発話秒 × 50) + 96, 256, 1500)`（`src/whisper-inference.mjs` の `computeAudioCtx`）。
- margin +96: margin ≈0 で反復アーティファクト実測 → +64 で全ケース一致だったが、丸め・pad ばらつきに備え +96（コストは +64ms 程度）。
- 下限 256: 短発話は相対 margin が薄く 124 で劣化を実測。256 で一致・レイテンシ影響は軽微。
- 上限 1500 = 全窓（maxSpeech 20s の機械分割でも式値 ≈1099 で窓内）。

### 2.2 (b) threads（audio_ctx=280/312 併用・4.3s 音声）

| -t | warm 中央値 | 8T 比 |
| --- | --- | --- |
| 8 | 1535ms | 基準 |
| **6（採用）** | 1673〜1780ms | +9〜11% |
| 4 | 1931ms | +26% |

**採用 = 6T**。裁定基準「最速に近い最小スレッド数」: 6T は 8T 比 +9〜11% で、配信中に器の二体と CPU を分け合う前提では 2 論理コアの節約を優先。ただし §4 の注意（-t は総 CPU を律しない）。

### 2.3 (c) 探索幅削減（--no-fallback / -bo 1）

| 設定 | warm（4.3s・8T・ac280） |
| --- | --- |
| なし | 1504〜1535ms |
| `--no-fallback -bo 1` | 1515〜1532ms |

**効果なし・不採用**。temperature 0 の greedy では fallback/best-of は正常経路で発動しないため（品質保険として fallback は残す）。

### 2.4 打ち切り判定

採用構成（6T + 動的 audio_ctx）で warm **1.5〜1.8s ≤ 打ち切り基準 2〜3s** → 探索終了（3 系統・組み合わせ発散なし）。

## 3. 採用設定の分布と縦貫通実測

### 3.1 /inference 往復の分布（bench-asr・4.3s TTS・6T・ac312・N=8）

```
warm: 1740 1752 1740 1760 1778 1760 1745 1758 1821 (cold 1737)
min=1740ms median=1760ms max=1821ms  外れ値なし（spread 81ms）・9/9 回同一転写
```

### 3.2 発話終了→転写到着（preflight-ears・実 VAD + 実 whisper の縦貫通・採用既定そのまま）

fake マイク（TTS PCM を実時間レートで注入）→ 実 Silero VAD → セグメンタ → リング切り出し → 実 whisper-server:

```
transcript[0] 0.64..2.97s latency=1475ms audio_ctx=256 「こんにちは耳のテストです」
transcript[1] 4.23..6.62s latency=1511ms audio_ctx=256 「今日はメッシュ生成の続きをやります」
```

**発話終了（VAD 確定）→ 転写到着 ≈1.5s**。この latency には minSilence(400ms) は含まれない（speechEnd 発火後の計測）ので、体感の「言い終わってから」は +0.4s 程度上乗せで ≈1.9s。人間ゲート「数秒以内の追従」の合格域。

## 4. CPU 負荷

| 状態 | 実測 | 手段 |
| --- | --- | --- |
| ASR 推論中（6T・ac312） | whisper-server プロセス **≈9.5〜9.8 コア分**（953〜983% of one core）・システム全体 74〜82% | `Get-Counter '\Process(whisper-server)\% Processor Time'` を推論バースト中に 1s×6 サンプル |
| アイドル（VAD のみ・修正後） | **≈1.8% of one core**（全体の ≈0.1%） | `process.cpuUsage()`・実時間レート近似で 12s 回し（≈23 f/s。実レート 31.25 f/s 換算でも ≈2.5%/コア） |
| アイドル（システム暗騒音） | 全体 1〜8% | Get-Counter 5 サンプル |

- **注意（正直な記録）**: `-t 6` を指定しても推論中のプロセス CPU は ≈10 コア分に達する。`-t` は主計算グラフのスレッド数で、BLAS/flash-attn 層が別に並列化する模様。推論は 1.5〜1.8s の短いバーストなので配信への影響は瞬間的だが、「6T なら 6 コアに収まる」わけではない。二体並走との干渉は人間ゲート（OBS 同時起動）で観察するべき点。
- **アイドル CPU の重要な回収**: onnxruntime-node の既定セッションはスレッドプールがスピン待ちし、silero（2.3MB）を実時間レートで回すだけで **≈358%/コア** を空費していた（実測）。`intraOpNumThreads: 1` で **1.8%/コア**・per-frame 0.20ms → 0.18ms（悪化なし）。`silero-vad.mjs` の既定に反映済み。
