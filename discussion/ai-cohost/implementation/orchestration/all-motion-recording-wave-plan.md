## 目的・受領する体験

現在の意図モーション経路で捕捉した発話区間について、選べなかったものだけでなく選べたものも残す。後日「この会話の背景で、この意図から、この対象と演技のこの版が選ばれた」と辿り、ニュアンス違いの演技を制作する材料にする。

普段のRuntime Player通常版/portableとSoulを開き直して会話すると、選択済み区間の記録ができる。演技JSONを更新・削除して再起動した後も、古い記録から当時の定義を取得できる。保存失敗・未観測を成功と取り違えない。実会話の本人確認は内部検証とは区別する。

## 合意・変更しない前提

- 全件保存。容量のための間引きや自動削除を導入しない。現在452区間で2,351,473 bytes、平均約5.2KB。10年約100万件/5.2GBという仮定をユーザーが許容した。
- 原意図/タグ、発話本文、会話文脈、選んだ演技/注意対象、演技版、観測できた要求結果・音声状態を保存する。選択済み、未対応、判定失敗、捕捉後の判定前中断を区別する。
- 演技名・hashだけでは当時の内容を取り戻せない。実際に候補/再生に使った起動snapshot由来の定義を保存し、同一内容を区間ごとに複製しない。後日の可変JSONを読み直して当時の版と扱わない。
- 発話速度優先。記録/版保存/遅延判定・応答待ちを、音声開始や進行の待ちにしない。失敗は診断可能にし、保存できなかったものを保存済みとしない。
- 現行の自由な意図→演技/対象の独立判定、未制作ペア/none/unknownの扱いを維持する。演技や判定説明を今回変更しない。
- 現行のモーションacceptedは要求受付まで。実描画・演技完走の証拠にしない。今回は完走telemetryを新設せず、観測範囲に正直な状態を保存する。
- 現在の意図付き発話の経路（ElevenLabs）を対象とする。新しいTTS経路への拡張、常時音声/動画の録画、記録ブラウザUI、過去ログの再判定/改変、モーション制作は範囲外。
- 既存 `speech-intent-none` v1〜v3と過去集計を保つ。新記録の配置/形式は担当が定め、旧分析に新しい成功記録を紛れ込ませない。
- 配信ログ/演技履歴の実データは運用データとしてGit外へ。手順・契約・必要な小さなテストfixtureのみ管理する。[構成管理規約](../../../model-authoring/asset-versioning-policy.md)に従う。

## context-checkの事実

シルフによる読取監査済み（未実装）。`speech-intent-delivery.mjs` は区間を閉じ全音声jobが終端へ達するとfinalizeへ進み、`speech-intent-motion.mjs` はunsupportedのみ記録する。既に原意図・判定時本文・最終本文・直前会話・区間識別・音声範囲がある。判定前中断では準備されない区間があるため捕捉済み情報を失わない経路が必要。

Playerの `speech-motion-assets.ts` は起動時に有効定義を保持するが、JSON `version:1` はschema版であり演技の履歴ではない。helloには演技版/clip IDがなく、上書き前の原本保存もない。Playerのloader/hello契約とSoulのparser/保存まで変更が跨がる。型/schemaは追加属性を制限しており、両側の契約テストが必要。

技術案は内容hashで引ける演技定義archiveと選択時の参照保持。保存場所、原子性、失敗時診断、旧Player/再接続との互換を担当が具体化する。別端末配布機構を新設する必要はないが、記録から保存定義へ辿る実際の手順を示す。

既存の `recount.mjs` は固定の旧scene/result:none/hashを照合する過去実験の再現器であり、今回の全件分析器へ無断転用しない。

## 1 Wave内の順序と成果

単一Orchが下記を順次実行する。Player/Soulは同じ契約に依存するので担当を並列分割しない。

1. **具体契約**: 記録単位、選択/要求/音声の状態、演技版とclip参照、保存原本、配置・診断を短いbasisに定める。schema/ライフサイクルは既存実装へ接地する。
2. **Playerの版保存と受け渡し**: 読み込んだ有効定義を再取得可能に保存し、候補snapshotと一致する版をSoulに伝える。未制作ペアなどclip不在も虚偽の参照にしない。
3. **Soulの全区間記録**: selected/unsupported/error/not-decided等を意味に沿って保存。捕捉後中断・判定遅延・切断/再接続・応答喪失を扱い、二重記録や別区間への結果混入を防ぐ。
4. **独立レビュー・実経路検証**: 以下の受入条件を検証。問題があればGnome修正→独立再レビュー。
5. **普段の配布先を更新**: backup後、通常exeとportableを更新し、実配布先から隔離起動して全件記録と版参照を確認。現用モデル・演技データは変更不要。起動中のユーザーアプリを無断終了しない。

Orch所有: `implementation/waves/all-motion-recording/basis.md`、`completion.md`、`human-gate.md`。独立レビュー: `implementation/reviews/all-motion-recording/review.md`。新形式と保存先・記録から版を取得する手順をこれらから辿れるようにする。rootは本計画・map・ユーザー報告のみ所有する。

## 合格判断

- 正常に選んだ区間と未対応区間の両方で、元意図/本文/文脈/対象/結果を読み返せる。
- 同じ演技IDの定義変更→再起動、さらに元JSON削除後も、旧新それぞれの記録から正しい保存定義を取得できる。同一内容は共有される。起動中編集・再接続で版を取り違えない。
- 捕捉済み区間の判定前中断、遅延判定、要求見送り/拒否/結果不明を記録し、受付を実描画完走と呼ばない。音声観測は音声として区別する。
- 記録/版保存を遅延または失敗させた検証で音声を待たせず、失敗を把握できる。通常finalizeの重複で記録を壊さない。
- 旧ログは不変、既存モーションの選択/再生と発話経路が回帰しない。対象単体・実WebSocket・型/schema・境界チェックを変更に合わせて実行する。
- 普段の `apps/runtime-player/dist/win-unpacked/Runtime Player.exe` と `dist/Runtime Player 0.0.0.exe` で新機能を確認。開発実行だけで完了としない。

## オーケストレーション

- root → 単一Orch-Sylph → 別コンテキストGnome / 別コンテキストReview-Sylph。Orch以下はGPT-6.1 Sol。
- 簡易オーケストレーション: 担当分割・文書量を絞り、実装/独立レビューの分離と上記検証は省略しない。最大5修正ループ。正常な作業中の担当は待つ。
- Orch-Sylph自身は実装担当ではない。source implementation は必ず別コンテキストの Gnome に委譲し、レビューは必ず別コンテキストの Review-Sylph に委譲すること。これを分離できない場合は実装せず escalate / blocked として報告すること。
- 全担当は共有workspaceで作業し、他者の変更や未追跡の運用記録を戻さない。外部書込・Git操作は必要な承認経路を使う。今回commit/pushは依頼されていない。
- 終了後は「画面へ関心を向ける」の最初の代表応答をユーザーと相談する。112件を一つの演技で全て覆う前提にしない。
