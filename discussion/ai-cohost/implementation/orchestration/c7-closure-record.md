# C7「配信に乗る」閉鎖記録

> Status: **完全閉鎖(2026-07-12)**。
> 位置づけ: 閉問題分解([../closed-problem-decomposition.md](../closed-problem-decomposition.md))の最後の問題。**wave なし・棚卸しなし・実装ゼロの検証のみで閉鎖**した唯一の閉問題であり、本ファイルが wave 計画の代わりの閉鎖成果物。

## 1. ゲート定義と結果

- ゲート(分解表 §3): 「OBS画面にユーザーのモデルとAIモデルが並び、両方生きている」(人間一目)。
- **結果: 合格(ユーザー実施 2026-07-12)**。OBS のシーンに二つの Browser Source を並べ、二体とも生きて見えることを確認。しかも**二役割が本来の姿で並走**した——ユーザー側モデルはフェイストラッキング駆動、AI側モデルは生理(C2/C3)駆動。構想の絵(ユーザー×自律AIの共演)が初めて配信出口で実物になった。

## 2. 実装ゼロで閉じた理由

C2〜C6 の全 wave で「Browser Source への parity 配信」を blocking レビュー基準として維持し続けたため、C7 に残る作業が検証のみになった(分解時の狙いどおり)。

parity の疎通も全系統で目視済み: ユーザーは開発期間中ちょくちょく OBS につないでおり、生理(C2/C3)だけでなく**チャネル駆動(C4/C5)と口(C6)も OBS 越しに動く姿を確認済み**(ユーザー確認 2026-07-12)。「配線の存在の確認と疎通の確認は別物」(C6 教訓)の観点でも、疎通側が人間の目で裏取りされている。

## 3. 既知制限: 二体同時起動の負荷(未計測)

- ユーザー観測(2026-07-12): 「シンプルにこのPCのスペックで2個動かすのはちょっときつそうだ」。ハードウェア側(GPU/CPU予算)要因の可能性が高いが、**未計測**。
- これは [../../../render-performance/player-survey.md](../../../render-performance/player-survey.md)(2026-07-08、結論「改善不要が有力・決定性に触る最適化は実測でボトルネック確定まで着手しない=保留」)が未解決質問として残した「stage と Browser Source 同時起動時の負荷は未計測」への**初の実データ**。
- **性能改善そのものは C7 のスコープに入れない(ユーザー裁定 2026-07-12)**。再開条件が満たされた事実のみ render-performance トピックに記録し、再開の要否・時期は別途裁定(S系列の前か、実配信で困ってからか)。再開点は player-survey の #5(deep profiling の live 配線=計測のみ)→ #1(無駄な getState() parse 除去)/ #4(三角形インデックスキャッシュ)。

## 4. これで何が完成したか

**C1〜C7 全閉鎖 = 器(vessel)の完成**。魂ゼロの状態で: 二体同居(C1)、呼吸・まばたき(C2)、視線・頭・姿勢+質感ツマミ(C3)、操縦チャネル+特区+参照ドライバ(C4)、曲線合成+実効値+release(C5)、口タイムライン+Articulation(C6)、そして OBS 二体並走(C7)。
