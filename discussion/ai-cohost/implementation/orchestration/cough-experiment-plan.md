# 咳払いの聞き取り実験(段階 1)の実装計画

> Status: 着手(ユーザー 2026-11-06「これやろうか」、試作・合図・置き場の OK)。ブランチ `ai-cohost/cough-experiment`(master `a305eaa8` から)。
> 根拠: 調査 [../../research/cough-filter-audio-tagging-2026-11.md](../../research/cough-filter-audio-tagging-2026-11.md)(以下「調査」)。

## 0. 何のためか

- 咳払いが「うん」などに聞き取られ、変な応答につながる(ユーザー: ほとんどは咳払い・だいたい「うん」になる・判定と表示の両方で困る)。
- 段階 1 は**データを取るための試作**で実験するだけ。本番の耳(操縦席)には入れない。何も落とさない。
- 実験で分かること: 咳払いが何に化けるか(「短い」を何文字にするかの材料)、咳払いと本物の「うん」で確率がどう分かれるか(しきい値の材料)。
- 段階 2(本番の耳で落とす)は、結果を見てから決める。「短い」の文字数・しきい値・モデルが無いときの扱い・Discord の耳で効かせるかは、段階 2 で決める(ユーザー「2文字以下を入れるかを考えるのは簡単な実験を行った後の方がいいな」)。

## 1. 決まったこと(ユーザー 2026-11-06)

- 試作は `apps/soul/agent/scripts/` に実験用の道具として置く。本番の耳の流れは変えない(ユーザー OK)。
- 合図: 咳払い・「うん」・「うーん」・軽い咳の 4 種類を 10 回ずつ(ユーザー OK)。BGM・ゲーム音ありの回はやらない(ユーザー「マイクは基本的にそれを拾ってないからな」)。
- 結果に文字起こしの文字を残してよい(わざとの声だけなので。ユーザー OK)。結果のファイルは git に入れないローカルの 1 行 1 件(ユーザー OK)。
- モデルは sherpa-onnx の公開ページから取得スクリプトで取る(約 6MB・ユーザー OK)。リポジトリには入れない。
- ライセンス: 使うのは重み(Hugging Face では Apache-2.0)だけで、配らないので構わないと扱う(ユーザー OK)。

## 2. 体制

- Undine → Orch-Sylph(opus)→ Gnome(opus)+ Review-Sylph(sonnet)。単独ドメイン。
- 機械ゲート: `apps/soul/agent` で `node --test` 全件 pass、リポジトリの根で `pnpm run check:soul-zone` pass。依存と lockfile は変えない(sherpa-onnx-node 2.0.0 は既に入っている。要るなら escalate)。
- 守ること:
  - テストと子エージェントは実データに触らない: `cockpit-settings.local.json`、`memories/`、`roles/`、`session-usage/`、`fire-diagnostics/`、`memory-backups/`、`.env*`(読まない)。
  - 操縦席を起動しない。本物のマイクを開かない。道具を本物で走らせない(走らせるのはユーザー)。本物の LLM・外部 API を呼ばない。モデルの取得(ダウンロード)もしない(取得スクリプトを書くだけ。走らせるのは Undine がユーザーの OK のもとで)。
  - 声は保存しない。音はメモリの中だけ。
  - 本番の耳の挙動(`ear-pipeline.mjs`・`local-stt-worker-core.mjs` など)は変えない。使い回すために小さな export を足すのはよい。

## 3. 作るもの

**触る所**: 新しい道具(例 `scripts/cough-experiment.mjs`。名前は裁量)と、要るなら専用の子プロセスのスクリプト、`scripts/fetch-local-stt-models.mjs`(判定モデルの取得を足す)、`apps/soul/agent/.gitignore`(結果の置き場)、テスト。

1. **流れは本番に揃える**: マイク → 本番の耳と同じ VAD と区切りの設定 → 本番と同じ Zipformer の文字起こし → 音の種類の判定(CED-tiny int8)。マイクの選び方も本番の耳に合わせる(実データの設定を読むのは、ユーザーが走らせたときだけ。テストでは読まない)。
   - 親では sherpa-onnx-node を読み込めない(調査 §5、`no-sherpa-in-parent.test.mjs`)。文字起こしと判定は子プロセスで回す。本番の子を変えずに済む形は Gnome の裁量(例: 実験専用の子が、本番と同じ設定で recognizer と `AudioTagging` を作る)。
2. **判定**: 区間の音に無音を足して約 5 秒にのばしてから `AudioTagging` に渡す(調査 §1・§7)。区間の文字数に関係なく、全区間を判定する(「短い」はまだ決めないため)。
3. **合図**: 4 種類 × 10 回を混ぜた順で 1 つずつ出す(例「咳払いを 1 回してください」)。合図のあと次の区間を待つ。来なければ「区間なし」として記録し次へ。1 つの合図の間に区間が複数来たら、すべてその合図の印で記録する。開始前に短い説明と、何回目かの表示を出す。途中で Ctrl+C したら、それまでの分を残して終わる。
4. **記録**(1 行 1 件の JSON、git に入れないローカルの置き場。例 `apps/soul/agent/cough-experiments/<日時>.jsonl`): 合図の種類・回数・文字起こしの文字・文字数・区間の長さ(ms)・Speech / Cough / Throat clearing の確率・1 位のラベルとその確率・時刻。音は残さない。
5. **終わりのまとめ**: 合図の種類ごとに、文字起こしの文字の内訳(「うん」何回・「ん」何回・空…)と、3 つの確率の最小・中央・最大をターミナルに出す。
6. **モデル**: 取得スクリプトに CED-tiny(sherpa-onnx の audio tagging の公開ファイル)を足す。置き場は `vendor/models/` の流儀。モデルが無ければ、道具は取得の仕方を 1 行出して止まる。
7. **テスト**: 偽物の sherpa(`AudioTagging` を足す)・偽物のマイクで、のばし方・合図の順・記録の形・まとめ・区間なし/複数・モデルが無いとき・音を書かないこと、を確かめる。

## 4. 実験(実装の合格のあと)

1. Undine がユーザーの OK のもとで取得スクリプトを走らせ、モデルを取る。
2. ユーザーが道具を走らせ、合図どおりに声を出す(40 回)。
3. Undine が結果のファイルを読み、分かれ方をまとめて調査の記録に足す。段階 2 の「短い」としきい値を相談する。

## 6. 段階 2 で決まったこと(ユーザー 2026-11-06・実装計画はまだ)

- **落とす条件**:
  - 文字起こしが 4 文字以下の区間だけを判定にかける(ユーザー「一回やってみるか」)。
  - Speech の確率が線より低ければ落とす。咳や咳払いの確率は見ない(調査 §9.2)。
  - 長い発話は判定にかけず、そのまま通す(ユーザー OK)。
  - 短い返事の測り直しはしない(ユーザー「計ったところでどうせすべてにはならない / 測定はこれで十分」)。
- **数字は画面に出さない設定ファイルで変えられるようにする**(ユーザー OK)。
  - 2 つの数字は、文字数の上限(既定 4)と Speech の線(既定 0.1 の案)。
  - 置き場は `cockpit-settings.local.json`。今のローカルの文字起こしの設定(hotwords・余白)と同じ扱いで、Start ごとに読む。
- **落としたことの知らせ**(ユーザー: タイムラインに乗るのは嫌・軽く分かればよい・残り続けるのは嫌。置き場の調査 [../../research/cough-drop-indicator-ui-2026-11.md](../../research/cough-drop-indicator-ui-2026-11.md)):
  - 上の帯の状態の表示の隣に、薄いグレーで「咳 ×N」と出す(候補 A・ユーザー OK)。
  - 最後に落としてから 8 秒で消える。続けて落ちると N が増え、消えるまでの時間がのびる(ユーザー「8秒でOK」)。
  - 札に出すのは「咳 ×N」だけ。マウスを乗せたときだけ、文字と確率を出す(ユーザー OK)。
  - ログのタブには、落とした行として残ってよい(ユーザー「ログは常時は見ないから残ってもいいよ」)。
  - アニメーションは付けない。開き直したときに札が消えていてもよい(Undine)。
- **Discord の耳でも効かせる**。誰の咳かは出さない(ユーザー「誰の咳かはでなくて大丈夫 / こっちも有効にしよう」)。
- ElevenLabs の経路には掛けない。文字しか届かないので判定ができない(Undine)。
- **まだ決めていないこと**:
  - 判定のモデルが無い・読み込めないときの扱い。
  - 本番でのモデルの取り方。既定の取得に含めるかどうか。
