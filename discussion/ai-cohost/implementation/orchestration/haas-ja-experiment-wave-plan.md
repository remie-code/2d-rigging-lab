# Haas-ja と Zipformer の比較実験

2026-11-09。1 wave・1 domain（A: Windows動作確認と発話比較）。Haas-jaをローカル文字起こしの選択肢に加える価値を、共演で使う発話と待ち時間から判断する。本番の耳・操縦席・Discordの設定への追加は、結果を見て別途決める。

**実装合格・人間ゲート待ち。** Windowsでの常駐動作と実エンジンを使った試験音声での比較を確認した。ユーザーの発話手順、測定条件、機械ゲートは[独立レビューの記録](../reviews/haas-ja-experiment/review.md)を参照する。

根拠は [Haasの公式モデルカード](https://huggingface.co/third-intelligence/Haas-ja-v1.0)、[Windows対応のGGUF配布元](https://huggingface.co/sakasegawa/Haas-ja-v1.0-GGUF)、[既存のローカルSTT比較](../../research/stt-candidates-2026-10.md)、[咳払い実験](cough-experiment-plan.md)。

## Domain A の順序とゲート

**短い音声での動作確認 → 比較用の道具と独立レビュー → ユーザーの発話で比較 → 結果を一緒に読む。** 依存が同じドメイン内で閉じるため、同じ担当が順番に進める。

### 1. Windowsでの動作確認（エージェント側）

- 第一候補は `speech.cpp` と Haas-ja-v1.0 の Q8 GGUF。実行系・モデルの版、Windows上の実行条件、CPU/GPUの使用経路を記録する。取得物はリポジトリへ入れない。
- ユーザーの声を使わず、短い日本語の試験音声を用意する。モデルを読み込んだ状態で複数の発話を連続処理でき、文字が返れば比較へ進む。モデルの初回ロード時間は会話中の待ち時間と分ける。
- 動かなければ環境・読み込み・推論のどこで止まったかを報告する。別の実行方式を検討する場合の候補はコミュニティ版ONNX。現行のWindows環境で動くかは未確認であり、読み込み失敗をHaasの認識性能の結果として扱わない。

### 2. ユーザーの発話で比較

- 合図と結果が分かるローカルの実験用の道具を用意する。ユーザーには普段の話し方で、普通の会話・短い相づち（「うん」など）・咳払い・固有名詞を含む発話を一度ずつしてもらう。同じ音声を両方の認識器に使う。ユーザーに発話をお願いするのは、動作確認・機械ゲート・レビューを通り、実行手順が揃ってから。
- 共通のVADと区切りを使って入力を対応づける。Zipformerは現行の前処理・設定を使い、方式ごとの前処理、語彙の補助の有無、スレッド数、実行デバイスを記録する。両方式を同時に走らせて負荷が干渉する場合は、収録した同じ音声を片方ずつ実時間で再生する。生音声は比較に必要な間だけメモリに保持する。音声を後日の再測定用に保存する必要があれば収録前に相談する。
- 各試行に、意図した発話または合図、両方式の転写、空の結果・VADで区間なし・複数区間・認識失敗の区別を残す。咳が文字になるか、本物の相づちが残るか、名前の表記がどうなるかを別々に見られるようにする。既存の咳フィルタ後も測る場合は認識直後の結果と別欄にする。
- **計測は二つ。** (a) 認識器に確定区間を渡してから結果が返るまで。(b) 実際の発話末尾から文字が確定するまで。後者には区切り待ちを含める。実時間再生を使う場合は収録音声上の発話末尾を再生の時計に対応させる。発話末尾を特定できない試行はその値を欠測にする。VAD確定からの既存 `latencyMs` を (b) として流用しない。
- 転写と計測値は端末内の比較結果として扱う。実発話の転写や生音声をGitへ入れない。結果は発話別に並べ、どの場面で改善・悪化したか、待ち時間がどう変わったかを要約する。観測から次を判断する実験なので、モデル間の勝敗を決める数値のしきい値は置かない。

## 体制と簡易レビュー

- Undine → Orch-Sylph → 別コンテキストの Gnome と Review-Sylph。Orch-Sylph自身は実装担当ではない。source implementation は必ず別コンテキストの Gnome に委譲し、レビューは必ず別コンテキストの Review-Sylph に委譲すること。これを分離できない場合は実装せず escalate / blocked として報告すること。
- 委譲の冒頭に `[subagent-call] 呼び出し元: Undine` または `[subagent-call] 呼び出し元: Sylph` を付ける。Gnomeは実験用の道具・必要なテストを担当する。既存の咳実験の流れを参考にし、WindowsでのVADとsherpaの別プロセス境界を守る。自動検証では実マイク、ユーザーの設定・記憶・認証情報を使わない。
- 機械ゲートは、試験入力での同一音声の受け渡し、計測区間、空・失敗の区別、音声をディスクに書かないことの確認、`apps/soul/agent` の `node --test`、ルートの `pnpm run check:soul-zone`。第1段のWindows実動作も証跡に残す。
- 最近の咳実験と同じく、独立Review-Sylph一人が計画・差分・検証結果を一報告で照合する。とくに入力の公平性、遅延の起点と終点、既存の耳への影響、結果から言える範囲を見る。問題がなければ一巡で閉じ、修正した箇所だけ再確認する。報告先は `discussion/ai-cohost/implementation/reviews/haas-ja-experiment/review.md`。
- レビュー合格後に、Undineがユーザーへ実行方法と発話の合図を案内する。ユーザーの発話で得た結果は、実装の機械ゲートと区別して記録する。
## 2026-11-09 の発話比較

ユーザーの発話で4種類を収録し、同一区間を両方式で比較できた。会話の試行は2区間になったため、本題の文を会話の結果として扱い、先行区間は別扱いとした。生音声と転写結果はリポジトリに含めない。

- 会話の文では、Haasが一部を自然な漢字表記にした。短い相づちは両方式とも拾えた。
- 咳払いは認識直後の出力では両方式とも文字になった。この比較では既存の咳フィルタを無効にしている。
- 固有名詞の試行では、Zipformerの方が名称に近い表記を返した箇所があった。Zipformerは共通設定の語彙補助あり、Haasは語彙補助なしのため、参考として扱う。
- 主な4区間で、Haasの認識処理時間はZipformerより約18〜55ms長かった。区切り待ちを含む再生内の推定では約11〜67ms長かった。厳密な発話末尾からの実測値とマイクの取り込み遅延は測っていない。

比較は実施済み。各種類の少数試行であり、全体の認識精度や実運用での優劣は判定していない。操縦席に追加するかは未決。
