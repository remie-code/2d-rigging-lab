# 自由な意図から発話モーションを育てる

2026-11-10、ユーザーと合意。実装ブランチ `codex/intent-motion`、コード基点 `a7ddfdfc`。計画作成と起動をユーザーが指示。Orch以下の実装・レビューエージェントはすべて **GPT-6.1 Sol (`gpt-6.1-sol`)**。

## 1. 体験と変更しない合意（User Gate）

チャッピーと実際に会話すると、本人が発話区間に添えた自由な意図から、その区間に合う既存モーションが選ばれて動く。対応できなければその意図の動きは取らず、後日ユーザーとエージェントが発話と文脈を読み返して新しい動きを作れる。

- 意図の内容を利用可能なタグ一覧に制限しない。機械的に区間を識別する書式は必要だが、意味の候補リストを生成LLMに選ばせない。
- 本人が出した意図を尊重する。本文と意図の一致を外部採点・矯正しない。
- DecisionAPIは登録済みの意図と明示的な「どれでもない」を判定する。近似候補への押し込みを避け、未対応を正常な結果として扱う。拒否・通信失敗・中断を未対応と偽って混ぜない。
- 発話全体ではなく意味のある区間ごとに意図を扱う。句点ごとの一文と意図区間を同一だと仮定しない。
- 未対応は意図の原文、対応区間の本文、発話と場の識別、会話文脈を後日たどれる形で残す。要約記憶だけに依存しない。候補追加は後日の共同制作で、自動モーション生成は今回に含めない。
- 意図の異なる言い方が同じ既存モーションへ集約されてよい。未対応タグ一つにつき一つのモーションを作る必要はない。
- 初期対応は今回の「受け取る」「関心を向ける」「問いかける」。受け取りは強い賛成の強制ではない。問いかけのあとには返答を待つ注意が続く。
- 相方はキャラから見て右、画面左。横向きはモデル可動域の最大80%程度を使用する。承認済みyaw80試作を基準とし、モデルの極値を再定義しない。
- 今回はElevenLabs発話を対象にする。場のモード（配信/Discord等）だけを理由に利用条件を分けない。
- **音声開始の速さを優先し、動きは多少遅れて開始してよい。** 意図判定の完了を音声合成・再生開始の待機条件にしない。同期は厳密な一致を要求しない。
- 最終人間ゲートはユーザーが実際にチャッピーと会話して動きを見た後、未対応の記録一件を開き「次にどんな動きを作るか」を議論できること。機械ゲートだけでこのゲートを合格にしない。

## 3. Wave構成と依存

**Wave 1の契約・再生・記録が独立レビューを通ってからWave 2を開始する。** 各waveは一人のOrch-Sylphが管理する。同じwave内の依存はそのOrch内で順に進め、共有契約が固まる前に依存する担当を並列起動しない。

### Wave 1 — 意図を受け取って動く／残す土台

1. 区間・意図・発話/世代/場ID・文脈の対応、判定結果、再生要求、未対応記録の契約を小さく定める。Orchは契約のbasisを残し、実装はGnomeへ委譲する。
2. 登録済み意図の説明と初期3モーションを定義。承認済み動きから、現在姿勢に連続して開始・遷移できるプリセットへ分ける。音声や口形をプリセットに固定しない。初期データはGit管理可能な小さい定義にし、外部モデルや録音をリポジトリに投入しない。
3. DecisionAPIで登録済み候補またはnoneを選ぶサービスを作る。候補追加時に生成側の自由な意図語彙を修正する必要がない構造とする。
4. 多軸モーションを実際のライブ制御経路で再生できるようにする。既存表情・口・視線等の所有権と競合を明示し、今回の発話演出に必要な範囲を実装。切断・中断・世代変更による古い要求を分離する。
5. noneを本文と会話文脈付きで永続化し、ユーザーとエージェントが後日読む手順を用意する。専用管理画面や場開始時の自動提示は今回の要件に足さない。
6. 制御した区間入力から、DecisionAPI→選択→ライブ再生、none→無演出→読み返せる記録の両経路を確認する。

Wave 1 gate: 正常選択/none/失敗が区別され、対応の取り違えがなく、初期動きがライブ経路で再現できる。現行表情/口パクに退行がない。独立レビュー合格。

### Wave 2 — チャッピーの実発話への接続

1. 自由な区間意図の出力教示と逐次解析を導入する。分割されたタグ、句点、複数区間、タグなし応答、既存タグとの併存を扱い、制御文字がTTSへ漏れないことを確認する。
2. 意図区間と音声job/再生時間軸を結び、判定と音声合成を並行させる。判定が未完了でも音声が進むことを制御された遅延で証明する。多少遅れて選択された動きを開始できる。
3. 次区間への遷移、自然終了の待つ姿勢、割込み/kill/場終了をつなぐ。古い世代の結果を新しい発話へ適用しない。姿勢の収束・重複処理・区間を過ぎた結果などの具体的動作は契約に明記してレビューする。未合意の体験変更が必要ならUndineへ戻す。
4. 実会話で出た未対応意図を、聞こえた範囲/未再生/中断等の状態と混同せず読み返せるようにする。記録の処理が音声開始の待機条件にならない構成にする。
5. 結線した経路の機械検証と少数の実DecisionAPI確認を行い、意図出力を含む初動/判定/音声開始/動き開始の観測点を残す。今回まだ測っていない速度を過去の他用途の測定値で保証しない。
6. 起動/確認/記録を開く具体的手順を整え、ユーザーの実会話ゲートへ渡す。

## 4. 検証と簡易レビュー

- 基盤の単体試験だけでなく、実送出・受信・再生の接続を通した統合証拠を取る。Wave 1の制御入力とWave 2の生成/逐次入力の双方を区別して報告する。
- noneが選べること、異なる言い方が登録済み意図へ集約できることを少数の具体例で確認。本文と意図の真偽の採点にはしない。
- 遅い判定、結果の順序入れ替わり、重複、割込み後の到着、切断/再接続、タグ分割、既存タグ・口の回帰を含める。待ち時間を固定sleepで隠さない。
- モーションの最大横向き80%、開始/つなぎの連続性、口パクとの併存を確認。外部モデルが必要な目視確認と、リポジトリだけで走る機械試験を分ける。
- 関連パッケージのrequired checksとSoul-zone規約に従う。既存失敗と新規回帰、未実施を区別し、合格した試験を理由なく繰り返さない。
- 独立Review-Sylph一人が各waveを一報告でレビュー。spec/design/testの3レーンへ機械的に分割しない。問題がなければ一巡、修正は限定再確認。最大5巡、価値判断の漏れはその前でもエスカレーション。

## 5. オーケストレーションと所有

Undineは計画・合意・依存・ゲート・完了報告を保持する。source/tests/domain差分の実装・直接精査は行わない。

Orch-Sylph自身は実装担当ではない。source implementation は必ず別コンテキストの Gnome に委譲し、レビューは必ず別コンテキストの Review-Sylph に委譲すること。これを分離できない場合は実装せず escalate / blocked として報告すること。

- 全階層の委譲に `[subagent-call] 呼び出し元: ...` を付ける。**全Orch/Gnome/Review-SylphはGPT-6.1 Sol**。モデル指定時は新規contextで必要なbasisを渡す。
- Gnomeには所有ファイル/モジュールを明示する。共有workspaceで他の作業があること、既存差分をrevertしないことを必ず伝える。
- 起動時の既存差分は会話モーションのconcept/experiments/research文書と各map。root所有の計画・上位mapと、既存の議論差分を無断で書き換えたりコミットに巻き込まない。
- branchのcheckout/commit/merge/pushはOrch以下で行わない。今回は実装とレビュー・確認手順まで。API鍵を出力せず、実マイク・本物のDiscord接続・ユーザーへの送信を機械試験で勝手に実行しない。
- 共有音声基盤・モデル・Control Channel全体の再設計へ広がる場合、scopeを広げる前にUndineへ戻す。
- root所有: 本計画、`implementation/orchestration/_map.md`、`implementation/_map.md`。
- Orch所有: `implementation/waves/intent-motion/` のdomain basis・completion・検証証拠・human-gate手順とそのmap。必要な既存ドメイン文書更新は実装担当へ委譲し所有を明示。
- Review-Sylph所有: `implementation/reviews/intent-motion/` の独立レビューとmap。
