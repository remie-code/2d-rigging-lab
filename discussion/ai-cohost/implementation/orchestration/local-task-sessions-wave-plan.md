## 1. 決定と責務

PDFを読むことは「ローカル処理を必要とする小タスク」の最初の用途。PDF専用品だけを増やさず、既存の記憶参照も頻出する特殊系として今回共通基盤へ移す。

| 担当 | 責務 |
| --- | --- |
| チャッピー | 依頼内容を決め、会話を続け、返答を理解してどう応答するか判断する。誰に何を話すか、秘匿情報の扱いもLLMの判断 |
| 小タスクセッション | 必要な道具で作業し、進め方・読む量・返答内容・読めなかった事情等を自律的に判断する |
| Cockpit／ツール | 能力ごとの実行環境と権限を用意し、依頼を担当へ渡し、返答を元の場へ届け、プロセスと資源の寿命を管理する |

- セッションは毎依頼新規。再利用・再利用判断・常駐担当poolは導入しない。
- 主会話の権限を広げない。ローカル処理担当には対象資料を読む環境と、場の管理下の作業領域へ書き出せる環境を用意する。cwdの指定とOSが強制する権限範囲を混同しない。既存のCodex/session設定を調査・実証して必要な境界を作る。
- 小タスクの意味上の成功／失敗や要約schema、固定の必須報告項目をツールで判定しない。担当の「読めなかった」も通常の返答として届ける。返答を得たこととプロセス失敗・取消し等の機械状態は区別する。
- 原本と作業領域は場に属する。担当終了のたびに内容を分類して移動・削除する構造は不要。後の新規担当が再参照可能。VC離脱は場の終了ではない。
- 短いDiscord本文は直接会話へ。既存の軽い画像共有を不用意に失わない。資料の参照情報から必要な小タスクをチャッピーが依頼できる。PDFを先頭3ページだけへ置換し毎Fireで注入する方式は今回の本線から置換する。
- 場の終了は、新規受付・発話を止め、受付済みの仕事を終え、記憶書き出し／保存・必要な整理を待ち、最後に場の領域を片付ける。閉じている場で「結果を発話し終えるまで待つ」実装にしない。
- 記憶書き出しの90秒待機上限は撤去。完了または失敗の確定まで待つ。本文の長さや生成時間に新しい上限を足さない。明示的な強制終了、通信・個別ツールの障害検知は区別する。
- 資料や小タスク返答だけが増えた場合も書き出し役へ回す。何を読むか、何を記憶に残すかは書き出し役の裁量。Cockpitは内容の重要性や秘匿性を判定しない。
- 記憶の書き出し役そのものを小タスク化する要求ではない。今回は記憶参照の移行と、書き出しへの材料・待機・寿命の修正を扱う。
- 場の領域と永続記憶の保存先を明確に区別する。永続記憶、ユーザーの元ファイル、他の場や稼働中タスクの領域を終了掃除で削除してはならない。
- 実資料や個人情報はGit外。元の `audio-devices-*.md` と `.codex-attachments` の除外を維持。再現可能な画像列・大きな試験生成物も追跡せず、小さな合成fixture／生成手順と証拠を残す。

## Accepted User Gate

### あなたが受け取るもの／行うこと
- 従来どおりチャッピーと話し、記憶を思い出す依頼ができる。
- Discordで選んだチャットへハンドアウトのPDFを投稿し、チャッピーに内容の確認を頼める。担当が読んでいる間も会話を続けられ、後から返答を受け取れる。
- 同じ場で後から資料を再確認できる。VC退出・再参加でも資料は失われない。
- 場を閉じると、仕事と記憶の書き出し・保存が終わるまで必要な資料が残り、最後に場のリソースが片付く。

### あなたが判断すること
- 記憶参照が従来の体験を保ち、資料の確認を任せながら会話し、結果を使えるか。
- 小タスクの進め方・返答内容は担当LLMが判断し、チャッピーが結果を踏まえて応答する体験になっているか。

### あなたが判断しないこと
- 共通基盤への移行の適否、プロセスとファイルの所有権、終了順序、機械的な回帰は実装・独立レビューで確認する。

### 合格条件
- 記憶参照とローカル小タスクが、共通の別セッション実行基盤を実際に使う。
- 依頼ごとに新しい担当セッションを起動し、再利用しない。処理中も主会話を進められる。
- PDFの先頭3ページに固定されず、依頼に応じて後半も担当が調べられる。
- 記憶の書き出しを90秒で待ち切らずに進める挙動がなく、資料の削除は必要な利用が終わった後になる。
- 内部検証の合格を、本人の会話確認の合格として代行記録しない。

### 違和感や不足があった場合のフィードバック
- どの依頼・会話・資料・終了操作で期待と異なったかを確認し、合意した責務と体験に照らして修正する。

## 2. 実装前の確認事実

- 既存recallは応答の `<recall>` を拾い、発話後に別の使い捨てセッションを起動。主会話は検索Promiseを待たない。結果をidleで発話または次askへ前置きする。
- 現行recallの実行1件＋待ち1件、自由文依頼、記憶フォルダと検索指示、found/要約、今話すか判定等には記憶固有の意味がある。これらを全能力の固定規約にしない。移行では従来の記憶参照の振る舞いを保つ。
- recall係のdisposeは配送を捨てるが実行中workerを直ちにabortしない。終了時に実行完了待ちと会話への配送待ちを分離する必要がある。
- 通常closeはclosing→転写コピー→Discord資料clear/主会話など停止→最終writer→必要ならorganizer→closed。現状のwriterには添付や小タスク返答の直接参照がない。
- 最終writer待ちは90秒race。writer自体の生成全体／記憶本文文字数の上限は確認されず、RPC受理後はterminalを待つ。再度Ctrl+Cは現行では待機を解除するだけで、worker停止とは一致しない。
- 前段Discord実装は原本を処理中だけ使い、PDF画像と本文を30分／12投稿のキャッシュで保持。チャット変更でclear。原本の場寿命と、現在の受信・通知の世代は新たに分ける必要がある。
- パス実験は非圧縮文字PDFで読取成功、画像PDFはread-onlyの画像書込に失敗。WinRT描画と画像入力は両合成PDFで成功した。新担当の作業領域と道具で再実証する。前段の先頭3ページはモデル仕様ではなく旧実装の裁量上限。
- 前段の内部検証はSoul 2,567件成功、本人の実Discord確認は未実施。Claudeの実モデルはOAuth期限切れのため未確認。

## 3. Wave構成

### Wave 1 — 共通基盤と記憶参照の実移行

- 既存挙動の基線を対象テストで確認。現在の未コミット差分を壊さず、増分が分かる証拠を残す。
- 依頼、実行環境、毎回の新規session、返答／機械失敗、場世代の所有と配送の共通契約を短いbasisに定める。意味判断を共通層へ持ち込まない。
- 記憶参照を本当に共通層へ通す。検索指示・記憶の場所・従来の発話判定等は記憶側の設定／接続部分として保持。
- 既存recallの体験、主会話の非待機、使い捨てsession、返答の取り違え防止を独立レビューで確認。
- 成果: `waves/local-task-sessions/basis.md`、`wave1-completion.md`、`reviews/local-task-sessions/wave1-review.md`。

### Wave 2 — 場の所有権と終了・記憶書き出し

- 場所有の資料／作業領域と参照口を作る。タスクは異なる作業先で動き、後続依頼から場の資料を参照できる。原本・作業ファイルの機械的な管理と内容判断を分ける。
- 受信／発話の停止と、資料破棄を別処理にする。終了中は会話への返答配送を待たず、実行完了の返答を保存側へ渡す。
- 記憶書き出しに会話と利用可能な資料／返答の参照を渡す。発話数だけの保存要否判定を修正。残す内容はwriterへ任せる。
- 90秒待機上限を撤去し、記憶保存・必要整理の後でのみ場の領域を解放。通常close、Ctrl+C/EOF、失敗、ロール変更を検証。異常終了で残った管理領域を次回に回収する場合、所有権と稼働状態を確認し、無関係なパスを消さない。
- 遅いfake worker/writerで順序を検証。90秒の実時間sleepを機械的に繰り返すテストより、待機と完了の契約を観測できる試験を使う。
- 成果: `wave2-completion.md`、`reviews/local-task-sessions/wave2-review.md`、basisの寿命・起動環境追記。

### Wave 3 — ローカル小タスクとDiscord資料の接続

- 場の資料保存をDiscord添付受信へ接続。保存済み資料の寿命と、新規受信先の切替・重複・通知の世代を区別する。短い本文は直接、添付はチャッピーから指定できる参照情報を渡す。
- 自由な依頼をローカル小タスク担当へ渡せる入口を用意。具体的なタグ／ツール書式は現行の会話・逐次発話に接地してbasisへ定める。依頼文を読み上げへ漏らさず、主会話が実処理を待たない。
- 担当には原本を参照する方法、書き込み可能な専用作業先、必要な道具を用意。実行モデルの決め方は既存ロール／補助担当の設定に接地し、選定理由を記録。開発用Orchモデル指定と製品で使うモデル選択を混同しない。
- PDFを4ページ以降まで調べる合成の文字PDF／画像PDFで検証。担当が道具を使い、書込みを伴う処理をして返答できることを通常Windows起動環境で実証する。ページを読む順序や結果の書き方はLLMの裁量で、固定3頁制約や機械的な要約品質判定を戻さない。
- 既存WinRT描画等は担当用の道具の部品として再利用可能。ライブラリやツールの有限の実行単位を、資料の後半を読めない製品上限にしない。依存・認証・権限を増やす必要がある場合は具体的な必要範囲を確認する。
- 毎回の新規担当から再参照でき、処理中も主会話を進められ、後着返答を使えることを確認。記憶参照・通常会話・Discord本文／画像・VC操作と終了処理を横断レビュー。
- 成果: `wave3-completion.md`、`local-task-experiment.md`、`human-gate.md`、`reviews/local-task-sessions/wave3-review.md`。

## 4. 内部確認と受け渡し

内部検証はUser Gateと分け、実装と実際の境界に見合う試験を行う。

- 共通層を使う記憶参照とローカル小タスクの両方で、主会話を占有せず、依頼ごとに新session。依頼・場・ロールと結果の対応、失敗・取消し・終了中の扱い。
- 原本や作業領域が別タスク終了／VC離脱／チャットの通知キャッシュ更新で失われない。旧受信先からの遅延入力を新着扱いしない。
- 通常の完了、失敗、明示中断で使用中の資源を削除しない。終了時に発話完了を待って詰まらない。永続記憶と場領域を混同しない。
- 資料／結果だけが増えた場合の最終保存、90秒で抜けない待機、writerが参照できる期間、保存後の後始末。
- 合成資料以外の実GM資料やユーザー会話を勝手に試験入力に使わない。実Discordへ無断投稿・参加して他者を巻き込まない。
- 最終の関連回帰と既存必須チェック、通常 `npm run cockpit --prefix apps/soul/agent` の隔離起動で確認。Player変更がなければ再ビルドは不要。通常起動から必要な道具が使えることまで確認。
- 実モデルの未実証、認証期限、外部サービス不通等を成功に混ぜず報告。機械的な代替検証で本人の実会話確認を代行しない。
- human-gateに実際の資料投稿・依頼・処理中の会話・再確認・VC退出と再参加・場終了の操作をまとめる。強制終了と回復の扱いも記す。

## 5. オーケストレーション・所有権

- root → 単一Orch-Sylph → 各WaveのGnome／独立Review-Sylph。全てGPT-6.1 Sol、fresh contextでの明示指定。共有のcockpit/server/fireを複数担当が同時編集しない。3 Waveを逐次実行する。
- 今回は通常構成として、各Waveでbasis・実差分・テスト・実行証拠を独立に確認し、最終Waveで全体の接続も確認。修正はGnomeへ、各Wave最大5ループ。
- Orch-Sylph自身は実装担当ではない。source implementation は必ず別コンテキストの Gnome に委譲し、レビューは必ず別コンテキストの Review-Sylph に委譲すること。これを分離できない場合は実装せず escalate / blocked として報告すること。
- rootは本計画・map・ユーザー判断を所有。Orchはbasis/完了/実験/本人手順、Gnomeはsource/tests/必要な道具、Review-Sylphはreviewを所有する。各子へUser Gate全文と必要basisを渡す。
- 全担当は共有workspaceにいる。前段の未コミット差分や他者の編集を戻さない。実装起動時にはcommit/merge/pushの依頼なし。完了後にユーザーがcommitを承認（merge/pushは未依頼）。
- 各Waveの独立合格をrootへ報告して、合意内なら次Waveへ自律継続する。新しい製品判断や権限変更等が必要なら具体的な差分をrootへ返す。正常な子をtimeoutで中断せず待機する。
