# 発話モーションの演技一覧をDecisions APIで再利用する

2026-11-28。作業ブランチは `codex/sentence-motion-catalog-cache`。実装・独立レビュー・実APIでの確認を1 Waveで行う。

## 採用判断

11/24・25の配信から選んだ10文を同じ演技一覧で判定したところ、共通の3,844トークンを初回に書き込み、後続9回すべてで読み取れた。初回を含むモーション判定の費用は実験時の現行方式から約38%減った。階層判定との別の比較では、最初の文を除く9文で、階層化した方が一括判定より約10%高かった。配信者は自然な仕草の選択差を許容し、今回は一覧をキャッシュした一括判定を採用した。

## Wave 1　毎文の演技と注意先を一回で選ぶ

- 本番が読み込む演技定義から、選択値と説明を安定した順序で並べる。共有入力の先頭に置き、一覧の末尾に30分の明示キャッシュ境界を置く。候補の追加・削除や説明の変更は、次回の起動で一覧とその内容に基づくキーに反映する。
- 後続の入力には、その文、直前の会話、同じ応答の先行文を渡す。質問には全候補の選択値を渡し、演技（該当なしを含む）と注意先を同じ一回のリクエストで判定する。対象別の再生判断と、音声が判定を待たずに進む経路を維持する。
- 共通のDecisions送信処理で、毎文モーションだけがこの形式を利用する。「今しゃべるか」やコメント判定など既存の呼び出しは従来の形式を扱えるようにする。

## 体制と完了の判断

Orch-SylphがGnomeに実装・回帰テストを依頼し、独立したReview-Sylphが合意・差分・検証結果を照合する。修正が生じた箇所は再確認する。

1. 固定部分が異なる台詞でも一致し、演技定義の更新で変わること、動的な会話本文が境界の後にあることを確認する。既存の判定利用者と音声経路は関連する回帰テストで確かめる。
2. 製品と同じ判定関数・送信経路で、配布中の演技一覧と異なる架空の二文を実APIに送る。初回の書き込みと後続の読み取りをAPIが返すusageで観測し、各文の演技・注意先と再生判断を記録する。検証では私的な会話や実際の場を使う必要はない。
3. 結果と制約をレビュー記録に残す。長時間配信での請求額は運用での観察事項とする。

## 結果

2026-11-28にWaveを完了した。製品の毎文判定から架空の二文を実APIに送り、初回に3,938トークンを書き込み、二文目に同数を読み取った。それぞれの対象に対応するクリップの再生要求まで確認した。最終関連テスト309件が成功し、独立レビューに合格した。[実測値と確認範囲](../reviews/sentence-motion-catalog-cache.md)
