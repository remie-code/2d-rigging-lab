# Soul全体の責務とディレクトリを整理する

2026-11-19。起点は master の `6c6ba68c`、作業ブランチは `codex/soul-structure-refactor`。全5 Waveと実配信・Discord通話の本人確認が完了した。

## 到達点

未来の開発者が「この挙動を変えたい」とき、名前と配置を手掛かりに本番の変更先と影響する体験へ辿れるようにする。Cockpitの起動、HTTP・画面などの操作入口、場の状態と寿命、各機能の実装の責務を明らかにする。閉場時に何を待ち、何を保存し、いつ資料を解放するかを一か所から順に読めることを重視する。既存の自然な境界は採用し、具体的なフォルダ名と物理配置は実物から決める。

## 全Waveに引き継ぐ合意

- **配信の相方**。普段のCockpitから開場し、配信者のマイク、ゲームの窓、明示したYouTubeコメント元を使用する。発話判断、手動・自発・割り込み・KILL、声の出力、体を使うロールの口パク・表情・モーションを保持する。閉場後に次の場へ古い判定やコメントを持ち込まない。[配信の体験](../../architecture/stream-restructure.md)
- **Discordの参加者**。Cockpit、Discord側のVC操作、Codexからの開閉場を保つ。複数話者、音声の送り先、権限に従うチャット・画像・資料、任意の見る窓を扱う。VCのみ退出・再参加したときは同じ場が続く。[Discordの体験](../../architecture/discord-mode.md)・[リモート開閉場](../waves/discord-remote-venue/wave2-operation.md)
- **場・記憶・小タスク**。ロール記憶の読み出し中や場の資料処理中にも会話が続く。正規閉場では受付済みの仕事を待ち、結果と会話を記憶に渡し、保存結果・必要な整理を取り扱ってから場の資源を解放する。通常閉場での二重保存防止と、リモート閉場での確定済み段の再実行防止・失敗後の再試行・結果不明時の保留を保つ。手動Cockpitと都度起動したCockpitのプロセス寿命の違いも保つ。
- **運用・互換**。既存の名前で起動でき、モデル・エンジン・ロール・設定・記憶Git・モーション資産・計測記録を従来の位置と形式で扱えること。通常の外部サービス、身体の有無や設定による違い、状態・警告・ログを維持する。Soulの独立npmと器との契約を守り、器側が起動するreference-driverも棚卸しに含める。[Soulの境界](../../../../apps/soul/README.md)
- **開発用記憶の隔離**。試験に使うロールと実際に解決された保存先を開場前に確認する。隔離したルートとテスト用ロールで正規の保存処理を通し、その記憶が書かれたことを確認する。チャッピー本人の記憶は、試験前後のHEADと作業状態を読み取りで照合する。本人の記憶・設定・実サービスに開発用の会話を流さない。
- **ゲート**。どのWaveの完了時も普段どおりに起動・会話・閉場できる状態にする。開発側が両方の体験を隔離して検証し、実サービス・実装・テスト代替の範囲を完了報告に明記する。本人確認は全Wave後の一度だけ。ユーザーが実際に配信の相方として使い、Discordで通話し、違和感が出た場面を一緒に確認する。

## Waveと依存

| Wave | 成果と担当 | 次に進む条件 |
|---|---|---|
| 1　現状と基準 | 配信とDiscordを別々の視点で本番入口から閉場まで追う。共通の会話・記憶・小タスク、身体と器、設定・ログ・保存先・運用入口・外部呼出元も含め、Soul全体を維持／移動／境界を後で決める領域に整理する。 | 現状の全回帰、両体験の開場・会話・閉場、テスト用記憶の保存と本人記憶の保護を確認。検証の穴に限って回帰テストを追加する。移動候補ごとに本番呼出元・相対パス・守るテスト・次の担当を記す。 |
| 2　個々の機能 | Wave 1の結果に基づき、Cockpitが引き受けている会話判断、記憶、担当セッション、音声・身体・モデル設定などの実装を、後から探せる所有先に置く。依存の独立した領域は並列に進める。 | 本番の組み立てを通して両体験が動く。既存データ、モデル選択、思い出し・資料処理中の会話、配信の身体経路、Discordの音声入出力を確認。 |
| 3　場の状態と寿命 | 状態の持ち主と共通開閉手順を定め、配信とDiscordの体験固有の処理を結ぶ。開始失敗の巻き戻し、古い世代の処理、同時操作、VC退出、通常閉場とリモート閉場を含む。 | 両体験の正常終了と失敗・再試行を検証。重複保存、早すぎる資料解放、処理中の結果の取り違えを防ぎ、閉場の手順を一続きに辿れる。 |
| 4　起動・操作・表示 | 起動スクリプト、本番実装の組み立て、HTTP受付、状態の配信・画面の境界を整理する。既存CLIやブラウザの操作から本番の同じ機能に到達させる。残った巨大ファイルを責務で再点検する。 | 通常起動、端末からの起動、Discordリモート操作、操作状態・計測・警告を検証。旧ソース本文を照合するテストは元々検出していた本番の配線不良を新構造でも検出できるようにする。 |
| 5　全体回帰と可読性 | 実装に関わっていないシルフが下記の問いを最初の入口から辿る。迷った場所を記録し、必要なら配置・命名・実装を直して再確認する。現在の構造を案内する地図を実装と照合する。 | Soul全回帰、器との境界、reference-driver、配信・Discord両方の隔離運用と記憶保護を確認。独立レビュー後に最後の本人確認へ渡す。 |

可読性の問いは (1) 配信中に発話と重なったYouTubeコメントの扱いをどこで変え、Discordへの影響をどう見分けるか、(2) VCを抜けて戻った際に何が残り、閉場とどこで分かれるか、(3) 資料を読む途中に閉場しても結果を保存後に片付けることをどこで確認できるか。担当者は初見の探索経路を残す。

## 体制と記録

ウンディーネが合意・依存・ゲートを保持する。Orch-Sylphが領域ごとの担当と結線担当を明示し、各Waveの実装をGnomeに、検証と合否を別コンテキストのReview-Sylphに委譲する。同時実装中の `cockpit.mjs` と `cockpit-server.mjs` は各ファイル一担当に固定する。Wave 3の状態遷移・閉場順は一担当が所有し、配信・Discord双方の観点でレビューする。各合格を確認して依存するWaveに進む。利用体験や合格条件を変える判断が生じた場合はウンディーネに戻す。

各Waveの完了記録は `implementation/waves/soul-structure-refactor/`、独立判定は `implementation/reviews/soul-structure-refactor/` に置く。実行条件、結果、残課題と裁量判断を残し、ここから実績へリンクする。基準となる規約は[ファイル構成](../../../development_convention/source-file-organization-policy.md)を参照。
