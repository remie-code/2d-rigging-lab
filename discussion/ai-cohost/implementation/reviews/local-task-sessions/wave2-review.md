# Wave 2 独立レビュー

修正1の再レビューで Wave 2 の内部検証は合格。承認範囲は [Wave 2 計画](../../orchestration/local-task-sessions-wave-plan.md) と [実装契約](../../waves/local-task-sessions/basis.md) を参照。

## 修正1の確認

- 初回の実装では Windows の `TEMP` と `TMP` が相対値のとき資料の参照も相対になった。`venue-task-resources.mjs` の根は修正1で `resolve(tmpdir(), …)` によって絶対化された。相対の一時フォルダを設定する新規試験で、資料と担当の cwd が絶対パスになること、別 cwd の担当が原本を読み取れること、writer に同じ参照を渡すこと、閉場で原本を削除することを確認した。

## 実装の確認

- 場が資料 ID と原本ファイルを所有し、依頼ごとに個別の作業ディレクトリを作る。同じ場の後続依頼は原本を参照できる。終了時の削除は自身が生成した根へ向かう。永続記憶の場所は従来のロール別に管理される。前段の Discord 受信・VC 操作・資料キャッシュ差分と Wave 1 の共通セッション・recall 切替は既存の作業ツリー差分。Discord 添付を場へ接続し、実行環境の権限を実証する箇所は Wave 3。
- 通常 close と CLI の最初の Ctrl+C／EOF は同じ閉場手順へ進む。受付と recall の未配送指示を閉じ、主会話を畳む。実行中の recall と受理済みの待ち一件、受理済みの場のタスクを完了まで待つ。コールバックで拾った担当返答は発話配送を止めた後も writer の材料になる。
- recall の受付時に準備関数がロールの実行口、記憶の場所、担当 factory を取得する。待ち一件にも受付時点の設定が適用される。その後の依頼の準備はその時点の設定から行う。
- 保存要否には資料と返答も含まれる。書き出しの既存の指示と、何を残すかの判断は writer にあり、資料の絶対パスと返答を材料として追加する。書き出しとコミットの処理を待ち、必要な整理を完了してから場の資源を解放する。91 秒を進めた試験でも場は閉場中を保ち、次の場の開始は 409 になる。
- タスクまたは recall の共通 scope が dispose の終了未確認を報告すると場の領域を保持する。Codex の接続は終了通知が得られない場合にエラーを出し、writer もその dispose エラーを受けて危険なコミットを始めず保持を通知する。確定済みの実行失敗では閉場処理を経て領域を解放する。二度目の Ctrl+C は強制終了のため途中の領域を残す。EOF の重複は通常閉場を継続する。
