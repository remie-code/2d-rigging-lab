# C1 UX定義: 役割の骨格と扉

> Status: 振る舞い(扉・閉扉の作法・招待の木・不変条件)=Accepted(ユーザー合意 2026-07-10)。見せ方(§7)=Accepted(ユーザー合意 2026-07-10)。
> 位置づけ: 閉問題C1([../closed-problem-decomposition.md](../closed-problem-decomposition.md))のwave化前UX定義。C1の実装ゲート自体は起動引数のみで成立させ、玄関(ピッカー)の実装は後のUX磨きwaveに置く。

## 1. 前提

- 役割=起動時の明示的合成。実行時の `if (role===...)` 分岐は禁止(案(c)、[../../architecture/runtime-player-model-host-roles.md](../../architecture/runtime-player-model-host-roles.md))。
- **一体=一プロセス=一組の窓(Stage+Control)**。プロセス分離を採る理由はユーザー視点の重み付けによる: 「配信中に自分のモデルが絶対に死なないこと」は「起動が1クリック増えること」より重い(ユーザー合意 2026-07-10)。トラッキングホストはミッションクリティカル、自律ホストは変化の激しい新参者であり、後者の障害が前者に触れてはならない。
- 中核の整理: **対称なのは境界(プロセス独立)、非対称なのは間柄(招いた側と客)**。間柄は所作の層(閉扉ダイアログ)だけに宿り、ランタイムには決して染みない。
- 器はどちらが配信の主役かを知らない。「人間メイン+AIサポート」と「AIメイン+人間サポート」は器から見て同一(二体並走)であり、主従はOBSレイアウトと魂のペルソナにのみ存在する。

## 2. 開く: 三枚の扉と玄関

所作(どこをクリックするか)と境界(プロセスかウインドウか)は独立である。扉2は「ウインドウ追加」に見える所作で、裏では別プロセスを起動する。ユーザーは境界を意識しなくてよい。

| 扉 | 所作 | 実体 | 日常度 |
|---|---|---|---|
| 扉1「いつもの自分」 | 役割ショートカット | トラッキングホスト起動。AI無しでも従来配信として完結 | 毎回 |
| 扉2「相方を呼ぶ」 | 起動済みインスタンスのトレイ/メニュー | 自律ホストを別プロセスとしてspawn。配信の途中からでも呼べる | 二人配信のたび |
| 扉3「二人配信セット」 | 役割ショートカット | **扉1+扉2の一括実行**(トラッキングホストが起動時に自動で招く)。別ボタンではなく合成として定義する | 定着後の毎回 |
| 玄関(ピッカー) | 引数なし起動 | 三枚の扉を画面に並べる。ショートカット製造所+初回の教室 | 初回とショートカット喪失時のみ |

- **禁止(恒久)**: 引数なし起動をいずれかの役割へ暗黙に束ねない。引数なし=常に玄関。黙ってどれかの役割になると「役割=起動時の明示的合成」の背骨が崩れ、意図しないプロファイル生成と取り違えが始まる。
- 玄関には「この扉のショートカットを作る」を置く。初回に一度玄関を通り、自分の扉のショートカットを作ったら、以後日常では玄関を通らない。
- 自律ホスト単独の扉は一等地に置かない(玄関から辿れれば十分)。
- 招く所作は全インスタンスが同じUIとして持つ(一様性)。「自律ホストには呼ぶメニューを出さない」という制限は実行時role分岐そのものであり、置かない。したがって相方から更に相方を呼ぶことも機構上可能である(三人配信への拡張が機構レベルで既に成立する)。ただし**招くのは常に人間の所作**であり、操縦チャネルの契約にプロセス起動/終了の語彙は含めない。魂は仲間を増やせず、減らせない。

## 3. 閉じる: 作法

扉は閉じられる。開く所作だけ設計して閉じる所作を設計しないのは片手落ちである。

- 一体=一プロセスなので、**そのインスタンスのControl Windowを閉じる=その体が退場する**(既存のWave20事実「Control close=app quit」にそのまま乗る。Stage Windowの直接閉じは従来どおりFocus Stageで復旧可能な非退場操作)。自律ホストがトレイに残って裏で生き続ける中途半端はさせない。
- 扉1の逆=配信終了の通常操作。扉2の逆=「相方を帰す」(招いた側のトレイ/メニューから、または相方側の窓を直接閉じる)。扉3の逆=閉扉ダイアログ(§4)が自然にセットの畳みを兼ねるため、専用の「セットを畳む」ボタンは作らない。
- **去り際の演出はスコープ外**: 「相方が挨拶してから退場する」は魂が別れを言い終えたあとに人間が扉を閉じるという運用の問題。器が保証するのは「きれいに消えること」だけで、「美しく去ること」は魂と配信者の領分。器に演出ロジックを染み込ませない。

## 4. 招待の木と閉扉ダイアログ

規則は一文: **「招いた記憶は親から子への片方向・セッション限りで、意図的な閉扉のときだけ木を降り、死は決して降りない」**。

- 招待関係は木になる。各ノードは**自分が直接招いた子のプロセスハンドルだけ**を持つ。全体を見渡す台帳はどこにもない。記憶はセッション限りで、永続化しない。
- **閉扉ダイアログ**: 招いた客が生きている状態で自分を閉じようとしたとき、毎回聞く——「相方も帰すか？」[一緒に閉じる/相方は残す]。毎回でよい(配信終わりの一回であり、誤爆で相方だけ生き残る事故のほうが痛い。ユーザー合意 2026-07-10)。
- 「一緒に閉じる」→ 終了シグナルが木を降りる。親に畳まれる子は自分のダイアログを出さず、黙って自分の客へ同じシグナルを渡してから帰る(ダイアログの連鎖は起きない)。
- 「相方は残す」→ 客の部分木はそのまま生き続け、以後は独立した根になる。
- 招いていない客(自分のspawnでなく独立に起動されたインスタンス)には何も聞かない。非対称性は招待の有無に正確に紐づき、恣意的な特別扱いにならない。
- この結合が存在するのは**閉じる瞬間のUIとOSプロセスハンドルへの終了シグナルだけ**である。ランタイムに相手を監視する・合わせるコードは一行も生えない。

## 5. 不変条件(ランタイムは無条件に対称)

1. 実行時の相互関与ゼロ: フレーム、ポート、userData、生死のいずれも互いに触れない。
2. **クラッシュは決して連鎖しない**。親が落ちても客は生き続ける(配信中にトラッキングホストが落ちても相方は喋り続け、人間は自分だけ再起動できる)。招待の記憶は親の死とともに消え、孤児は独立インスタンスとして直接閉じればよい。
3. 閉じたあとOBSに死体を残さない: Browser Source接続断→固まった最終フレームではなく透明(無)を映す。
4. 「帰る」と「死ぬ」はOBSからは等価(接続断→透明)。これは欠陥ではなく安全側への倒れ方であり、C5「魂を殺してもキャラは息をしている」と同系譜。
5. userData/ポート分離は「役割ごと」ではなく**「インスタンスごと」**に切る(招待の木がN体同時を既に許すため。C1のゲートは二体のままでよい)。

## 6. C1実装ゲートとの対応

- C1のゲート「二インスタンスが別モデルを同時表示し、window-state/profileが混ざらない」に加え、本定義から機械検証可能なゲートが一つ増える: **「片方のプロセスをkillしても、もう片方のフレームが止まらない」**(不変条件2)。
- C1実装は起動引数(役割・プロファイル指定)のみで成立させる。引数の切り方は、将来の玄関・扉2・扉3がその引数を呼ぶ形と食い違わないように設計する(玄関・トレイ招待・閉扉ダイアログの実装自体は後続のUX磨きwave)。

## 7. 見せ方

前提として効く既存事実: **OBSはBrowser Source(loopbackサーバ)経由で映像を取り、窓そのものをキャプチャしない**。窓は配信に映らない操縦席であり、識別装飾を配信汚染の心配なしに置ける。

### 7.1 UI語彙(英語)

既存Runtime PlayerのUIは英語で統一されているため、画面上の語彙もそれに合わせる: `Tracking Host` / `Autonomous Host` / `Companion` / `Invite Companion` / `Dismiss Companion`。「扉」「玄関」「招待の木」は本ドキュメント側の概念名であり、UIには出さない。

### 7.2 役割の識別(バッジ=役割、インスタンス識別=モデル名相乗り)

- 何と何を見分けるか: Stage Window二枚はモデル自体が最大の識別子でありほぼ問題にならない。本丸は**瓜二つのControl Window二枚**(取り違えると相方のつもりで自分のLook Forwardを押す等の事故になる)と、**同一アイコンのトレイ二個**。
- Control WindowのHeader先頭に役割バッジ(`Tracking Host` / `Autonomous Host`)を置き、Headerの帯またはバッジにだけ役割ごとのアクセント色を敷く。**文字+色の二重**にする(咄嗟の判断で色の記憶は信用できず、視界の隅で効くのは色であるため)。
- ウインドウタイトルにも役割名を含める(既存のCopy Window Titleがそのまま区別可能なタイトルを配る)。
- 識別の単位は**役割**とし、インスタンス識別のための新機構は足さない。タイトルとHeaderに**ロード中のモデル名を今までどおり出す**ことで実質インスタンス識別を兼ねさせる(N体時代への備えは既存表示への相乗りで足りる)。

### 7.3 Companionカード(扉2の家、Overviewページ)

「相方を呼ぶ」の一等地は**OverviewページのCompanionカード**とする。Headerには置かない(Headerの既存規律は「Live中に頻繁に押す操作だけ」であり、招待は配信につき一回の設営所作)。

```text
+--------------------------------------------+
|  Companion                                 |
|                                            |
|  No companion invited.                     |
|  [ Invite Companion ]                      |
+--------------------------------------------+

招待後:

+--------------------------------------------+
|  Companion                                 |
|                                            |
|  Autonomous Host — <model name>   running  |
|  [ Dismiss Companion ]                     |
+--------------------------------------------+
```

- このカードは§4の招待の記憶(自分が直接招いた子、セッション限り・片方向)の**そのままのUI表現**である。設計とUIが同じ形をとる。
- `Dismiss Companion` が扉2の逆(相方を帰す)の家になる。招いていないときはDismissを出さない(カードの状態がそのまま関係の有無を示す)。
- 一様性の帰結として自律ホストにも同じカードが出る(そこから三体目を招ける)。特別扱いのコードは書かない。
- アプリケーションメニューとトレイメニューに `Invite Companion` を鏡写しで置く。

### 7.4 トレイ(脇役)

トレイは命綱(click-through回復)+近道であり、唯一の入口にしない(日常の所作を忘れられる場所に置かない。ユーザー合意 2026-07-10)。

- アイコンに役割色のドットを重ねる。
- ツールチップを「Runtime Player — <役割> / <モデル名>」にする。
- メニューはControl Window側の鏡写し(`Invite Companion` を含む)。

### 7.5 閉扉ダイアログ

出る条件は一つ: **自分が直接招いた客が生きている状態で、Control Windowを閉じた(=quit)とき**。客がいなければ今までどおり黙って終了する(確認を増やさない)。

```text
+----------------------------------------------------------+
|  Close Runtime Player                                     |
|                                                          |
|  This instance invited a companion that is still         |
|  running (Autonomous Host — <model name>).               |
|                                                          |
|  Close the companion too?                                |
|                                                          |
|        [ Close Both ]  [ Leave It Running ]  [ Cancel ]  |
+----------------------------------------------------------+
```

- **既定(Enter)= Close Both**。配信終わりの一括畳みが最頻ケースであり、痛い事故は「相方だけ生き残る」なので安全側=両方閉じる。Escape=Cancel。
- Cancelは誤クリック保護を兼ねる。客が複数なら文言が数になるだけ(`invited 2 companions`)。伝播規則は§4のとおり。

### 7.6 玄関

引数なし起動で出る一枚きりの小さい窓。選んだら玄関は閉じてその合成が立ち上がる。

```text
+------------------------------------------------------------+
|  Runtime Player                                             |
|                                                             |
|  +-------------------+  +-------------------+               |
|  |  Tracking Host    |  |  Duo Set          |               |
|  |  Stream as        |  |  Tracking Host +  |               |
|  |  yourself         |  |  Companion        |               |
|  |  [ Launch ]       |  |  [ Launch ]       |               |
|  |  Create shortcut  |  |  Create shortcut  |               |
|  +-------------------+  +-------------------+               |
|                                                             |
|  Autonomous Host only...            (小さく、隅に)          |
+------------------------------------------------------------+
```

- 大きい扉は二枚だけ(いつもの自分/二人セット)。自律ホスト単独は隅の小さいリンク(§2: 一等地に置かない)。
- 各扉の `Create shortcut` で玄関がショートカット製造所を兼ねる。
- **意図的に置かないもの: 「次からこれにする/今後表示しない」チェックボックス**。置いた瞬間「引数なし=役割への暗黙束縛の禁止(恒久)」を破る。玄関は恒久に玄関である。
