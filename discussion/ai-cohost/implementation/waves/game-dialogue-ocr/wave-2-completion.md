# 黙読したゲームの台詞を次の会話に渡す

配信の場を開くと、指定されたゲームの窓から確定した文字のまとまりが Cockpit の「ゲーム画面」に並ぶ。次に通常の発話機会が来ると、前回から進んだ分を会話入力に載せる。「推論に使った範囲」の線は、その回に実際に渡した行に引く。[Wave の計画](../../orchestration/game-dialogue-ocr-wave-plan.md) · [体験の合意](../../../game-dialogue/screen-text-blocks.md) · [独立レビュー合格](../../reviews/game-dialogue-ocr/wave-2-review.md)

## 実装

- 定期取得は配信の開閉、窓の指定、画面文字起こしの設定と連動する。対象の切り替えや閉場では、実行中の取得と認識を中止して保留を捨てる。対象の消失、最小化、同名窓への置き換わりは次の撮影で検知する。処理中に来た取得周期は見送る。従来の一枚撮影は別の経路で動く。[周期の変更方法](../../../../../apps/soul/README.md)
- 2026-11-22 に取得周期の既定値を1,000 msへ変更した。下記の Windows 計測は環境変数で100 msと3,000 msを指定したときの結果。
- 確定順と表示順を別に持つ。Cockpit の本文は確定順に並び、時刻欄で表示開始・最終観測・確定時刻を確認できる。発話の入力には表示順と表示期間も添える。ゲーム画面の確定は、新しい発話や動作意図の判定を起こさない。
- 会話入力の既定は直近5分・4,000文字。場ごとの `apps/soul/agent/session-usage/` の JSONL で `type: "fire"` の `conversationWindow` を見ると、前回の投入からの経過 `pendingElapsedMs`、投入前の整形文字数 `pendingChars`、実際に渡した `windowSeqs`、一度も渡らず落ちたゲーム行の連番・表示開始時刻・理由 `droppedUnsentGame` を追える。理由は `time` または `chars`。この記録は本文を持たない。同じ場でスレッドが替わっても、すでに渡ったゲーム行や後続に追い越されたゲーム行は戻らない。

## Windows で確認したこと

最終差分を一時コピーに置き、通常の `node scripts/cockpit.mjs` から起動。実デスクトップ上の自前 WinForms ウィンドウで台詞を送り、Windows の実キャプチャ・WinRT OCR と Chrome を通した。設定、ロール、記憶、ブラウザのプロファイルは一時コピーに隔離し、マイク入力、推論、記憶書き出し役は模擬した。

| `STREAM_GAME_OCR_INTERVAL_MS` | 実測した WinRT OCR の開始間隔 | 同時実行の最大 |
| --- | --- | --- |
| 100 ms | 1,744 / 1,473 / 1,421 / 1,427 ms | 1 |
| 3,000 ms | 2,822 / 3,014 / 3,010 / 3,085 ms | 1 |

- 「星の灯りを探してください。」が確定し、Chrome の「ゲーム画面」行、2 px の「推論に使った範囲」の線、`fireAsk.windowSeqs: [0]`、localhost の推論入力が一致した。画面の確定だけでの推論呼び出しは0件。閉場で実行中の OCR を取り消し、待機しても追加実行は0件。再開後に前の台詞は現れなかった。
- OCR 実行中に通常の手動発話と画像付き手動発話を受理した。追加試行の模擬 Aivis と模擬プレーヤーでは、発話までの計測が通常33 ms、画像付き157 ms（一枚撮影148 ms）。相方行「確認しました。」も実 Cockpit に出た。
- 二値とも実行後の使用ログに `pendingChars: 82`、`windowSeqs: [0]`、`droppedUnsentGame: []` を確認した。経過は687 msと2,202 ms。閉場時に模擬の記憶書き出し役が一時ロールの記憶ファイルへ台詞を書いた。
- 自動テストでは、他方の上限に達せず時間で落ちる場合と、文字数で落ちる場合をそれぞれ入力・使用ログと照合した。頭のスレッドを再作成しても文字数で落ちた古い台詞が復活せず、発話演出の判定にゲーム本文が入らないことも確認した。
- 独立レビューは指摘2件の修正後に合格。レビュー担当が対象316テストと隔離 localhost の Cockpit HTTP 試験1件を実行し、全件が通過した。
- 最終差分の `npm.cmd test --prefix apps/soul/agent -- --test-reporter=spec` は2,628件すべて通過。ループバック接続に許可が必要なため承認後に実行した。`git diff --check` も通過。

再実行時は Windows の `%LOCALAPPDATA%\Temp` に残っている一時コピーを使う。最終計測は `game-ocr-smoke-da80ac87a39242a192df8364a12570c9`（100 ms）と `game-ocr-smoke-db4143229f4d4c2e94413eee05bc4c5b`（3,000 ms）、発話確認は `game-ocr-smoke-8732334def5b407abff2ca4420ebde53`。既存の `ocr.jsonl` と `browser` は別名で保管し、`card.txt` を最初の台詞に戻す。`SMOKE_REAL_MODULES` に作業ツリーの `apps/soul/agent` の絶対パスを設定し、一時コピーから `powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File .\fixture.ps1` で合成窓を表示した状態で、同じコピーから `node smoke.mjs 100` または `node smoke.mjs 3000` を実行する。

実ゲームで黙読した話を普段の相方が追えるか、実マイクと物理音声で期待どおり応答するかは、次の配信者確認で見る。

## 最後に配信者が確かめること

1. Windows でいつもの Cockpit を起動する。「配信の準備」で「ゲームの窓」を選び、「ゲーム画面の文字起こし」をオンにして「配信を始める」。Haas-ja を使う場合は開始前に選択しておき、場に入った後の方式表示も Haas-ja になっていることを確認する。
2. 相方が話している間に、ゲームで名前と台詞を含むページを数枚黙読する。各ページをまず数秒表示し、最後に話題にする台詞のページから次へ送る。「会話」欄に消えた台詞が「ゲーム画面」として、名前と本文の改行を保って並ぶことを確認する。
3. 台詞を読み上げず、消えたページについてひと言話しかける。返答にそのページで得た情報が反映され、Cockpit の「推論に使った範囲」の線が、その回に渡ったゲーム行を囲むことを確認する。そのまま同じページの内容を話題にしてよい。対象の台詞行が再追加されず、線はその回に新たに渡った行に更新される。
4. 話題にした台詞が線に入らなければ、その返答に対応する `conversationWindow` を確認する。時間か文字数で落ちた場合は、`droppedUnsentGame` の表示開始時刻を録画や確認時の時刻と照らし合わせる。配信の場を閉じて終了する。
