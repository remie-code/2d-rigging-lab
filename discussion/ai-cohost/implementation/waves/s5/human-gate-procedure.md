> 実マイク・実器接続・実スピーカー再生を伴うため Gnome / エージェントは実行しない＝規律）。

## なぜ人間がやるのか（配線・実出現 ≠ 実機の見え方・特に「白紙で成功扱い」の地雷）

機械ゲート（魂の全テスト緑・Domain A/B/C の fake 縦貫通・`scripts/observe-vision.mjs` の実 SDK
5 ask）は「メモ帳窓を実キャプチャ → 画像込みで実射 → 返事が画面内容に言及する」までを証明済み
（[../../../experiments/s5-vision.md](../../../experiments/s5-vision.md)）。残る未検証は
**実ゲーム窓での見え方**——棚卸し §3-1 の重大な地雷「GDI BitBlt 取得の経路では DirectComposition
系の描画内容が写らず、Win11 新メモ帳ですら真っ白で『成功』扱いになった」の教訓どおり、**PrintWindow
（本実装の採用経路）が実ゲーム窓（GPU スワップチェーン描画）でも composited 内容を撮れるかは
実ゲームで試すまで分からない**。「エラーにならず撮れたのに中身が真っ黒/透明」という失敗は機械
テストでは検出できない（domain-a.md §2 注記・§7 質問 2）。これは人間の目でしか判定できない。

## 1〜4. 全器官起動（S3/S4 手順書と同一）

[../s4/human-gate-procedure.md](../s4/human-gate-procedure.md) の **§1〜§4 をそのまま実施**する:

1. **AivisSpeech を起動**（`http://127.0.0.1:10101`）。
2. **自律ホスト（器）を起動し Channel を開く**（`Open Channel` → Endpoint URL を控える）。
3. **操縦席を fire 有効で起動**:
   ```
   npm run cockpit --prefix apps/soul/agent -- --channel "ws://127.0.0.1:<port>/channel?token=<token>"
   ```
4. **ブラウザで開き、マイクを選んで Start**（ヘッダが `Listening`・`whisper: up` / `ffmpeg: up`）。

（S5 で新規に増える依存・追加コマンドは無い。器コード・契約・依存は完全不変。）

## 5. ゲームを起動する（S5 の要・ここが新規）

普段配信で映すゲームを 1 本、通常どおり起動してプレイ可能な状態にする（フルスクリーンでも
ウインドウモードでも可）。**最小化しない**（§9 で最小化時の挙動確認は別途行う）。

## 6. 操縦席で対象ウインドウを選ぶ

1. 操縦席の「Vision target」セクションで **Refresh windows**（一覧取得）ボタンを押す。
2. `<select>` に起動中のウインドウ一覧（`{pid, processName, title}` のタイトル）が表示されることを
   確認する。**ゲームのウインドウタイトルが一覧に現れるか**を確認する（Win32 の
   `MainWindowTitle` 制約——プロセスごと主窓 1 個のみ。マルチウインドウ構成のゲームは取りこぼす
   可能性がある・domain-a.md §3「window-list の制約」）。
3. ゲームのタイトルを選択し **Set target** で確定する（`cockpit-settings.local.json` に永続化
   される・次回起動でも復元される）。

## 7. 視覚発火（S5 の要）

**Fire (vision) ボタン**を押す（または AHK が導入済みなら `Ctrl+Alt+G`）。

- Timeline に「見た」マーカー行 + **縮小サムネ画像**が表示される。
- 続いて通常 Fire と同様に `soul: thinking` → soul 行（返事のテキスト）→ `soul: idle`。
- 返事の声が鳴り、器の口が動く（S3 ゲートの再演）。

## 8. 合格判定 — 「画面に映っているものに言及した返事が返る」

以下 2 点を確認する:

1. **サムネに中身が実際に写っているか**（操縦席の「見た」マーカー行のサムネ画像を見る）。
   - **白紙/真っ黒/透明であれば不合格**——これが棚卸し §3-1・§4-1 で警告されていた「PrintWindow が
     実ゲーム窓の GPU スワップチェーン描画を撮れない」地雷が実際に踏まれたケース。その場合は
     `fireVisionError` 診断は出ない（キャプチャ自体は「成功」扱いのまま中身だけが空白になる
     可能性がある・domain-a.md §2 の白紙判定の限界）ため、**目視でしか気づけない**。踏んだ場合は
     ゲームタイトル・ジャンル（2D/3D・使用エンジンが分かれば）・OS/GPU 情報を記録して
     [s5-followup.md](s5-followup.md) へ追記する（gdigrab 等の代替経路検討の判断材料）。
2. **返事の内容が画面に映っているものに言及しているか**（サムネが正常に写っていた場合）。
   ゲーム画面に映っている具体的な要素（キャラクター・UI・スコア・状況等）に、返事が触れているかを
   見る。[s5-vision.md](../../../experiments/s5-vision.md) の機械観測（メモ帳の特徴的なマーカー
   本文に言及した）と同種の判定を、実ゲーム窓で確認する。

**あわせて確認**: 通常 Fire ボタン（画像なし）を 1 回押し、S3/S4 と同様に会話ログの直近窓だけを
注入した返事が返る（従来どおり無退行）ことを一言確認する。

これが一目一聴で成り立てば **S5 人間ゲート合格**。

### 任意（余裕があれば）: 画像がディスクに残らないことの目視確認

機械ゲート「画像のディスク非書き込み」はコード構造上の担保（サーバ側にファイル書き込み経路が
無い・§4 domain-c.md）に留まっており、ブラウザ側の実挙動は machine test の対象外（domain-c.md
§7 質問 3）。余裕があれば、視覚発火の直後にブラウザの DevTools（Network / Application タブ）で
サムネ画像がディスク相当の永続化先（ダウンロード・localStorage 等）に残っていないことを一度
確認しておくと、この構造的担保が実機でも裏取りされる。

## 9. うまくいかないときの切り分け（S5 固有）

まず S3/S4 手順書の切り分け表（起動拒否・`fire disabled`・`ears-not-running`・声/口の不一致）を
参照する。S5 固有の症状:

| 症状 | 見るところ |
|------|-----------|
| サムネが白紙/真っ黒/透明 | §8-1 の地雷。ゲームのタイトル・エンジンを記録し followup へ。実ゲーム窓での composited 撮影が PrintWindow でも失敗するケース（domain-a.md §7 質問 2 の実確認） |
| ゴースト行 `(vision fire: no-target — ...)` | 対象ウインドウが未設定。§6 で Set target したか確認 |
| ゴースト行 `(vision fire: notFound — ...)` | 対象ウインドウが閉じられた/タイトルが変わった。Refresh windows で選び直す |
| ゴースト行 `(vision fire: minimized — ...)` | 対象ウインドウが最小化されている。復元してから再度 Fire（本実装は IsIconic を PrintWindow の前に判定して弾く設計・domain-a.md §7 質問 1 の実確認材料。復元後は正常に撮れるか確認する） |
| ゴースト行 `(vision fire: failed — ...)` | PrintWindow 自体が失敗（GDI 例外等）。頻発する場合は対象アプリ名を記録して followup へ |
| ゴースト行 `(vision fire: timeout — ...)` | PowerShell 側がタイムアウト（既定 5000ms）。頻発する場合は followup へ（タイムアウト値の見直し） |
| ウインドウ一覧にゲームが出ない | Win32 `MainWindowTitle` 制約（プロセスごと主窓 1 個）。マルチウインドウ構成のゲームは取りこぼす可能性（domain-a.md §3） |
| 対象を被覆した状態で視覚発火 | サムネに「被覆元だけが写り覆いは写らない」ことを確認する（棚卸し §3-1: DWM リダイレクトサーフェス経由なら覆いは写らない設計上の期待。PrintWindow でも同様かは今回の確認材料） |

## 10. 終了

操縦席のターミナルで **Ctrl+C**（S3/S4 と同一・全器官が畳まれて終了）。ゲームも通常どおり終了する。
