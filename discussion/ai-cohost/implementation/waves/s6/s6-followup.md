## 1. barge-in の実機体感（人間ゲート待ち・最優先の梯子）

wave-plan §1 人間ゲート①の本体。[human-gate-procedure.md](human-gate-procedure.md) §6 に判定手順を
用意した。**この wave の機械ゲート・実 SDK 観測（s6-conversation.md）は barge-in の「機構が動くこと」
（切断点算出・soul 追記・sendSet 送出）までを実射で確認したが、「体感レイテンシ」（実マイク発話開始
→実際に声が止まるまでの時間）と「口閉じの見え方（release が自然か）」は実マイク・実器・実 WinRT
MediaPlayer が要るため未検証のまま**。

- **口閉じ release の実機挙動**（domain-b.md §8-5・design レビュー確認済み）: mouth-open へ
  value=0・ttl 400ms を送ると器は speech タイムラインを releaseMs（既定 400ms）かけて基底へ強制
  release する（inventory §2・既存意味論）。実際の口の閉じ方（release が自然か・声停止と口閉じの
  体感ズレ）は実器での目視が要る。人間ゲート①で確認する。
- **機械弁窓（200ms）の体感チューニング**（domain-b.md §8-2）: 短いほど barge-in は速いが瞬間
  スパイクを拾いやすい。人間ゲートの体感で v0 定数を直す。
- **STOP の完了通知タイミング**（domain-a.md §7-2）: `stop()` は送出のみで、実際の停止確定は
  `STOPPED` 行到達時点。barge-in の「止めた」確定を `STOPPED` 待ちにするかは Domain B が現状の
  `isPlaying()` フラグで足りると判断した設計のまま。実機で体感の遅れが問題になったら見直す。

## 2. 呼びかけ照合の実人声拡張（人間ゲート待ち）

- **転写揺れの実マイク採取**（inventory §4-2・fire-scheduler.mjs コメント）: 照合集合 v0
  （`コーディ`/`コーディー`/`コーティ`/`コーティー`）は AivisSpeech 合成音の実測のみで、実マイク・
  実人声の転写揺れは未採取（実マイク規律）。人間ゲート②で「呼びかけがうまく拾われるか」を確認し、
  もし別の揺れが観測されたら `NAME_VARIANTS_V0`（データ定数）を拡張する。
- **既知の誤爆「コーディネート」**（domain-c.md §8-2・spec/design レビューで受容確認済み）:
  名前が Cody=コーディ由来ゆえ「コーディネート」を部分一致で拾う（call は確率の希釈が無く毎回撃つ）。
  v0 は受容（誤爆は免罪符）。人間ゲート②③で実害の頻度を観測してから緊縮（語境界・前後文脈）を検討。
- **転写側の用語登録=Whisper initial promptによる語彙バイアス**（ユーザー要望 2026-07-14・「あとでやろう」裁定）:
  受け側（揺れ集合照合）に加え、**転写そのものの精度を上げる**正攻法。Whisper系はデコード前のprompt文字列で
  固有名詞の綴りを誘導できる（OpenAI公式もこの用途を案内）。うちらは発話セグメント毎に1リクエストなので、
  whisper-clientにpromptフィールドを足せば全発話が常にバイアスを受ける（耳の器官の小変更）。
  **注意**: バイアスは確率的・保証でない。副作用=言っていない語の幻聴混入（プロンプト語が転写に紛れる
  →呼びかけ誤発火の増加リスク）。**段取り**: UI改定wave閉鎖後の小さい閉問題として、
  ①棚卸し=vendor whisper-server v1.9.1がリクエストでpromptを受けるか実機確認
  ②S6棚卸しの合成音ハーネス（AivisSpeech×話速/ピッチ/抑揚）を再利用し、promptあり/なしで
  「名前入り音声の正答率」と「名前なし音声への幻聴混入率」を両面実測 ③数字で採否。
  成立すれば受け側照合との挟み撃ちで呼びかけ精度が両側から締まる。

## 3. 自発発火の定数チューニング（人間ゲート待ち・v0 コード内定数のまま）

wave-plan 裁定8「ツマミは作らない・人間ゲートの体感で直す」の対象。以下はすべて
`src/mind/fire-scheduler.mjs` の export 定数（コード側を直接編集して調整する）:

| 定数 | 現在値 | 調整観点（人間ゲート③④で体感を見る） |
|---|---|---|
| `TURN_END_SILENCE_MS` | 2000 | 短いと ASR warm レイテンシ内に撃ち、直前発話が会話ログに載る前に反応しうる |
| `TURN_END_PROBABILITY` | 0.35 | 高すぎると相槌がうるさい・低すぎると反応が薄い |
| `TURN_END_REFRACTORY_MS` | 8000 | 立て続けの相槌の間隔 |
| `SILENCE_BASE_MS` / `SILENCE_JITTER_MS` | 45000 / 30000 | 「間が持たなくなる手前」の目安。配信のテンポで変わりうる |
| `SILENCE_REFRACTORY_MS` | 90000 | 沈黙発火の連発防止。視覚発火のコスト（usage 計器で見える）と体感のバランス |
| `SILENCE_BUDGET_V0` | 6 | セッション内の沈黙発火回数上限。長時間配信では枯渇して止まる（§4 参照） |
| `BARGE_IN_MIN_SPEECH_MS`（barge-in.mjs） | 200 | §1 参照 |

人間ゲート③④での複数回の体感試行と、実配信での運用フィードバックを踏まえて調整する。

## 4. silenceBudget のセッション使い捨てとの関係（design レビュー §8-8 の申し送り）

`silenceBudget`（既定6）は `createFireScheduler` インスタンスの生存期間内で単調減少し、リセット
手段が無い（`setEnabled` の再 ON でも戻らない・サーバ再起動でしか戻らない）。長時間配信では沈黙
発火が予算切れで止まる挙動になる（wave-plan §2「長回し（セッション使い捨て）はスコープ外」との
整合は取れているが、Domain D 以降で見落とされないよう明記しておく）。

- **梯子**: 実配信の長回し運用で「沈黙発火がある時点から起きなくなる」という体感が問題になったら、
  (a) セッション使い捨て（後述 §5）の一環として scheduler ごと差し替える、(b) 予算を時間ベースの
  リセット（例: N 時間ごとに回復）へ変える、のどちらかを検討する。

## 5. セッション使い捨て（長回し）の方向性（wave-plan §2 裁定10・スコープ外）

inventory §1 裁定10 の再確認: 会話の正本は転写バッファ側にあり、セッション差し替えは構造的に安い
（裏で温めて差し替え可能）という方向性のみ合意済み。**細部（差し替えタイミング・閾値・計器基準）は
実配信の問題駆動＝この wave のスコープ外**のまま。silenceBudget の枯渇（§4）もこの文脈に含まれる。

## 6. 実況長回しの計測（未実施・実配信の領分）

`experiments/s6-conversation.md` は 1 セッション・5 ask（数十秒〜1分程度の論理時間）の短い縦串観測
であり、実配信の長時間運用（数時間）での:
- usage の累積傾向（cache TTL 切れ後の再課金・S5 followup §2 で既に持ち越されている項目と同根）。
- 自発発火の体感頻度の劣化（silenceBudget 枯渇・§4）。
- barge-in の誤爆蓄積（免罪符として受容しているが、長時間では蓄積してうるさく感じる可能性）。

はいずれも未計測（人間ゲート後の実配信運用でのみ観測できる）。followup として持ち越す。

## 7. HTTP 応答レイテンシの UX 裁定（domain-b.md §8-1・Domain D への申し送りだった項目）

`fire()` が再生実区間を `await` するようになった結果、`POST /api/fire` の HTTP 応答は「発話が終わる
or 遮られる」まで返らなくなった（従来は play() 送出直後に即時 resolve）。

- **この Domain D での判断**: 操縦席の Fire ボタンは既存のとおり「押したら disabled → 応答 state /
  SSE soul で復帰」という設計のままにした（新規の UI 変更はしていない）。barge-in・自発発火の実装が
  この応答遅延を前提に成立している（speaking window を正しく覆うことが barge-in の必要条件）ため、
  「早期 resolve + 裏で再生追跡」という代替設計（Design Y）への変更は本 Domain では見送った——
  変更する積極的な理由（体感の悪さ等）が人間ゲートで観測されていないため。
- **梯子**: 人間ゲートで「Fire ボタンを押してから反応が遅い」という体感が問題になったら、Design Y
  （fire() を早期 resolve させ、再生実区間の追跡と barge-in 可能窓を別の内部状態として持つ）を
  検討する。

## 8. コーディネート誤爆・呼びかけの busy 非対称・不応期基点の保守設計（domain-c.md §8 の再掲・受容済み）

以下は spec/design/test の 3 レーンいずれのレビューでも non-blocking と判定済みの設計裁量。人間
ゲート③④での実害観測があれば再検討する（現時点では変更しない）:

- 呼びかけ（call）も busy 中は発火要求を出さない非対称（不応期/確率は掛けないが busy だけ respect
  する）。
- 不応期の基点は「発火要求を出した時点」で更新（busy/空窓等で実際には発話に至らなくても抑制される・
  リトライ嵐を避ける保守設計）。
- 沈黙の「活動」定義は speechStart/speechEnd + you/soul 転写のみ（speechCancel は無視）。

## 9. Domain A（声の器官刷新）由来の持ち越し（domain-a.md §7・非 blocking）

- **isPlaying() の粒度**: 状態応答フラグに基づく粗いブール。切断点算出は `playbackStartedAtMs` +
  タイムラインで足りると判断（Domain B で実装済み・実 Position を Node へ返す口は作っていない）。
  実機で不足が判明したら追加を検討。
- **デバイス名は完全一致**（`listAudioDevices()` の返す `name` をそのまま渡す前提）。同名デバイスが
  複数存在する環境では `id` 指定が要るかもしれない（未実装・実機は同名なしのため v0 は名前で十分と
  判断）。
- **WinRT ロードのオーバーヘッド**（常駐起動〜最初の STARTED まで実測521ms）: 常駐 1 プロセスなので
  初回のみ。起動タイミングは cli/orchestrator の既存結線に従う。

## 10. Domain D 自身の設計判断（§質問・迷った裁定点の集約）

- **出力デバイス変更の適用方式＝「その場再起動」**（domain-d.md §・Domain A §7-3 の申し送りへの
  回答）: 常駐プレイヤーは起動時に env でデバイス名を受けるため、デバイス変更には常駐プロセスの
  再起動が要る。「次回起動から適用」より「その場再起動（既存 player を dispose して次回
  ensureFireResources() で再生成）」を採用した——配信中に気づいてから切り替える運用（wave-plan §5
  choke point）を考えると次回起動待ちは現実的でないため。**再生中の発話の扱い**: dispose のみで
  barge-in の interrupt は経由しない（次に声を出すときから新デバイスに切り替わる・進行中の発話が
  古いデバイスのまま完了する可能性はある）。人間ゲート⑥で違和感が無いか確認してほしい。
- **selfFireEnabled の永続化は POST 経路のみ**: `server.setSelfFireEnabled()`（プログラム的呼び出し・
  Domain C が用意した継ぎ目）は永続化フック（`onSetSelfFireEnabled`）を呼ばない設計にした（HTTP
  エンドポイント `POST /api/self-fire` のみが永続化する）。既存 Domain C テストの互換性を優先した
  判断だが、将来 `server.setSelfFireEnabled()` を永続化と連動させたい用途が出たら見直しが要る。
- **自発発火マーカーは SSE `selfFire` を新設**（`fire`/`visionCaptured` イベントとは別枠）: kind
  （call/turn-end/silence）の情報を運ぶため新規イベント種別にした。通常の `fire` イベントと
  `selfFire` イベントが同一発火で両方飛ぶ（やや冗長）が、self-fire の発火要求が実際に発火した
  か（fired）まで含めて示すには専用イベントが必要と判断した。
- **バージイン診断のフィールド拡張**: 既存 `diagnostic` SSE イベントに `elapsedMs`/`charsSpoken`/
  `totalChars`/`prefix` を追加した（`fireVisionError` の `kind` と同じ「新規イベント種別を増やさず
  既存に相乗り」の設計を踏襲）。

- fire-orchestrator: speaking window の明示的 busy 拒否テスト・timeline null 要素の直接テスト

## 12. 口数（反応確率）の Cockpit 可変化（ユーザー裁定・今後の課題）

> 出典: S6 人間ゲート後のユーザーフィードバック（2026-07-13・Domain E 追撃の裁定と同席）。

自発発火の「口数」（＝どれくらい積極的に喋るか）は、配信のフェーズによって変えたくなる——会話がメイン
のときは相方によく喋ってほしいし、ゲームに集中したいときは今くらい（控えめ）でいい。**この切替は配信中に
操縦席（Cockpit）から行えるべき**というのがユーザー裁定である。以下を今後の課題として刻む:

- **配信中に Cockpit から切替できること**（CLI 起動オプションでの固定は不可＝配信を止めずに変えたい）。
- **UI は生スライダーではなくモード切替**（`控えめ / ふつう / おしゃべり` の 3 段階程度）。ゲイン CLI 面の
  教訓（S4 で「生の数値ツマミは UX 裁定で撤去」）と同じく、生の確率値を露出しない方向。
- **モードと定数の対応イメージ**: 「会話メイン」→ おしゃべり側（`TURN_END_PROBABILITY` を上げる・不応期を
  縮める等）／「ゲーム集中」→ 現行程度（＝控えめ）。具体的な定数マッピングは実装時に §3 の調整表を土台に
  決める。
- **実装時期は今後の課題**。現状の v0 は `src/mind/fire-scheduler.mjs` のコード内定数固定（ツマミなし・
  裁定 8）。この可変化は「自発 OFF トグル（S6 で実装済み）」の隣に増設するイメージ（`POST /api/self-fire`
  と同型の薄い継ぎ目 + settings 永続化 + scheduler へ定数束を渡す口）で、既存の結線パターンに乗る。
- **関連**: §3 の定数チューニング（人間ゲートの体感で直す）は「開発時に定数を書き換える」話、こちらは
  「配信中にユーザーがモードを選ぶ」話。前者が固まってからモード束（プリセット）を定義するのが自然。

## 13. 人間ゲート④(沈黙発火の実機体感)の持ち越し(2026-07-13・閉鎖時判定)

人間ゲートは①②③⑤⑥合格(「4以外は完全に達成」)。④は試せる状況になくユーザー判断で持ち越し・S6は閉鎖。機械側は実SDK実射(experiments/s6-conversation.md)で沈黙発火の動作自体を確認済みのため、残るは実機体感(放置45〜75秒→画面に言及した一言・頻度がうるさくないか)のみ。**次の人間ゲート(S7想定)に相乗りして確認する**。追撃E(自発発火に画像同乗)の再ゲート一点確認(human-gate-procedure.md §9-1)も同一手順で兼ねる。

**→ 解消(2026-07-14・S7実装後の実機確認)**: ユーザーが実機で「放置の結果喋り始める現象は観測できた」「画面も見えている」と確認。**④沈黙発火(実機体感)+追撃E(自発発火の画面言及)ともに合格**。これでS6の人間ゲートは全項目クリア。残るS系列の未確認人間ゲートはS7(YouTube実配信でのコメント拾い=ユーザー都合で後日)のみ。
