# 視界の取得許可と、Discordチャットからの受け取り

> 2026-11-16、初期の体験合意に続くユーザーとUndineの議論。機能実装やデバイスの採用はしていない。

## 1. 視界を取得してよい範囲と、取得のきっかけを分ける

### ユーザーの前提

- 外出時には見知らぬ他人が映り、撮影を許可されていない場面もある。配信画面のように無条件で映像を送り続ける前提にはしない。見せたい場面を選んで共有する。
- 家の中のユースケースは、基本的に許可された視界であることを前提にしてよい。発話のたびに画像を得る、配信に近い運用が許容される。

これは利用体験の前提であり、屋外・屋内一般の撮影可否を断定する法的な判断ではない。

### 合意した区別

1. **誰の視界か**：参加者からの共有か、チャッピー自身の目か。
2. **どこまで取得してよいか**：選んだ一枚、共有を許可している間、継続して許可された視界など。
3. **いつ取得するか**：参加者の「見せる」操作時、会話のために必要になったときなど。

外出／在宅という場所のモードだけに固定せず、視界ごとに許可の持ち方を変えられる方向を合意した。継続して取得を許可することと、映像を常時送信することは同義ではない。

チャッピーには「今も見えている」のか「以前に見せてもらった画像があるだけ」なのかが伝わる必要がある。外で一枚共有した後の移動先まで、見えているかのように扱わない。

具体的な許可状態のデータ構造、更新・停止のUI、取得頻度は未決。

## 2. 新しい要素を増やさない最小構成の案

ユーザーは、シンプルさを「新たな要素を導入しないこと」と定義した。Undineが次を提案し、ユーザーはDiscordのチャット欄を使う点を肯定した。全構成の製品選定や実装着手を合意したものではない。

- 家のPC：既存チャッピーを起動してDiscordの場を開く。当初はVC参加も事前に済ませる案だったが、後続合意では[VC参加・退出をDiscord側からも操作する](mobile-vc-control.md)方向になった。
- 手元のスマホ：同じVCに参加し、必要な場面だけ写真を送る。
- 通話用イヤホン等：スマホを持ち続けず会話する。手持ち機器の有無・適性は未確認。
- 写真を見せたいときは安全に立ち止まり、撮影してよい場面を選んでVC付属テキストチャットへ送る。

新たな装着型カメラや専用共有アプリを先に導入しなくても、会話と選択的な視界共有を試せるのでは、という案。スマホをかざしながら歩く運用は想定しない。

### 外部仕様として確認した範囲

Discord公式ヘルプは、モバイルでの撮影・写真送信と、VC付属テキストチャットへの添付送信を説明している。[モバイル操作](https://support.discord.com/hc/en-us/articles/360046618751-Getting-Started-on-Mobile) / [添付ファイル](https://support.discord.com/hc/en-us/articles/25444343291031-File-Attachments-FAQ)（2026-11-16確認）

これはチャッピーが写真を受信できるという意味ではない。現行のチャット・添付受信は未対応。[現行の限定棚卸し](repository-inventory-2026-11-16.md)。後続の[VC操作の合意](mobile-vc-control.md)では、家のPCで場を開く流れは維持し、VC接続だけをDiscord側からも操作する。アプリ起動・場の作成の遠隔化は今回の要求に含めない。

## 3. チャットの閲覧範囲を、ユーザーの権限に固定しない

[過去の秘匿ハンドアウトの議論](discord-private-handout-history-2026-11-16.md)を確認したあと、ユーザーが将来の拡張条件を明示した。

> 今後、ユーザー自身には閲覧権限がなく、チャッピーとGMだけが見られるチャットを、チャッピーの読む先として選択する機能が要求される可能性がある。

この可能性を意識したうえで、まずは選んだチャットを読めればよい。今から秘匿ハンドアウトの全体験を実装する要求ではない。

設計上の方向として、チャッピー自身に閲覧権限がある情報源を扱える余地を残す。ユーザーのDiscord画面を撮影して読む経路だけには依存しない。受け取った全文を必ずユーザーの操縦席へ表示する前提も置かない。これは、秘匿内容の取り扱い規則や表示仕様を決定したものではない。

非公開の読み先の選択方法、DMか限定チャンネルか、資料を誰にどう開示できるかは未決。一般のVC付属チャットを秘匿資料の送信先として採用したわけではない。

## 4. 実際の場面を通じて考えること

当初、ユーザーは「画像が見える」「PDFが読める」「チャットに書ける」を将来の場面から考える候補として挙げた。その後の機能整理で、**指定したDiscordチャットのテキスト・画像・PDFを当面の対象**と明示した。受け取った内容を踏まえてVCで会話できるところまでを扱う。チャットへの書き込みは今回の中心機能として追加していない。

後続context-checkで、読む先はCockpitから指定・変更し、新規投稿を受け取ってVC会話で参照することを合意した。代表的な問いは「今チャットに貼った、見れる？」。投稿ごとの強制発話は不要。読む先の変更に、既に会話で知った内容の忘却は含めない。

対応する画像形式やPDFの読取方式、秘匿内容の詳細な扱いは別途具体化する。PDFはまずCodexセッションにローカル保存先のパスを渡して読む方法を試し、必要時に読取ツール、さらに不足時にアプリ側変換を検討する。[承認済み実装計画](../implementation/orchestration/discord-companion-inputs-wave-plan.md)を参照。チャットへの書き込みは必要な場面から別途考える。

同日の機能整理では、この読み取りと[Discord側からのVC参加・退出操作](mobile-vc-control.md)の二つで、既に家のPCで場を開いている外出利用の最小構成を概ね満たすという認識を共有した。

## 5. 会話の経路と個人向けの機器選定の分離

ChatGPTアプリの音声会話も候補に挙がったが、既存のElevenLabsの声へ差し替える標準機能は公式情報で確認できなかった。提供された声の選択と、ElevenLabs連携による音声ファイル生成は、会話音声の差し替えとは区別する。[ChatGPT Voice](https://help.openai.com/en/articles/20001274-chatgpt-voice) / [ElevenLabs MCP](https://elevenlabs.io/docs/eleven-api/resources/mcp-server)（2026-11-16確認）

ユーザーはDiscordベースで考えると判断した。

機器の選定はユーザー個人に特化した内容なので、同日のユーザー指示によりGitの追跡対象外とする。端末情報・装着の好み・候補製品の比較はローカルの `audio-devices-*.md` に残し、共有する設計文書には転記しない。会話と選択的な視界共有の要求は、本トピックの追跡対象文書に保持する。
