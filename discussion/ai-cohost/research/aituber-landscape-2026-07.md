# 調査: AITuber技術地形(2026年7月時点)

> Status: Recorded(2026-07-10)。Sylph調査(web)の統合。情報種別: 公式事実・外部調査事実(出典付き)。
> 注意: 本文書では外部の一般語彙「AITuber」を出典文脈で使用する。本トピックの独自語彙は「AI共演者(ai-cohost)」。

## 1. 標準アーキテクチャ

2025-2026年のAITuber実装はほぼ全て同型のパイプライン:

```
コメント/音声取得 → 選別キュー → LLM(ストリーミング) → 文単位分割
  → 文ごとにTTS(逐次) → 再生 + 感情タグ→表情 + 音素タイミング→口形 → アバター描画 → OBS
```

主要OSS:

- **AITuberKit**(tegnike): 日本のデファクト。Next.js製一体型。LLM15種以上・TTS11種以上・VRM/Live2D対応。**v2.0.0以降カスタムライセンスで商用利用は別途ライセンス**。開発は活発(v2.56.0=2026-07-08)。https://github.com/tegnike/aituber-kit / https://docs.aituberkit.com/guide/introduction
- **Open-LLM-VTuber**: 13k+ stars。完全ローカル動作・徹底モジュール化(ASR/LLM/TTS/アバターを設定で差し替え)。ライセンス移行の動きあり。https://github.com/Open-LLM-VTuber/Open-LLM-VTuber
- 先端例: OBSヘッドレスコンテナ化+GCEでの完全自律配信(koduki氏)。「魂(LLMコア)/精神(キャラ定義)/肉体(I/O)」3層分離、「決まった処理はワークフローで書く方が楽」という設計思想。https://zenn.dev/koduki/articles/aituber-renv2-20260215

**含意**: 既存OSSはアバター描画込みの一体型であり、本プロジェクトはそこが不要(自前ランタイム実運用中)。パイプライン上流だけ薄く自作し、感情タグ規約等の設計だけ参考にするのが合理的。

  - **⚠訂正(2026-07-12、S1棚卸しの実機検証)**: AivisSpeech Engine 1.1.0-dev の実機では `audio_query`/`mora_length` の**モーラ長・pitchが全零**で返る(APIの形はVOICEVOX互換だが長さの実値が入らない)。「音素長が秒単位で返る」は**このエンジンでは不成立**。代替の時間材料=合成WAVの実長(モーラ均等割り、S1裁定で採用)。モーラの**種類**(音素列)は正しく返るため「TTS選定がリップシンク方式を規定する」の骨子は生き残る。詳細: [../implementation/orchestration/s1-planning-inventory.md](../implementation/orchestration/s1-planning-inventory.md) §3
- **にじボイスは2026-02-04にサービス終了済み**(日俳連の「声優に酷似」指摘を受けた撤退)。ボイスクローン系は声の出所に注意という運用教訓。https://algomatic.jp/news/notice_nijivoice_20251121

## 3. レイテンシ設計

- 標準手法: LLMをストリーミングで受け、句読点で文単位に分割し、文ごとにTTSへ投げ、生成済み音声をキューで逐次再生。体感遅延は「LLM初トークン+1文分のTTS」まで縮む。
- コメント駆動の配信は対話より要求が緩く、**2〜5秒でも視聴体験は成立**(コメントは常に流れており即答の期待が薄い)。
- TTSサーバ常駐+プリウォームは必須の実務。発話中に次応答を先行生成する先読みも定番。

## 4. 感情・所作の駆動

- **インラインタグ方式がデファクト**: システムプロンプトで応答に `[happy]` 等を付けさせ、ストリーミング解析でタグを剥がして表情コントローラへ、本文をTTSへ。`[happy][bow]` のような併記で複合表現も可能。https://docs.aituberkit.com/guide/character/common
- structured outputは全体が揃うまでパースできずストリーミングと相性が悪いため不採用が主流。
- TTSのスタイル指定に同じタグを流用し、**声と表情の感情を一つのタグで同期**させるのが定石。
- 本プロジェクトへの含意: 決定論的パラメータ駆動なので「感情タグ→パラメータカーブのプリセット」写像テーブルで接続できる。

## 5. チャット取得

- YouTube: 公式Data API v3(クォータ日10,000ユニットで長時間配信は枯渇しがち) or 非公式ライブラリ(pytchat系。クォータ不要だが仕様変更で周期的に壊れる)。**壊れる前提で差し替え可能に抽象化必須**。
- Twitch: 公式EventSub(WebSocket)が整備されており良好。旧IRCからの移行が公式推奨。https://dev.twitch.tv/docs/chat/irc-migration/

## 6. 運用面の落とし穴

- **プラットフォーム規約**: YouTubeの2025-07収益化ポリシー改定は「大量生産・没個性コンテンツの排除」であり生成AI自体の排除ではない。ライブ配信は人間の関与が見えやすくリスク低側。ただし**リアルに見える合成コンテンツのAI利用開示設定は必須**。https://www.itmedia.co.jp/aiplus/articles/2507/10/news128.html
- **プロンプトインジェクション**: 視聴者コメントは全て信頼できない入力。多層防御(コメントの明示的隔離 / 入出力NGワード / 出力検査 / LLMに与える能力の最小化)。**TTSに渡る直前の最終テキスト検査が要所**。緊急ミュート/キルスイッチを用意。
- **長時間安定性**: 会話履歴の無限成長(要約圧縮かスライディングウィンドウ)、チャット取得の切断、TTSサーバのメモリリーク、話題ループ。各段を独立プロセス化しwatchdogで再起動が実務パターン。
- **speech-to-speech APIの不採用理由**: カスタム声不可(キャラ声にできない)、実測TTFT 0.78〜2.98秒で圧倒的に速いわけではない、高額(OpenAI Realtimeで〜$0.30/分≒3時間配信$54)、リップシンク資産と不整合。https://softcery.com/lab/ai-voice-agents-real-time-vs-turn-based-tts-stt-architecture
