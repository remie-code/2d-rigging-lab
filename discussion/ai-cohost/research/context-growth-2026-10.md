# 長い配信で頭の応答が遅くなる件(2026-10-17)

> 配信で会話が長くなると応答が十数秒になる(ユーザー観測)。原因と圧縮手段の調査(Sylph)。【リポジトリ事実】【記録】【公式】【推測】を分ける。

## 1. 原因の候補(リポジトリ事実)

- 頭のセッションは配信中ずっと同じ(Codex は 1 つの app-server と 1 つの thread、Claude は常駐の query)。作り直すのは頭の切り替え・記憶の ON/OFF・会話指示の保存・(Codex の turn 失敗)だけ。
- **会話の窓が重複して積み上がる**: 発火のたびに直近 5 分・4000 字の窓を丸ごと渡し、セッションは前の ask を全部履歴に持つ。5 分以内に N 回発火すると同じ行が最大 N 回入る。チャッピーの発話は assistant の応答としても、次の窓の `soul:` 行としても入る。
- **画像が履歴に残る**: Codex では base64 のまま rollout に残ることを確認。Claude も SDK の履歴に残る。
- Codex のシステムプロンプト(仮面・表情タグの教示・記憶のダイジェスト)は最初の user メッセージに連結しているだけ(`developerInstructions` / `baseInstructions` は未使用)。圧縮で要約・脱落するおそれがある(推測)。
- usage は `last` だけ取り、`total` と `modelContextWindow` は捨てている。ファイルにも残らない。

## 2. 記録

- fire-diagnostics は直近 5 件だけ。残っていた #202〜#206(1 プロセス、頭は codex-61-sol、途中で作り直しなし、約 200 回目の発火。すべて speak-now の視覚発火)で、ask 開始 → 最初の文字が **12.3〜13.8 秒**、ask 全体 15.2〜16.8 秒、注入は 1.1〜1.2k 字。
- input_tokens の推移は記録なし。遅さが履歴の長さによるものかは確定できない(推測: 画像だけで 10 万トークン級が履歴に入っていた可能性)。
- 過去: Terra は同じ thread で in_tok 117k まで伸びても約 4 秒で平坦だった(brain-swap.md §7)。

## 3. 圧縮の手段(公式・型で確認)

- Codex(同梱 0.163.0、stable): `thread/compact/start {threadId}`(手動圧縮。進捗は turn / item 通知、`contextCompaction` item)、`thread/inject_items`(turn を起こさず履歴へ追加)、`thread/fork`・`thread/revert`、自動圧縮の設定 `model_auto_compact_token_limit`(既定値は公式に記載なし)・`compact_prompt`。圧縮中の turn には入力を差し込めない。https://learn.chatgpt.com/docs/app-server 、https://learn.chatgpt.com/docs/config-file/config-reference
- Claude Agent SDK(0.3.207): `/compact` をプロンプトとして送る(`compact_boundary` で結果)、`autoCompactEnabled` / `autoCompactWindow` の設定、`getContextUsage()`。今の llm-session は `/compact` の結果を返事として扱ってしまうので専用の送り口が要る。https://code.claude.com/docs/en/agent-sdk/slash-commands

## 4. ユーザーの方針(2026-10-17)

- 会話の作り直し(新しいセッションに要約を渡す)はやらない(変な断絶が起きそう)。
- 窓の重複を減らす(前回から増えた分だけ渡す)は取り組む。
- 頭の側の圧縮を、特定の条件で緩い頻度で呼ぶ。細かいことを忘れるのは仕方ない。できれば配信者が話していない隙間に行う。
- 画像は「ゲーム配信の強い記憶」なので個別に消さない。圧縮で要約されるのに任せる。

## 5. 決定(ユーザー 2026-10-17)

今の仕組みの理解: 発火のたびに、転写バッファから届いて 5 分以内の行(you / soul / viewer)を 4000 字までの窓にして、(画面を見る発火ならその回の画像 1 枚と指示を前に付けて)同じ Codex スレッドに 1 通送る。スレッドは全部覚えているので、窓の行が 10 回前後重なり、画像は発火ごとに 1 枚ずつ積もる(約 200 回で 200 枚近く)。

4 つをまとめて実装する(圧縮はスケーラビリティのため最初から対応):

1. **記録**: 発火ごとの入力トークン(今回分と累計、`tokenUsage.total` / `last` / `modelContextWindow`)と、最初の文字までの時間をファイルに残す(配信を通して読み返せるように)。
2. **増えた分だけ渡す**: 前回渡した行より後ろだけを渡す。チャッピーの行(実際に聞こえた分)も増えた分に含める(遮られた・NG の補正を保つ)。「推論に使った範囲」の表示は「どこまで」が分かればよいので今のまま。
3. **隙間で手動の圧縮(Codex のみ)**: `thread/compact/start` を、累計トークンがしきい値を超え、チャッピーが空いていて、配信者が少し黙っているときに呼ぶ。しきい値は記録を取ってから決める(当面の初期値は仮)。Codex の自動圧縮には頼らない。圧縮中の発火は、待たせるのが簡単なら待たせ、難しければ捨てる。
4. **人格の指示は圧縮の直後に 1 回だけ差し込み直す**(`thread/inject_items`。保険。普段の発火の仕組みには出さない)。

- Claude の頭は当面使わないので対象外。

## 6. 実装の合意(context-check 済み、2026-10-17)

- 本物の Codex で圧縮を 1 セットだけ試してよい(使い捨ての会話で数回やり取り → 圧縮 → 人格の指示を差し込み → もう 1 回。サブスク枠を少し使う)。圧縮の所要時間と、口調・表情タグが保たれるかを見る。
- しきい値の初期値: **扱える最大量(modelContextWindow)の 66% を超えたら**(圧縮後に約 20% 残る想定だと 50% は頻度が高すぎるため。ユーザー)。設定で変えられる。
- 隙間の定義: チャッピーが空いている・判定の待ちがない・配信者の喋り終わりから 3 秒以上・前の圧縮から 10 分以上。返事が終わるたびと数秒おきに確かめる。
- 圧縮中の発火は終わるまで待たせる。60 秒を超えたら待つのをやめて発火する。
- 記録: 発火ごとに 1 行(発火番号・頭・今回と累計の入力トークン・キャッシュ分・最大量・最初の文字までの時間・画像の有無・渡した行数と文字数。本文は書かない)。`apps/soul/agent/session-usage/` に起動ごと 1 ファイル(gitignore)、直近 20 回分を残す。
- 増えた分だけ: 会話が新しく始まったとき・Codex が内部で会話を作り直したときは直近 5 分を全部。新しい行が無い発火は「(前回から新しい発言はなし)」。4000 字の上限は残す。
- 人格の指示の差し込み直しは、会話の最初に渡しているものと同じ中身。
- 見え方: 圧縮の開始と終了をターミナルに 1 行・ログのタブに 1 行。メイン画面は今の表示のまま。

## 7. 実装報告(Gnome、2026-10-17)

- 変更: codex-session(ask の戻りに tokenUsage = last / total / modelContextWindow、`conversationKey()`・`getContextUsage()`・`isCompacting()`・`compact()`。圧縮中の ask は最大 60 秒待つ)、fire-injection(`formatFireInjectionSince`、「(前回から新しい発言はなし)」)、fire-orchestrator(同じ会話なら前回の最後の seq より後ろだけ、会話が替わったら 5 分全部、`onAskRecord`)、新規 context-compactor.mjs(判定と 5 秒おきの確認)・session-usage-log.mjs(起動ごと 1 ファイル、直近 20 個)、cockpit-server(配信者が喋っているか・喋り終わりの時刻、ログのタブに圧縮の行)、設定キー `compactThresholdRatio` / `compactQuietSec` / `compactMinIntervalMin`(次回起動から)。`node --test` 1367/1367、check:soul-zone 通過。
- Gnome が決めた点: 空窓の判定は従来どおり 5 分全体で行い、増えた分が 0 でも発火して「(前回から新しい発言はなし)」。ask が失敗したら目印を進めない。記録に `windowMode`(full / delta)を追加。「判定の待ち」に speak-now・コメント反応・弾く判定の待ちを含める。圧縮の失敗では thread を作り直さず、10 分は再試行しない。差し込みは role "user" の input_text。しきい値は直近の ask の `last.inputTokens / modelContextWindow`(ちょうど 66% は含めない)。
- 実機の 1 セット(gpt-6.1-sol / effort low、4 往復 → 圧縮 → 差し込み → 1 回): 圧縮から差し込みまで **7.34 秒**。modelContextWindow は **475,000**(66% ≈ 313,500)。毎回の入力のうち約 14k は Codex 自身の固定の指示。会話が短すぎて圧縮で縮む幅は測れていない(圧縮後の last は 15,114)。圧縮後の返事は口調・正規の表情タグとも保たれ、圧縮前の話題も覚えていた。圧縮の turn 自身の入力トークンは 0 で返る(当てにならない)。
- 未確認: 長い会話(画像が多い)での圧縮の所要時間と縮み幅。60 秒の待ちを打ち切って圧縮中の thread に turn を送ったときの挙動。
- 注意(ウンディーネ): 最大量が 475k なので 66% は約 31 万トークン。前回の配信で 12 秒台だったときの文脈がそこまで達していたかは分からない(記録がなかった)。遅さが 31 万より手前で効き始めるなら、しきい値を下げる必要がある。次の配信の記録で、文脈の大きさと最初の文字までの時間の関係を見てから決める。
