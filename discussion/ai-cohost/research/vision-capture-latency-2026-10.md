# 画面キャプチャの遅延(2026-10-17)

> 自発の発火(speak-now・コメント反応)は `fire({vision:"preferred"})` で、受理の後に画面を撮ってから LLM に渡す。その待ちが約 0.5 秒あることの調査(Sylph)。

## 1. 内訳(自分で起動したメモ帳の窓で実測)

| 中身 | 時間 |
|---|---|
| powershell.exe の起動(撮るたびに毎回) | 約 330ms |
| C# の P/Invoke 定義を毎回コンパイル(窓探しより前なので見つからなくても払う) | 約 110ms |
| Get-Process で窓を探す | 約 35〜55ms |
| 撮影(PrintWindow)・縮小・JPEG・base64 | 合計 約 60ms |
| 合計(成功) | 約 600ms |

- 仕組み: src/eyes/powershell-exec.mjs が撮影ごとに PowerShell を spawn、src/eyes/window-capture.mjs のスクリプトが Add-Type(C# コンパイル)→ 窓タイトル完全一致で検索 → PrintWindow → 長辺 1024 に縮小 → JPEG 75 → base64。待ち点は fire-orchestrator の `await captureImpl(title)` の 1 か所。
- **重要**: 本番の visionTarget は OBS 本体の窓タイトル(シーン名を含む)。シーンを切り替えると完全一致しなくなる可能性が高い(推測)。fire-diagnostics に残っていた撮影 5 回はすべて notFound(画像なしで喋るので気付きにくい)。
- 画像を早く用意しても、LLM が画像を読む分の時間は減らない(過去の実験で画像付きの冷えた ask の最初の文字まで 4.8 秒)。

## 2. 代替方式(実測・推測)

| 案 | 返事に乗る時間 | 手間 | 備考 |
|---|---|---|---|
| A. 今のスクリプトを軽くする(コンパイルをやめる等) | 約 400ms | 小 | |
| B. 小さな exe ヘルパーを毎回起動 | 約 75ms(実測) | 小〜中 | csc.exe(OS 付属)でビルド可 |
| C. 撮る係を常駐(PowerShell か exe) | 約 35〜55ms(実測。起動 0.45 秒は初回だけ) | 中 | 寿命管理・再起動・UTF-8 の約束が要る |
| D. 1〜2 秒おきに先撮り | ほぼ 0 | 中 | 画像が最大 1〜2 秒古い。ゲームによってはカクつく可能性(推測) |
| E. 判定の開始と同時に撮り始める | 判定の往復と重なる | 中 | 判定の多くは「待つ」なので無駄撮りが増える |
| F. OBS WebSocket の GetSourceScreenshot | 数十 ms(推測) | 中 | 配信画面そのものを貰える。窓タイトル問題も消える。OBS の WebSocket 有効化とパスワード保管が要る。仕様は一次資料で要確認 |
| G. Windows.Graphics.Capture の常駐ヘルパー | ほぼ 0 | 大 | |
| H. 待つ上限(例 150ms で画像なしへ) | 最悪でも上限 | 小 | |

## 3. 決定(ユーザー 2026-10-17)

- **C(撮る係を常駐させる)を採用**。撮る対象は**ゲームの窓**のまま。
- OBS から貰う方式(F)は採らない: 配信画面には配信者やチャッピーの立ち絵が重なっていて、その下のゲーム画面が見えなくなるため。
- 窓タイトルの問題は、配信前にユーザーが撮る窓を正しく合わせるので問題ない(OBS 本体窓が設定されていたのは今の状態というだけ)。
- 撮影の仕組みの直しは、操縦席の作り直し(2 本目)とは別の作業として行う。

## 4. 実装の合意(context-check 済み、2026-10-17)

1. 撮る係は常駐の PowerShell(実測済み、ビルド物の配布が要らない)。C# の型の読み込みは起動時に 1 回だけ。入出力とも UTF-8。
2. **耳(マイク)の Start に合わせて立ち上げ、耳の Stop で止める**(ユーザー案。配信前に起動の 0.45 秒を払い終える)。
3. 1 回の撮影に 2 秒の上限。超えたらその回は画像なしで喋り(今と同じ扱い)、撮る係を立ち上げ直す。
4. 窓はタイトルの完全一致のまま(配信前にユーザーが合わせる)。
5. 撮る窓の一覧(準備・設定で使う)は今のまま。
6. テストは偽物の撮る係で通す。最後にユーザーが実際のゲームの窓で画面を見て喋る発火を数回行い、撮影時間がログで短くなっているかを見る。

## 5. 実装報告(Gnome、2026-10-17)

- 追加: `src/eyes/resident-capture.mjs`(常駐の撮る係。起動時に型を 1 回読み込み、要求 `CAPTURE <id> <base64 タイトル>`、応答は既存の形 + 終端行。2 秒の上限、超過・落ちたら立ち上げ直し)とテスト 19 件。cockpit-server に `onEarsStarted` / `onEarsStopped`、scripts/cockpit.mjs で耳の Start / Stop に結線し `captureImpl` に注入。撮影ごとにターミナルへ `[cockpit] capture: via=resident ms=… result=…`(タイトルや画像は書かない)。
- Gnome が決めた点: 撮る係が使えないとき(起動中・立ち上げ直し中・諦めた後・同時の 2 件目)は今の毎回起動に戻す(手動の「見て喋る」が中止されないように)。起動完了前に 3 回続けて落ちたら、その耳の Start の間は諦める(次の Start で再挑戦)。起動完了の上限 10 秒。撮る係を立ち上げるのは耳の Start が成功した後。
- 検証: `node --test` 1248/1248、check:soul-zone 通過(ウンディーネ再実行)。メモ帳の窓で、撮る係の起動 367〜398ms、撮影 中央値 48ms(初回だけ約 140ms。毎回起動は 591〜617ms)。日本語タイトルの完全一致で撮影できた。操縦席の終了で撮る係が残らないことを確認。
- 未確認: ゲームの窓(DirectX 等)での撮影時間。ユーザーの確認待ち。

## 6. Endfield と OBS が撮れない件(2026-10-17)

- 症状: 撮る窓「Endfield」と OBS 本体窓の撮影が `PrintWindow returned false`(常駐・毎回起動の両方で同じ。AivisSpeech の窓は撮れる)。
- 原因(調査): Endfield と、Endfield を撮るために起動し直したとみられる OBS が、操縦席より高い権限(管理者)で動いている(実行ファイルのパスが読めない)。低い権限のプロセスから高い権限の窓への PrintWindow は Windows が断る。常駐化による退行ではない。画面の範囲を直接写す方法は権限の壁を越えるが、一番手前に見えているものしか撮れない(確認時はブラウザが写った)。
- 決定(ユーザー): 操縦席を管理者として起動する(`start-cockpit.cmd` を右クリック → 管理者として実行)。確認したところ、Claude の頭はツール無効、Codex の頭は read-only の砂場・ネットワークなし・承認なしで動くため、書き換えや外部送信はできない(読める範囲は広がる)。
- それでも Endfield が撮れない場合はアンチチートが原因とみて、OBS WebSocket でゲームキャプチャのソースだけを貰う方式に切り替える(配信画面全体ではないので立ち絵の問題は無い)。
- 結果(2026-10-17): 管理者として起動した操縦席で、Endfield と OBS の撮影に問題がなかった(ユーザー確認)。
