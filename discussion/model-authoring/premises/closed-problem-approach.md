# Closed Problem Approach

> 「Fable に 2D モデルを作らせる」を解く方法論の合意。2026-07-02 合意（提案: ユーザー）。

## 定義

ユーザーが実際に行っている rigging 工程（実証済みの「いつもの手順」）を Fable が追体験する形で、モデル制作を**「閉じたより簡単な問題の連続」**に分解して検証する。

各閉問題で問うのは 2 つ:

- **A.** この問題を解くために Fable に必要な API は何か
- **B.** 実際に Fable が作業し、ユーザーが満足できるか

工程順序の正しさ自体は議論しない。課題は「Fable にとって正しい手順で作業すること」ではなく「作業した結果が良いものであること」だからである。

## 棄却された代替案

- **ref 描画 + 壊した変種による弁別テスト**: 採点基準の準備がユーザーの認知負荷限界を超えるため棄却（詳細は [authoring-solvability-analysis.md](authoring-solvability-analysis.md)）。
- ただし閉問題アプローチはこのテストの意図（Fable の目の測定）を放棄していない。視覚判定を要する工程の中に、自然にスコープされた形で埋め込んで継承している。採点基準は「ユーザーが一目見て満足するか」であり、この狭さならユーザーの認知負荷内に収まる。

## 利点（合意）

- **i. Fable の認知負荷低減** — 「rigging をこなす」という題目は大きすぎて良い結果への収束を保証しないが、その中の 1 操作なら十分に可能性があり、議論も地に足がつく。
- **ii. ユーザーの認知負荷低減** — rigging 全体の正解定義はユーザーに不可解だが、眼球の rigging に限れば可解に近づく。
- **iii. ref 参照範囲のスコープ** — ref は強力だが情報量が多すぎる。閉じた問題設定が「今どこを見るか」を明確に規定し、認知負荷を大きく下げる。
- **iv. API 整備の需要駆動化** — 閉問題が要求する最小 API 面だけを造る。インターフェースの網羅的な先造りをしない。次の閉問題が次の面を要求する。
- **v. 反証の前倒し** — 第一閉問題（眼球 X）の視覚判定は判定梯子のほぼ最下段の幾何タスク。もし Fable がこれに失敗するなら、中心的未知（Fable の視覚弁別力）に最小の建造投資で否定的な答えが出る。成功しても失敗しても、一番安い実験で一番重い情報が取れる。

## 既知リスク（named, deferred）

- **局所満足の合成が全体の良さを保証しない**（例: 眼球 X リグが後工程の顔向き X のデフォーマ階層と干渉する可能性）。ただしユーザーの工程順は配信実証済みモデルを産んだ実手順であり、合成問題はその順序の中で管理されてきた実績がある。閉問題を跨ぐ干渉が現れた時点で扱い、全体整合の事前設計はしない（非有界空間への逆戻り防止）。

## 構造的性質

- 1 閉問題 = 1 認識合わせ単位。**wave 規律のモデル制作への移植**。事前に認識合わせを済ませ、実行を確認作業に落とす。
- この開発の大半はユーザー × Fable の対話が占め、**実際のモデル作成工程は対話完了後の事後確認作業に過ぎない**（ユーザー方針）。
- 閉問題の記録から蒸留した不変量は `../craft/` に昇格し、制作定石（工程の地図）が副産物として蓄積される。閉問題の順序自体がユーザーの実工程順であるため、問題列を並べること自体が定石の文書化になる。
