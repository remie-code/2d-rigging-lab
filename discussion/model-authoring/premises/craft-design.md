# Craft Design

> `craft/` の成果物イメージと参照モデルの合意。2026-07-02 合意。

## 目的

craft/ は **Fable が2周目を1周目より上手くやるための記憶**（手続き記憶）。閉問題を通過するたびに、その記録から再利用可能なレシピと不変量を蒸留して蓄積する。

- **レシピ側**: 次に別のモデルで同じ工程をやるとき、対話なしで実行できる手順書
- **不変量側**: 視覚判断で使った基準の言語化（次の判断を速く正確にする経験則）

## 参照モデル（Accepted）

一括読み込みではなく**工程単位の遅延ロード**。2周目の Fable も有限コンテキストのエージェントであることから逆算する。

1. **craft の `_map.md`（= 工程の地図）だけを常駐させる** — 工程の順序と現在位置のみ
2. 工程に入るたびに**その工程のレシピ1枚だけをロードして実行する**
3. レシピが「★視覚判断」と印した点でだけ判断基準を発動し、「ユーザー gate」と印した点でだけユーザーの目（観測器）を呼ぶ

これは discussion-management の導線/成果物分離と同型の構造であり、craft/ が discussion/ 配下に自然に収まる理由でもある。

### 棄却された代替案

- **SKILLS 形式（`.claude/skills/`）での定義**（ユーザー当初案）。討議の結果、常駐地図 + 遅延ロード方式の方が筋が良いと合意。craft はエージェントの行動規範ではなくワークスペース固有のドメイン知識であり、工程単位の粒度で読み書きされ、周回ごとに改訂される——skill のロード粒度・更新様式と合わない。

## レシピの品質基準（Accepted）

> **自己完結性テスト: 「まっさらなエージェントがこのファイル1枚と API アクセスだけで、その工程を実行できるか」**

各レシピは1枚で閉じること: 前提状態、叩く API 列、判断点とその基準、完了チェック、エスカレーション条件。

帰結: **自己完結したレシピはそのまま委任プロンプトになる**。2周目では判断がほぼ不要な工程（メッシュ生成、デフォーマ作成、keyform 打ち等）はレシピを渡してサブエージェントに委任でき、ルートコンテキストは地図と判断だけを持つ（implementation-orchestration と同じコンテキスト保護構造）。

## 終着イメージ

閉問題の連続が rigging 完了まで閉じたとき、craft/ は**プログラム**に収束する:

- **工程の地図** = 実行順序（制御フロー）
- **各レシピ** = 手続き（ほぼ決定論的な API 列 + 印付きの判断点）
- **共有不変量** = 複数工程から参照される判断基準（対称性チェック、密度の経験則など工程を跨ぐもの）

**2周目 = craft/ というプログラムを Fable がオーケストレーターとして実行すること**。ユーザーの目はプログラム中に印された gate でのみ呼ばれる観測器となる。

## 書き戻しループ（Accepted）

参照は読むだけではない。2周目はレシピの曖昧箇所・基準の粗い箇所を露呈させるため、**読む → 実行 → 改訂**のループで craft/ 自体を周回ごとに硬くする（mutable conventions と同じ扱い）。

## 蒸留の書式方針（Accepted）

01-eyeball-x の蒸留から、**最初から自己完結性テストに通る形式で書く**。1周目の蒸留が2周目の実行形式を先取りしていれば、後の昇格作業が不要になる。

## 想定構成（craft/ 作成時）

```text
craft/
  _map.md          # 工程の地図: 順序、状態、各レシピへのリンク
  <工程名>.md      # 工程単位のレシピ（自己完結）
  invariants/      # 共有不変量（必要になった時点で作成）
```
