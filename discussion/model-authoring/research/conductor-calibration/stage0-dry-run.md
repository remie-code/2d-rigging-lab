# 工程0 空実行テスト（開眼と棚卸し）— 実行計画と質問リスト

> 実施: クリーン Fable（三十三代目）、2026-07-06。入力 = _conductor.md + craft レシピ00〜10 + premises 全5文書のみ（封じ込め遵守: closed-problems/・research/ 本文・ref/・rigging ワークスペース実体は未読）。op 不発行・CLI 不実行の計画のみ。
> 想定状況 = 新規モデル（PSD インポート直後・メッシュ未生成・リグ皆無）のワークスペース受領直後。

## 1. 実行計画

### Phase A: 実行系確立（レシピ00 手順1〜2＋前提確認）

1. **受領物の確認**: ユーザーから `<PKG>` パスを受領。`<PKG>` が `open-model-package-v1` 構造であることを manifest で確認（違えばエスカレーション: レシピ00）。git 管理状態は **`git status` のみ**で確認（封じ込め: git log 禁止）。未 init なら `git init && git add -A && git commit -m "[init]"`。
2. **STATE dir の決定**: `<PKG>-state`（`<PKG>` の外。中に置くと CLI reject）。
3. **CLI 疎通 = 健診**: `<REPO>` から `validatePackage {profile:"strict"}`（読み取り封筒、capabilities `["read","validate"]`）。新規インポートは error 0 が期待値。★error があれば内容を読んで「進行可能な既知クラスか、ユーザー相談か」を判断。blocking / 構造不一致 / textureDimensionSources の reject → ユーザーへ。
4. **開眼レンダ**: `renderView {outDir, outputName}`（view 省略 = 全身）。**完全透明が正常**（全 drawable がプレースホルダメッシュ・頂点0。故障と誤診しない）。レンダは gate 提出束に保存。
5. **baseline git commit**: 未コミット差分があれば commit。メッセージは工程タグ接頭辞つき（書式未定義 → 質問12。仮: `[stage0] baseline`）。baseline 存在確認は git log が禁止のため、**自分の commit コマンド出力の記録**で代替（質問2）。

### Phase B: 意味論解決表（棚卸し本体）

6. **一次ソースの読取り**（すべてパッケージ JSON の直読み。op 不要）:
   - `<PKG>/model/drawables.json` — displayName ⇄ drawableId、baseDrawOrder、partId、runtimeVisibility
   - `<PKG>/model/graph.json` — parts（PSD グループ名が Parts Container にそのまま残る。部品コンテナ単位の列挙に使う）
   - `<PKG>/model/meshes.json` — 各 drawable の頂点数（新規なら全0のはず。0でないものがあれば「どこまでリグ済みか」の証跡）
   - `<PKG>/model/parameters.json` + `<REPO>/packages/package-format/src/parameter-presets.ts` — プリセットは常在（parameters.json に無くてもサーフェスに存在: レシピ08）。使用予定パラメータの実 ID・range・default をここで確定
   - `<PKG>/model/masks.json`・`rig-controls.json` — 新規なら空の確認（リグ皆無の裏取り）
7. **委任分担**: 棚卸しは機械的列挙寄り（model-allocation-policy: 中位以下で足る）だが、工程0全体は指揮書 §0 の「調査・棚卸しの大物は非 Fable（opus 級）へ」と「実装はクリーン Fable へ」に跨る。**本計画では drawable 数が多い場合（目安: 100超）のみ列挙を opus へ孫委任**し、表の設計・曖昧判定は自分が持つ（質問14）。委任時は規律パック（封じ込め verbatim・report.md 漸進書き・停止条件）を積む。
8. **解決表の作成**: 行 = 意味論単位（顔輪郭 / 鼻（基底鼻——face 階層の part 所属。表情セット配下の nose 群と partId で見分ける: レシピ06）/ 目 L/R × 状態（開・半・閉、eyelash・eyewhite・irides）/ 眉 / 口 / 前髪・横房・後ろ髪（揺れ系統の分割単位で）/ 耳 / 付属物（帽子・眼鏡・立ち付属物の有無）/ 首 / 胴 / 腕 / 衣装差分 / 参照素材（口閉じ・母音））。列 = ユーザー語彙・displayName・drawableId・partId・baseDrawOrder・メッシュ有無・runtimeVisibility・使用予定工程。
   - 表情差分の同名パーツは**無印サフィックスのセットが第1=デフォルト表情**（レシピ00）
   - **一級規則1: 不一致・曖昧は推測で埋めず、表に「質問」行として残して gate で停止**。ユーザー語彙列は displayName から私が仮案を書き、gate で確認する方式と仮定（質問6）
9. **パラメータ解決表**: param_eyeball_x/y・param_eye_left/right_open・口系（Mouth Open・母音——preset に母音が無い場合の扱いは質問8）・param_face_angle_x/y/z・body 系 X/Z・Hair Front/Side/Back Sway X・Accessory Sway X。各 ID・range・min/max の意味（方向規約は**用語でなく観測量**で記録: 「max = 画面右視線」等）。

### Phase C: 素材マニフェスト（全工程の素材前提の一括照合）

10. **工程別チェックリスト**（各レシピの「前提状態」から逆算した照合項目）:
    | 工程 | 素材前提 | 出典 |
    |---|---|---|
    | 2 目 | 開き目セット（eyelash/eyewhite/irides）・半目セット（eyelash2/eyewhite2/半目眼球）・閉じセット（eyelash3） | レシピ05 構造 |
    | 2 口 | 最大情報素材 = 全開「あ」（歯・舌・口内が描かれている）・参照素材: 閉じシルエット + 母音 i/u/e/o（永久非表示 drawable として供給） | レシピ09 §0 |
    | 3 回転 | 立体物の有無（帽子・眼鏡・立ち付属物・房）。「パーツで出す」解に必要な後頭部パーツ等の有無 | レシピ07 |
    | 4 揺れ | 揺れ系統が自由長別に別 drawable へ分割されているか（自由長が違う房はパラメータを分ける前提） | レシピ08 §0 |
    | 5 差分 | 衣装差分一式・共有パーツ（首・髪）の切り分け・アトラス形式所属の対象確認 | レシピ10 |
    判定は 有 / 無 / 曖昧 の三値。**無・曖昧は一括依頼リストへ**（1周目の律速 = 素材後出しを構造で消す: 指揮書 工程0）。
11. **供給方式の確認事項**: 不足素材をユーザーが追加する手順（PSD 再インポート？）と、それが既存ワークスペース（revision・生成済みメッシュ・可視旗）に与える影響は craft に記述が無い → 質問13。供給待ちと工程1着手の順序もここで合意する。

### Phase D: 正典値実測シート（以後の全数値の唯一の出所）

12. **採寸リスト**（`inspectEvaluatedGeometry`、includeVertices:false、読み取り封筒）:
    - canvas / model bounds（全身寸法）
    - 頬幅（顔素材 bbox 幅）・白目 L/R・虹彩 L/R・まつげ各状態・口・眉・鼻・各房・首・胴・主要付属物の rest bbox
    - **注意: 工程0の計測基底は宣言 bounds**（プレースホルダ・頂点0のため）。レシピ06 は「生成後の実頂点範囲」を要求し「宣言 bounds は実頂点範囲より狭いことがある」と警告する → シートは**二段構え**（工程0: 宣言値列 / 工程1後: 頂点範囲列を追記して確定）と仮定（質問4）
    - **px→cm 宣言**: 全身 px ÷ 想定身長（レシピ08 §2.2）。想定身長はユーザーに質問（質問5）
    - **回転 pivot 候補**: cx（顔中心線）・cy（縦回転軸 = 耳の高さ相場、目の高さ X 赤道と 4px 以内の実証: レシピ06）・FaceZ pivot（首素材 bbox 中心）・BodyX 軸 = 脊柱（胴素材の alpha 重心実測——texture-atlas.json の binaryAssetRef から画素を読む）・BodyZ pivot（相場の記述なし → 質問16）
13. シートはファイルとして永続化（置き場所の規約なし → 質問3。仮: 周回用の作業ディレクトリに `canonical-measurements.md`）。「以後の全数値の唯一の出所」なので、gen スクリプト群が参照できるパスに置く。

### Phase E: 可視旗の明示化（工程0で唯一の committed op 群になりうる）

14. 「空メッシュで偶然隠れている」素材の列挙: meshes.json 頂点0 ∧ runtimeVisibility true ∧ 最終的に隠れているべきもの（衣装差分・参照素材・非デフォルト表情セット）を抽出。
15. 各 drawable へ `setRuntimeVisibility false`（レシピ04。1枚ずつ、apply-op.mjs で dry-run→commit、1 op = 1 git commit）。同値再設定は reject（no-op 保護）なので現在値を先に確認。
    - **留意**: レシピ10 順序則は「所属→メッシュ→デフォーマ→可視旗」。false 方向への明示化は「切替前の絵に差分素材が漏れ出る」事故の予防であり順序則と整合すると読んだが、指揮書に明文が無い（質問10）。レシピ04 の「足場の返却」原則により、この旗は工程5で variant ゲートに引き継ぐ恒久措置である旨をシートに記録する。
    - ランナー apply-op.mjs / run-batch.mjs は closed-problems/ 配下 = 封印対象という矛盾がある（質問1）。
16. 明示化後レンダ1枚（変化なしが期待値——空メッシュは元々描かれない。差分ゼロ自体が「偶然でなく旗で隠れている」ことの証跡になる）。

### Phase F: 【gate】スコープ合意（提出束）

17. 提出物: ①意味論解決表（曖昧行 = 質問付き）②素材マニフェスト + 不足の一括依頼リスト ③正典値実測シート（宣言値版）④開眼レンダ + validate 結果 ⑤可視旗明示化の一覧。指揮書 §4 の定型様式は sweep レンダ前提で工程0には合わない部分があるため、③残ダイヤル明示に相当するものとして**合意項目リスト**を出す。
18. 合意を求める項目: rigging 対象の意味論列挙（転置はしご5軸 + 眼球XY + 開閉 + 口パク + 揺れ系統の分割案 + 差分）/ 除外（例: BodyY は工程列に無い——設計か確認: 質問9）/ 演出ゲインの初期方針（ゲイン1基準 = 鼻振幅 ≈ 頬幅の10%が上品、〜20%が演出強め: レシピ06。κ・damping 等は後工程ダイヤルである旨の予告のみ）/ ユーザー語彙の確定 / 想定身長（px→cm）/ variant グループ設計をこの gate でやるか工程5冒頭か（質問11）。
19. gate 通過後: 解決表・シートを committed 版として確定し、工程1（メッシュ一括）の委任文の材料にする。

### op 発行一歩手前の粒度での成果物一覧

- 読み取りコマンド封筒 JSON × N（validate 1・renderView 2・inspectEvaluatedGeometry 1バッチ〜十数件）— 全て作成可能。agentId 等 session フィールドの値規約のみ仮置き（質問18）
- 変異 op スペック × 可視旗枚数分（setRuntimeVisibility。basePackageRevision は run-batch.mjs の自動充填を使う想定）
- 永続ファイル: 意味論解決表・素材マニフェスト・正典値実測シート・gate 提出文

## 2. 質問リスト（指揮書と craft だけでは決められない点。推測で埋めた箇所は明記）

**封じ込めの矛盾（構造的・最優先）**

1. **実行ランナーの封じ込め矛盾**: 変異 op の実証済みランナー apply-op.mjs（レシピ00）と run-batch.mjs（_map「実行系の改善」）はどちらも `closed-problems/01-eyeball-x/experiment/` 配下にある。2周目封印規約（指揮書 §0・§5）は closed-problems/ を「読まない」と定める。**ランナーの読込・実行は例外か**。例外なら封じ込め文の改訂が要る。→ 計画では「例外として許可」と推測して組み込んだ。
2. **git log 禁止 vs レシピ00 完了チェックの矛盾**: 封じ込め（指揮書 §5）は「状態確認は git status のみ可（git log 禁止）」だが、レシピ00 完了チェックは「git log に baseline がある」を要求する。→ 計画では「自分の commit コマンド出力の記録で代替」と推測で埋めた。どちらが正か。
3. **委任較正記録の型の所在**: 指揮書 §3 は「委任の較正記録は research/delegation-calibration-log.md の型に従い続ける」と言うが、research/ は封印対象。孫委任（質問14）をすれば工程0でも較正記録が発生する。型の参照は例外か、型を指揮書へ転記すべきか。

**工程0の手順そのものの穴**

4. **正典値実測シートの計測基底の時系列問題**: 工程0はメッシュ未生成のため rest bbox = 宣言 bounds しか取れない。だがレシピ06 は「生成後の実頂点範囲」を要求し、「頬幅 = 顔メッシュ bbox 幅」（ゲイン1基準の分母）もメッシュ前提。シートが「以後の全数値の唯一の出所」であるためには、**工程1後の再計測・追記の手順**が指揮書に要るのではないか。→ 計画では「宣言値列 + 工程1後の頂点範囲列の二段構え」と推測で埋めた。
5. **px→cm 宣言に必要な想定身長**: レシピ08 の宣言（例: 18px=1cm）は「全身 px と想定身長から」導く。想定身長はユーザーに聞くしかない。→ gate 合意項目に入れた（これは仕様通りの質問かもしれないが、指揮書の工程0節に「身長をユーザーに聞け」の明文は無い）。
6. **ユーザー語彙の一次ソース**: 解決表の「ユーザー語彙」列は、私が displayName から仮案を書き gate で確認する方式か、先にユーザーの呼び名リストを受領する方式か。→ 前者と推測で埋めた。
7. **眼球 Y の設計根拠の不在**: 指揮書 工程2 は「眼球XY」だが、レシピ02 は X のみ。Y の振幅（(白目高−虹彩高)/2 の転置か）・縦 squash s の要否は未記述。統一原理（レシピ06 末尾）の「眼球も同族・純平行移動」から転置可能と推測したが、実証記録が無い。工程0の実測シートに白目/虹彩の高さを入れるかどうかに影響するため、工程0時点で確認したい（→ 高さも採寸する、で推測実装済み）。
8. **口系パラメータの実 ID**: Mouth Open・母音のプリセット ID はどのレシピにも明記が無い。preset カタログ（parameter-presets.ts）を読んで解決する計画だが、**母音がプリセットに無い場合**カスタム createParameter を作ってよいか（レシピ08 の「createParameter 不要・禁止」は sway プリセット文脈であり、一般則かが不明）。
9. **BodyY の不在は設計か**: 転置はしごは FaceX→FaceY→FaceZ→BodyX→BodyZ で BodyY が無い。スコープ外（除外リスト行き）が正しいか、単なる1周目の未踏か。スコープ合意 gate の除外欄に影響する。
10. **可視旗明示化とレシピ10 順序則の整合**: 工程0で差分素材の旗を false に明示することと、レシピ10 の順序則「所属→メッシュ→デフォーマ→可視旗」の関係が指揮書に明文化されていない。false 方向は安全（漏れ出し予防）と推測したが、工程5で旗を扱い直す前提の宣言が工程0節に無い。
11. **variant グループ設計の合意タイミング**: レシピ10 §1 の「ユーザーと合意する項目」（グループ名・mode・所属表・defaultActive）は、工程0のスコープ gate で合意するのか、工程5冒頭か。素材マニフェストが衣装差分を照合する以上、工程0で所属表の意味論だけは合意するのが自然と推測。
12. **工程タグ接頭辞の書式**: 一級規則2「工程タグ接頭辞」の正確な語彙（`[stage0]`? `[cp番号]`? 1周目の `[modify]` 系?）が未定義。→ `[stage0]` と仮置き。
13. **素材不足の一括依頼後の供給手順**: ユーザーが不足素材を追加する方法（PSD 再インポート？既存パッケージへの部分追加？）と、それが既存ワークスペース（packageRevision・生成済みメッシュ・可視旗・解決表の ID 安定性）に与える影響が craft のどこにも無い。供給待ちと工程1着手の順序（全部待つか、既存分を先行するか）も未定義。**1周目の律速を構造で消す趣旨に直結する穴**。
14. **工程0の委任分担の指定**: 指揮書 §0 は「実装は工程単位でクリーン Fable へ」「調査・棚卸しの大物は非 Fable（opus 級）へ」の両方を言うが、工程0はほぼ棚卸しでできている。工程0全体を opus に出すのか、クリーン Fable が受けて列挙だけ孫委任するのか。→ 後者と推測で埋めた（解決表の曖昧判定は解釈的調査 = 上位モデル、の配分原則から）。
15. **renderView 出力先の規約**: outDir・命名・レンダ成果物の保管場所（gate 提出束・報告の「レンダパス」）の規約が無い。→ STATE dir 隣の `renders/` と仮置き。
16. **BodyZ の pivot 候補**: FaceZ は「首素材 bbox 中心」の実測レシピがあるが、BodyZ の pivot の相場・実測法（腰? 脊柱下端?）が無い。工程0の採寸リストに何を入れるべきか。→ 胴 bbox と alpha 重心だけ採っておく、で推測実装。
17. **成果物（解決表・マニフェスト・実測シート）の置き場所とファイル名の規約**: 指揮書は成果物の存在を要求するが所在を定めない。<PKG> 内（git 管理に乗る）か、discussion 配下か、STATE dir か。gen スクリプトからの参照性と git 巻き戻しとの関係（<PKG> 内に置くと op の巻き戻しでシートも巻き戻る）まで含めて規約が要る。→ 周回用作業ディレクトリと仮置き。
18. **command 封筒の session フィールド規約**（軽微）: agentId 等の値の慣例が未記述。→ 周回名+工程名で仮置き。

## 4. 自己判定

**穴があり条件付き**。工程の骨格（A→F の順序・成果物・gate 提出物）は指揮書と craft だけで組み立てられ、読み取り系コマンドの封筒粒度まで落ちた。ただし (a) 封じ込めの矛盾2件（質問1・2）はランナー実行と完了チェックという工程0の必須動作に直接刺さっており、解消なしに op 発行へ進むと規約違反が確定する。(b) 成果物の置き場所（質問17）と実測シートの計測基底（質問4）は後続全工程が参照する基盤であり、仮置きのまま走ると工程1以降で手戻りになる。この4件の裁定があれば計画は確定する。
