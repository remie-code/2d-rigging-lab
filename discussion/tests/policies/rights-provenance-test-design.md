# Rights / Provenance Test Design

> P1 policy for proving fixture, package, AI edit, demo, and proposal assets are rights-clean enough for the project gate.

## 1. Purpose

Rights/provenance tests prove that source assets and derived artifacts have traceable authorship, license or permission metadata, display/redistribution flags, AI-use records, and links from source assets to package objects and captures.

This policy does not make legal conclusions. It defines test evidence and review status for the Private 2D Rigging Lab / Prototype.

## 2. Basis

### Official Facts

No external official facts are used as test oracles in this policy.

### Repository Facts

- `AC-MVP-002` requires rights-clean input assets, generated assets, fixtures, AI edits, and provenance records.
- `AC-RIGHTS-001` through `AC-RIGHTS-005` require no required dependency on non-redistributable assets, rights metadata, demo/proposal hygiene, proprietary format exclusion, and no SDK/Core dependency.
- `SC-MVP-001` requires provenance for source art and derived package objects.
- `SC-AI-003` and `SC-AI-004` require AI assistance to classify provenance metadata and leave audit logs.
- `streaming-demo-policy.md` requires demo surfaces to use only original, generated, or explicitly permitted assets.

### Assumptions

- Fixtures can include blocked or incomplete metadata only when the fixture purpose is to test validator failure.
- Rights review status is project evidence, not legal advice.

## 3. Policy Decisions

- Every source asset in an MVP fixture must have a provenance record.
- Every texture, drawable, generated package artifact, AI edit, capture, and proposal attachment must trace back to one or more source provenance records.
- Missing author, license or permission reference, AI-use status, display flag, or redistribution flag is at least `needs_review`; it is `fail` when used in MVP acceptance or demo capture.
- Blocked assets must not appear in demo-safe captures or proposal material.
- Existing Cubism models, official samples, third-party Live2D models, nizima assets, commercial models, Cubism SDK/Core assets, and rights-unknown materials are forbidden fixture sources except as negative metadata strings inside invalid test fixtures.
- Provenance must not use Cubism formats, Viewer matching, Physics compatibility, or existing model behavior as evidence.

## 4. Provenance Record

Each source or derived asset has a logical provenance record.

| Field | Required | Meaning |
|-------|----------|---------|
| `provenanceId` | yes | Stable ID without spaces. |
| `assetId` | yes | Stable asset ID without spaces. |
| `assetKind` | yes | `sourcePsd`, `sourcePng`, `texture`, `drawable`, `package`, `capture`, `aiEdit`, `proposalAttachment`, or equivalent project-defined kind. |
| `sourceType` | yes | `original`, `generated`, `explicitPermission`, `derived`, `testInvalid`, or `blocked`. |
| `author` | yes | Person, project actor, or generation system responsible for the asset. |
| `createdBy` | yes | Human, tool, or AI process that created this artifact. |
| `licenseName` | yes | License or permission label. |
| `licenseRef` | yes | Local permission record or license reference. |
| `permissionScope` | yes | Allowed project uses. |
| `displayAllowed` | yes | Whether the asset may appear in demo/proposal surfaces. |
| `redistributionAllowed` | yes | Whether the asset may be redistributed. |
| `modificationAllowed` | yes | Whether derived package artifacts may be created. |
| `aiGenerated` | yes | Whether generated by AI. |
| `aiEdited` | yes | Whether edited by AI. |
| `aiTool` | no | Tool/provider summary when AI was used. |
| `aiPromptSummary` | no | Short non-sensitive summary of AI prompt or edit intent. |
| `sourceFileHash` | yes | Hash for persisted source files when applicable. |
| `parentProvenanceIds` | yes | Source records for derived assets. |
| `derivedArtifactIds` | yes | Artifacts derived from this provenance record. |
| `relatedOperationIds` | no | Operations that created or changed provenance metadata. |
| `reviewStatus` | yes | `cleared`, `needs_review`, or `blocked`. |
| `blockedReason` | no | Required when `reviewStatus: "blocked"`. |
| `reviewedBy` | no | Reviewer or automated profile. |
| `reviewedAt` | no | Timestamp, excluded from deterministic hashes unless explicitly included. |

## 5. Fixture Manifest Requirements

Each fixture used by acceptance, GUI evidence, AI, demo-safe, or proposal tests must declare:

| Field | Required | Rule |
|-------|----------|------|
| `fixtureId` | yes | Stable ID without spaces. |
| `rightsProfile` | yes | `mvp-clean`, `demo-clean`, `proposal-clean`, `invalid-missing`, `invalid-blocked`, or equivalent profile. |
| `sourceAssets` | yes | Source asset refs with provenance IDs. |
| `derivedAssets` | yes | Texture, drawable, package, capture, and AI edit refs. |
| `provenanceRecords` | yes | Complete records or refs. |
| `demoAllowedAssetIds` | yes | Assets allowed on demo surface. |
| `blockedAssetIds` | yes | Assets intentionally blocked or invalid. Empty for clean fixtures. |
| `rightsExpectedStatus` | yes | Expected validator status. |
| `negativeFixtureReason` | no | Required for invalid fixtures. |
| `noThirdPartyModelDeclaration` | yes | Declaration that the fixture does not use existing Cubism, official sample, third-party, nizima, or commercial model assets unless it is a negative metadata-only fixture. |

## 6. Provenance Graph Checks

The provenance graph must prove:

- source asset to imported layer or split PNG;
- source asset to texture;
- texture to drawable;
- drawable to package object;
- package object to operation IDs that created or changed it;
- package object to capture or proposal attachment when displayed;
- AI suggestion to repair candidate provenance;
- approved AI repair to committed operation ID and derived artifact provenance.

Any derived artifact without a parent provenance record fails acceptance.

## 7. Required Checks

| Check ID | Gate | Failure condition |
|----------|------|-------------------|
| `rights.metadata.complete` | `mvp-blocking` | Required provenance fields are missing for MVP evidence. |
| `rights.source.forbidden` | `mvp-blocking` | Fixture depends on existing Cubism model, official sample, third-party Live2D model, nizima asset, commercial model, SDK/Core asset, or rights-unknown material. |
| `rights.display.blockedAsset` | `mvp-blocking` | Blocked or unknown asset appears in demo/proposal/capture surface. |
| `rights.derived.parentMissing` | `mvp-blocking` | Derived asset lacks parent provenance. |
| `rights.aiEdit.provenanceRequired` | `mvp-blocking` | AI-generated or AI-edited artifact lacks AI-use metadata. |
| `rights.permission.scopeMismatch` | `mvp-blocking` | Asset is used outside declared display, redistribution, or modification scope. |
| `rights.legalClaim.forbidden` | `mvp-blocking` | Test or AI output declares legal safety or patent clearance as fact. |
| `rights.proposal.attachmentClean` | `p1-blocking` | Proposal material lacks provenance or includes blocked/internal/private package artifacts. |

## 9. Rights / Provenance Report

Tests emit or reference `rights-provenance-report.json`.

| Field | Required | Meaning |
|-------|----------|---------|
| `schemaVersion` | yes | Literal policy version, currently `rights-provenance-report-v1`. |
| `reportId` | yes | Stable ID without spaces. |
| `testId` | yes | Test ID without spaces. |
| `fixtureId` | yes | Fixture ID without spaces. |
| `rightsProfile` | yes | Profile used for the check. |
| `assetResults` | yes | Per-asset status and findings. |
| `provenanceGraphStatus` | yes | `complete`, `incomplete`, or `blocked`. |
| `displayStatus` | yes | Whether demo/proposal display is allowed. |
| `redistributionStatus` | yes | Whether redistribution is allowed by metadata. |
| `aiUseStatus` | yes | AI-use completeness status. |
| `forbiddenSourceFindings` | yes | Forbidden source/dependency findings. |
| `operationRefs` | no | Operations that created or repaired metadata. |
| `recommendedAction` | yes | `pass`, `needs_review`, or `block`. |
| `status` | yes | Final `pass`, `fail`, or `needs_review`. |

## 10. Pass / Fail Rules

- `pass`: all required provenance records are complete, usage is within declared scope, displayed assets are cleared, and no forbidden source is present.
- `needs_review`: metadata exists but permission scope, AI-use summary, or reviewer confirmation is incomplete and the asset is not used in a blocking MVP/demo path.
- `fail`: required metadata is missing in MVP evidence, blocked asset appears, a derived chain is broken, a forbidden source is used, or legal safety is asserted as fact.
